# ACP Window (Agent Chats)

The ACP window is a chat window that looks like the notebook assistance window, but talks to an external coding agent (currently [OpenCode](https://opencode.ai)) through the [Agent Client Protocol](https://agentclientprotocol.com) (ACP) instead of using Chatbook's own LLM pipeline. The agent runs as a child process (`opencode acp`), works in a project folder, and asks the user for permission before editing files or running shell commands. The protocol connection is provided by the ACPLink paclet. With the `"SSHSettings"` setting, the agent, the project folder and git are on another computer, reached over ssh (see [Remote mode (SSH)](#remote-mode-ssh)).

Source: `Source/Chatbook/ACP/`. Tests: `Tests/ACPState.wlt`, `Tests/ACPTranscript.wlt`, `Tests/ACPRendering.wlt`, `Tests/ACPWindow.wlt`, `Tests/ACPConnection.wlt`, `Tests/ACPGit.wlt`, `Tests/ACPReview.wlt`, `Tests/ACPPermissionDetails.wlt`, `Tests/ACPSessions.wlt`, `Tests/ACPRemote.wlt`, `Tests/ACPFolderPicker.wlt`, `Tests/ACPNotebookTools.wlt`, `Tests/ACPMCP.wlt`. Remote mode is tested with a fake ssh (`Tests/Data/ACP/fake-ssh`, with the helpers in `Tests/Data/ACP/FakeSSH.wl`; see [Testing remote mode](#testing-remote-mode)).

## Opening the window

```wl
ShowNotebookAssistance[ "ACPWindow" ]                    (* attached to the current user notebook, if any *)
ShowNotebookAssistance[ nbo, "ACPWindow" ]               (* nbo: NotebookObject or None *)
ShowNotebookAssistance[ cell, "ACPWindow" ]              (* the cell's notebook *)

ShowNotebookAssistance[
    "ACPWindow",
    "Input"                -> "Explain the build script",   (* put text in the input field *)
    "EvaluateInput"        -> True,                         (* and send it (queued until connected) *)
    "NewChat"              -> True,                         (* close the existing ACP window and start over *)
    "ChatNotebookSettings" -> <| "ProjectDirectory" -> "~/src/myproject" |>
]

(* the agent, the project folder and git on another computer (remote mode) *)
ShowNotebookAssistance[
    "ACPWindow",
    "ChatNotebookSettings" -> <|
        "SSHSettings" -> <|
            "Username"    -> "ubuntu",
            "MachineName" -> "ec2-203-0-113-100.compute-1.amazonaws.com",
            "Arguments"   -> { "-i", "C:/Users/me/keys/aws_key.pem" }
        |>,
        "ProjectDirectory" -> "~/projects/app"                  (* a folder on that computer *)
    |>
]
```

The window is 480 points wide (600 on macOS; `$acpWindowWidth`), wider than the Notebook Assistant's 360 (450), since tool cards, the permission panel and the toolbar need the room. It is placed left of the source notebook by the Notebook Assistant's `attachToLeft` with the width as a third argument (the Notebook Assistant's two-argument form is unchanged), which scales it with the source notebook's magnification and caps it so that the window fits on the source's display: its `"FullRegion"` less 32 points for the frame and a gap at each edge, at least 240 points (`attachedWindowWidth`, pure). Like the Notebook Assistant, the window gets this width, its position and its magnification (0.85 × the source's) again each time it is shown from a notebook. A window without a source notebook gets the width capped to its own display (`notebookDisplayRange`) at the display's left edge.

There is at most one ACP window (found by `findCurrentWorkspaceChat["ACP"]`). Calling `ShowNotebookAssistance` again reuses it; an explicit `"ProjectDirectory"` that differs from the window's directory switches the window to it (starting a new session), unless a turn is running. Explicit `"ACPAgent"`, `"ACPAgentCommandLine"`, `"ACPMCPServer"`, `"ACPModel"` and `"SSHSettings"` settings are applied to the open window too: a new agent or command line reconnects (after the running turn, if there is one), and so does a new `"ACPMCPServer"` of a local window (turning it off ends the agent's access to the notebook tools at once, see [MCP server](#mcp-server); a remote window only keeps the value), a new model is selected in the current session, and a window in `"Error"` (e.g. OpenCode was not found) reconnects. `"SSHSettings"` for another host (another machine, user or port; local counts as a host too) switches the window to that host: a new chat in the call's folder or the host's last one (refused while a turn runs or a session loads). Other changes of `"SSHSettings"` (a key file, other ssh options) reconnect, like a new command line. See [Settings and host identity](#settings-and-host-identity).

### Settings

`"ChatNotebookSettings"` keys understood by the ACP window (validated by `validateACPWindowSettings` in `ChatModes/ShowNotebookAssistance.wl`; invalid values give `ShowNotebookAssistance::InvalidACPWindowSettings`, and an invalid `"SSHSettings"` gives `ShowNotebookAssistance::InvalidACPSSHSettings` with the reason):

| Key | Values | Default |
|---|---|---|
| `"ProjectDirectory"` | directory (string or `File`), `None`, `Automatic` | `Automatic`: the last project folder used, else the source notebook's folder, else none (the window asks for one). With `"SSHSettings"`: a folder on the remote computer, absolute or starting with `~/` (`~` is the remote home folder), never checked on this computer; `Automatic` is the host's last project folder, else none (the [folder picker](#project-folders-and-the-folder-picker) opens) |
| `"ACPAgent"` | `"OpenCode"`, `Automatic` | `"OpenCode"` |
| `"ACPAgentCommandLine"` | `Automatic`; a program (string or `File`: a path, or a command name looked up like the default), run with the agent's arguments (`acp`); or the whole command line `{program, args...}`, as in `RunProcess` (the agent's arguments are not added). Always the command on the computer that runs the agent: with `"SSHSettings"` a path or name on the remote computer, looked up there | `Automatic`: `opencode acp`, with `opencode` found by searching `PATH`, then `~/.opencode/bin`, `~/.local/bin`, `~/.bun/bin`, `~/.npm-global/bin`, then `/opt/homebrew/bin` and `/usr/local/bin` (a front end started from the macOS Dock gives the kernel a minimal `PATH`); remote: the same search in the remote `PATH` and folders. A switch to another host resets it to `Automatic` (with a notice), unless the same call gives one |
| `"ACPModel"` | model value such as `"openai/gpt-6.1-sol"`, `Automatic` | the last model chosen for this agent, else `llmkit/gpt-5.4` (if offered), else `openai/gpt-6.1-sol` (if offered), else the agent's default |
| `"ACPMCPServer"` | `True`, `False`, `Automatic` | `Automatic`: a local window offers the agent the [MCP server](#mcp-server) of the notebook tools (if an AgentTools paclet with `StartMCPSocketServer` is available) when Chatbook starts the agent's own program: the default command line, a program given as `"ACPAgentCommandLine"`, or a whole command line whose program has the agent's name (e.g. `{"/opt/oc/bin/opencode", "acp", "--print-logs"}`). A command line that runs another program (`docker`, `env`, `ssh`, a wrapper script) may not pass `OPENCODE_CONFIG_CONTENT` on, and with it the "ask" rules of the tools that change open notebooks, so it gets the server only with `True` (`acpMCPEnabledQ`, `acpOwnAgentCommandQ`). `True`: offered to any local agent. `False`: no MCP servers from Chatbook. Remote windows never offer it. A change reconnects a local window (and turning the server off revokes the connection's token at once); a remote window only keeps the value |
| `"SSHSettings"` | `None`, `Automatic`; a host name or `"user@host"`; `<\| "MachineName" -> host, "Username" -> user, "Arguments" -> {ssh options...}, "Executable" -> ssh program \|>` (or a list of rules). See [Settings and host identity](#settings-and-host-identity) | `None`: everything on this computer |

User choices are persisted in `CurrentValue[$FrontEnd, {PrivateFrontEndOptions, "InterfaceSettings", "Chatbook", "ACP", ...}]`: `"LastProjectDirectory"` (local windows), `{"LastModel", agent}`, `{"LastEffort", agent}`, `{"RecentModels", agent}`, and for remote windows, per host (`hostKey`, see [Settings and host identity](#settings-and-host-identity)), `{"SSH", hostKey, "LastProjectDirectory"}` and `{"SSH", hostKey, "Home"}` (the remote home folder, from a launch's `home` marker (also a failed launch's) or a folder picker listing. It seeds a new window's `"RemoteHome"`, which is used for display and, until a launch reports the real home, to expand a `~` folder given later for the same host. A new window's own `~` folder is left to the launch), and the folder picker's `{"FolderPickerShowHidden"}` (the mode is not persisted). Without a front end (tests) the same keys are kept in `$headlessSettings`.

The window's notebook-level state lives in its `TaggingRules`: `"ChatNotebookSettings"` (with `"AppName" -> "ACP"`, `"ACPWindow" -> True`, `"WorkspaceChat" -> True`) and `"ACP"` (`"ProjectDirectory"`, `"Agent"`, `"Settings"` (the explicit `"ACPAgent"`, `"ACPAgentCommandLine"`, `"ACPMCPServer"`, `"ACPModel"` and `"SSHSettings"` settings, the last in its canonical form, so a window rebuilt after a kernel restart connects the same way, to the same host), `"Input"`, `"Busy"`, `"KernelSessionID"`, `"ResumableSessionID"`, and for [attachments](#attachments) `"Attachments"` (the draft's references), `"QueuedPrompt"` and `"PreparingPrompt"` (the text and the references of a queued message and of one that is prepared), and `"PromptTarget"` (where a message of the window's [prompt notebooks](#prompt-notebook) goes, as their docked cells show it)).

When OpenCode is not found, the error's "Locate OpenCode..." button opens a file chooser (run by the front end); the chosen file becomes the program of the window's `"ACPAgentCommandLine"` setting and the window reconnects. Remote windows have no such button (a local file is no program on the remote computer): their error says how to install OpenCode there or give its command line.

The program of a command line (`acpFindProgram`) is a path (with a directory part, or starting with `~`), which must exist, or a command name, looked up like `opencode` (on Windows a name without an extension also matches `.exe` and `.cmd`); a program that is not found gives the "not found" error with its name. The process gets the window's environment (`OPENCODE_CONFIG_CONTENT`, which makes OpenCode ask before edits, shell commands and the notebook tools that change open notebooks, and the LLMKit key). To run the agent on another computer, use `"SSHSettings"` (see [Remote mode (SSH)](#remote-mode-ssh)), not a command line such as `{"ssh", host, "~/.opencode/bin/opencode", "acp"}`: only in remote mode does the environment reach the agent and are the project folder, git and the Sessions window's folders on that computer. A command line that starts the agent somewhere else by itself (ssh, a container) does not pass the environment on (ssh forwards no variables by default), so the agent there uses its own configuration, and OpenCode's default is to edit files and run commands without asking. Such a command line therefore gets the notebook tools' MCP server only with `"ACPMCPServer" -> True` (an agent that can reach this computer's 127.0.0.1, e.g. in a container with `--network=host`, could change the open notebooks without asking).

## State model

All agent traffic is handled by ACPLink's reader task, which calls Chatbook's handlers asynchronously; nothing waits for the agent. Kernel state is a cache that can be rebuilt from the window's `TaggingRules`.

**Window records** (`$acpWindows[nbo]`): `"Status"` (`"NoDirectory"`, `"Connecting"`, `"Ready"`, `"Running"`, `"Restoring"` (a saved session is loaded and written, see [Sessions](#sessions)), `"Disconnected"`, `"Error"`), `"Error"`, `"ProjectDirectory"`, `"Connection"`, `"SessionID"`, `"ResumableSessionID"`, `"AgentInfo"`, `"ConfigOptions"` (the raw ACP config options: model, mode, effort), `"PendingConfig"`, `"PendingPermissions"` (by request ID, in arrival order), `"Requests"` (continuations of outstanding client requests, keyed by string IDs `"cb-..."`), `"CurrentTurn"`, `"Usage"`, `"Notice"` (a string, or `<| "Text", "Command" |>` for a notice with a terminal command, shown as typed in the code font with "Copy command", see [Everything else](#everything-else)), `"QueuedPrompt"` (the messages sent while a turn runs, with their prepared attachments, in the order of their Send clicks: `<| "Text", "Attachments", "At" |>`; see [Attachments](#attachments), "The queue"), `"QueuedTurn"`, `"Attachments"` (the draft's attachments: references) and `"Preparing"` (a message whose attachments are prepared; see [Attachments](#attachments)), `"Settings"`, `"Git"` (the git summary of the project folder, which the "Review" button shows, see [Reviewing changes](#reviewing-changes)), `"Sessions"`, `"Restore"` and `"PendingRestore"` (see [Sessions](#sessions)), `"SessionOrigin"` (`"New"`, `"Resumed"` or `"Loaded"`), `"ErrorDetailOpen"` (whether the toolbar's error view shows its details, see [Everything else](#everything-else)), `"InitSendFailedAt"` (see [the `initialize` grace period](#launching-the-agent)), and more (see the comments in `UI.wl`, `Connection.wl`, `Git.wl` and `Sessions.wl`). Remote windows also have `"LaunchNonce"` (per launch), `"Remote"` (the launch's host, host key, canonical settings, agent command line and install URL; no secrets), `"RemoteHome"`, `"RemoteAgentPath"`, `"RemoteVerified"` (a launch reached the host), `"LaunchMarkers"`, `"LaunchProgress"` (the number of the launch's progress lines seen on standard error, which restart the `initialize` timeout, see [Launching the agent](#launching-the-agent)) and `"FolderPicker"` (the [folder picker's](#project-folders-and-the-folder-picker) store); their `"Settings"` hold the canonical `"SSHSettings"`.

**Turn records** (`$acpTurns[turnID]`, created by `acpNewTurn`): the prompt, its `"Attachments"` (prepared, see [Attachments](#attachments)), cells, timing, `"StopReason"`, `"ClientCancel"` (`"Stop"`/`"Reject"`), `"Error"`, `"Remote"` (`acpTurnRemote`: `None`, or the host of a remote window's turn, `<| "Host", "Short", "Home" |>`; its paths are on that host), and the transcript as `"Order"` (a list of entity keys) plus `"Entities"`. Entity keys are lists: `{"Message", id}`, `{"Thought", id}`, `{"Tool", toolCallId}`, `{"Permission", requestID}`, `{"Notice", n}`, `{"Plan"}`. Tool entities keep the canonical tool name (`bash` becomes `"shell"`, `task` becomes `"subagent"`, `apply_patch` becomes `"patch"`), status, `"ClientOutcome"` (`"Declined"`/`"Stopped"`), raw input/output, accumulated diffs and the permission request.

The reducer functions in `Transcript.wl` (`acpApplyUpdate`, `acpApplyPermissionRequest`, `acpApplyPermissionOutcome`, `acpApplyPermissionWithdrawn`, `acpApplyClientCancel`, `acpApplyTurnEnd`, `acpApplyNotice`) are pure: they take a turn and return `<|"Turn" -> new, "Changed" -> {keys...}, "Layout" -> bool|>`, which `acpTurnUpdate` uses to mark the changed views dirty.

`acpTurnSplit[turn]` decides what the final cell shows: the answer is the run of trailing top-level messages after the last non-message entity; everything before it goes into a closed "Worked for ..." opener. Its label is the time worked, without the time spent waiting for the user's approval; when that was at least 5 s (`$significantWaitingTime`), the label has a tooltip that says how long ("Plus 4m 2s waiting for your approval", `acpWorkedForTooltip`; a `TooltipBox`, which renders anywhere). If the turn did not end normally (Stop, a declined permission, an error, `max_tokens`, ...) and there is no answer, the last step's tools (from the first one that did not complete normally, or only the last tool if all completed) and the message right before them are shown expanded below the opener, followed by a status line such as "You declined: edit notes.md. Tell OpenCode what to do instead."

**Rendering.** The active output cell has one `Dynamic` that tracks the turn's layout symbol and contains one `Dynamic` per entity, each tracking that entity's change symbol (`acpLayoutSymbol`, `acpEntitySymbol`). Handlers mark symbols dirty; the pump task bumps the dirty ones every 0.2 s while a turn runs, a window connects, or a connection is open. Entity boxes are cached by version; streaming messages only re-format the text after the last blank line. Opener state for live views is kept in `$acpOpen` and toggled by preemptive event handlers. The live view's "Working" opener starts closed (`$workOpenDefault`, `workOpenQ` in Rendering.wl): its header's label ("Working · 1m 5s · Running `ls`", refreshed once a second) says what is happening, and nothing shows below it, not even the answer as it is written, until the user opens it. When the turn ends, `acpFinalizeTurn` (UI.wl) replaces the active cell with the static `acpFinalCell`, whose tool-card openers are front-end-only (`staticOpener`: a `DynamicModule` over the card's pane, built-in boxes only, so they render anywhere, including a copied or saved cell, without the kernel). Their click handlers use only the front end's own functions (`` FEPrivate`Set[Typeset`open, FEPrivate`If[Typeset`open, False, True]] ``, `staticOpenerHeader`; the review window's cards too): with `Not`, a click in a saved copy with no kernel running started a kernel and the card did not open. The "Worked for" opener is front-end-only too (`workOpenerBoxes`): the boxes of Chatbook's `ThoughtsOpener` template (the closed and the open view in a `PaneSelector`, the italic label and chevron that darken under the pointer, the content in the `ThinkingContent` template's pane, the "Hide" line), built in, with a `DynamicModule` variable of its own (`` Typeset`workOpen ``) that the header and "Hide" toggle with `FEPrivate`Set`/`FEPrivate`If`, a "Hide" label that is a `DynamicBox` of a front end resource (the template's is one of `ToBoxes`, which needs the kernel) and `DynamicModuleValues :> {}` (the template's `Automatic` needs the kernel). In a real front end it is pixel-identical to the template with the same label and content: closed, open and under the pointer, at magnifications 0.85, 1, 1.5 and 2 in light mode and at 0.85 and 2 in dark mode. The template version made a pasted copy hang (see "Copies and pastes" in [Tool cards](#tool-cards)). The openers of single thoughts are still Chatbook's `ThoughtsOpener` template, which needs a kernel in a copy (see Known limitations). The opener's inline cell keeps the `"ThoughtsOpener"` style, with `TaggingRules -> <|"ACPWork" -> <|"Duration" -> seconds|>|>` where the template had its metadata. A card's pane holds a grid: its first row is the header line, built by `cardHeaderGrid` as in the live view, with a chevron that follows the state (a `PaneSelector` of the two chevrons) and the click handler; its second row is a `PaneSelector` that shows the body (with the divider and the "Hide" line, which close the card too) when the card is open and `Spacer[{0, 0}]` when it is closed. The grid has `RowMinHeight -> 0` and its baseline on the header row (`BaselinePosition -> {1, 1}`), so a closed card is exactly as tall as a closed live card (a grid row is otherwise a line high even when it shows nothing, and the default baseline added a few points). The header is written once per card, which keeps a final cell with many tool cards from storing the title's fit `DynamicBox` (and a badge's fit switch) twice per card, as the header in both panes of a `PaneSelector` did. An earlier version stored it once as the argument of a `TemplateBox` with an inline `DisplayFunction`; pasting a copy of a final cell whose "Worked for" opener was open then made the front end spin (see "Copies and pastes" in [Tool cards](#tool-cards)).

**Finalization.** The front end must not be evaluating a `Dynamic` of the active cell when the final cell replaces it. A kernel-initiated `NotebookWrite` (or `NotebookDelete`) that replaces a cell while the front end waits for the kernel to evaluate one of that cell's `Dynamic`s, in the middle of formatting the cell, makes WolframNB 15.0.1 log `Assertion "overcounted formatting" failed ... CellControl.cpp:45` and, with many such `Dynamic`s, exit with SIGSEGV about a second later, losing the user's unsaved work. With the "Working" opener open this happened at the end of almost every turn whose last updates came in a burst: each new entity is an inline cell with its own `Dynamic`, which the front end evaluates one by one as it formats them, and the finalization runs in the pump, a scheduled task that holds the kernel for the second or two that rendering the final cell takes, so the front end's next request always waited for it and the write arrived during that wait. Evidence (fe.py, Xvfb, mock agent): a kernel timeline showed entity `Dynamic`s evaluated after the write and the removal of their symbols, just before the crash; a layout bump one pump tick before an otherwise safe write (3 s debounce) reproduced the assertion; with a 3 s debounce, or with the opener closed, it did not happen. So finalization has two steps (UI.wl):

* `acpFinalizeTurn` claims the turn (after the 0.2 s debounce, `$acpFinalizeDebounce`) and freezes its live view (`acpFreezeLiveView`, Rendering.wl): while "Working" is open, it renders the views of all entities into the render cache, then `acpFreezeTurnViews` (State.wl) stops the publication of the turn's layout and entity symbols (`bumpSymbol` skips them) and bumps the layout symbol a last time. The layout's `Dynamic` then renders the frozen view (`liveLayout0`): the same boxes without `Dynamic`s (the entities' cached boxes and the Working header's label put in directly; the front-end-only boxes stay), so it looks the same except that the elapsed time stops, and notes the time in the turn (`"FrozenViewShownAt"`).
* `acpWriteFinalCell` (scheduled every 50 ms, `$acpFreezePoll`) waits until the front end has rendered the frozen view and that was at least `$acpFreezeSettle` (0.15 s) ago (`acpFrozenViewPendingQ`), then renders the final cell and writes it (once: `"FinalWriteClaimed"`) and finishes the turn. After that rendering the front end formats only static boxes, and no symbol of the turn changes any more, so nothing makes it evaluate a `Dynamic` of the cell during the write. The front end does not evaluate the `Dynamic`s of a cell that is scrolled out of view, so it never renders the frozen view of such a cell: after `$acpFreezeTimeout` (5 s) the final cell is rendered in one pump evaluation and written in a later one, and if the user scrolls the cell into view meanwhile (the front end's request waits while the kernel renders), the write waits until that rendering of the frozen view has settled (measured: the request was served right after the render and the write followed 0.4 s later). A freeze that fails, or a cell that is gone, does not delay the write.

The cost is the time to the front end's rendering of the frozen view plus the settle time: in a mock-agent turn ending with a Reject, the final cell was written 0.2 s later than before with "Working" closed and 0.6 s later with it open (the pre-rendering of its cards in the pump included). Measured with fe.py (Linux, Xvfb, WolframNB 15.0.1, the mock agent, "Working" opened by a click or the `ToggleOpen` action): before the change, 6 of 7 turn ends with "Working" open crashed in a 40-card burst followed by `end_turn` (an earlier check had 5 of 5, also with a Reject of the last permission followed at once by a thought, an answer with a code block and `end_turn`), and with the change disabled at run time, 1 of 1 each with a Stop mid-burst (80 cards arriving 50 ms apart), an error response after a 40-card burst and a long turn (streamed thoughts, 12 tools spaced out, code blocks, `end_turn` right after the last message). With it, none of 23 turn ends with "Working" open (those scenarios, a queued prompt, the cell scrolled out of view and back in during the wait, two first turns after a kernel restart, a turn that waited minutes for an approval) and 8 with it closed failed the assertion or crashed. Screenshots taken every 0.15 s showed no change when the frozen view replaced the live one (pixel-identical frames), the final cell in place of the active one as before, the scroll position kept (`AutoScroll -> False`), and a queued prompt's cell after the final cell.

Finalization then drops the turn's state: its change symbols (which are removed), its frozen flag and its render caches. Once a turn is claimed for finalization it always ends: rendering failures fall back to simpler cells, and housekeeping finishes a finalization that has not completed after 30 s (`acpForceFinishTurn`).

Inline cells inside `ChatOutput` cells must use `boxCell`/`textBoxCell` (`Rendering.wl`): `BoxData` cells need their boxes wrapped in `StyleBox[..., "Text"]`, otherwise strings appear in the code font, and `TextData` cells need the `"Text"` style. `Tests/ACPRendering.wlt` checks this for every fixture.

**Thoughts.** Each ACP thought message is one `{"Thought", id}` entity; OpenCode sends each part of an OpenAI reasoning summary as its own message, and such parts are often just a bold title ("**Planning TOML import/export wrappers**"). A finished thought that is a single short line is shown as that line with Chatbook's `ShortThoughts` template: the italic font of the "Thought for ..." labels, no opener and no duration (the label stays in the template's arguments, `{thoughts, label, meta}` like `ThoughtsOpener`, but is not shown), with small vertical margins, so consecutive titles read as a list. `shortThoughtsText` (`Formatting.wl`, also used for Chatbook's own reasoning summaries) decides: after trimming and removing a `**...**` or `__...__` wrapper that covers the whole line, the text has no line break and at most 75 characters (`$shortThoughtsLength`: such a line fits on one line inside the "Worked for" opener of a 480-point window at magnification 0.85, measured with the template's font; a full-width East Asian character counts as 2.5, since it is 1 em wide). A line that starts with an unterminated `**` or `__` (a thought cut off by a stop or an error while its title streamed) keeps the opener, which hides the raw asterisks. The line goes through `markdownItems` like any thought (neutralized, formatted as untrusted content). The final cell uses it (`thoughtsOpenerCell`), and so does the live view once the thought is no longer the last entity (`thoughtCell`: it stays "Thinking..." while it streams, since its text may still be an unterminated `**Plann`; the short form has no state, and the entity's signature includes whether it is active). Other thoughts use `ThoughtsOpener` (`EmptyThoughts` for an empty one). A restored session's turn leaves out its thoughts without text (`emptyThoughtQ`): OpenCode replays an empty reasoning part that the live turn did not show, which would be a "Thoughts" label with nothing in it.

## Threading rules

These rules apply to all code in `ACP/`:

1. **R1. Nothing blocks.** No ACP code holds an evaluation for the length of a turn. Agent traffic is processed by ACPLink's permanent reader task.
2. **R2. Handlers are interrupts.** Reader handlers only update kernel state and mark views dirty: no front end calls, no `NotebookWrite`, no waiting, no synchronous ACPLink requests (they would deadlock inside the reader's `PreemptProtect`), no dialogs. Strings used in handlers come from `acpConnectionLabel`, which never calls the front end. Front end work is deferred with `acpSchedule`.
3. **R3. Isolation.** Every asynchronous or preemptive entry point (reader handlers, scheduled tasks, `Dynamic` renderers, preemptive buttons and event handlers) runs inside `acpIsolated`, which catches everything, defers aborts, blocks Chatbook's chat globals (so an ACP handler can't disturb a notebook assistance chat it interrupted, and vice versa), and records messages in `$acpDebugLog` instead of printing them. The main link evaluations, the MCP drain (see [MCP server](#mcp-server)) and the other jobs it runs (`acpMainLinkRun`: the preparation of a message's [attachments](#attachments) and of a [prompt notebook](#prompt-notebook)'s message, which convert notebooks and rasterize graphics), run in `acpIsolatedAbortable`, the same without `AbortProtect`, so that Alt+. can abort a tool or a job. ACP code never calls `withChatState`, `ChatCellEvaluate`, `evaluateWorkspaceChat` or `StopChat`.
4. **R4. Shared state changes only through `acpWindowUpdate` / `acpTurnUpdate`**, which apply a pure function under `PreemptProtect`.
5. **R5. Deferred work goes through one task.** `acpSchedule[eval]` (or `acpSchedule[eval, delay]`) queues `eval` for the pump task, which evaluates everything that is due every 50 ms, in order, each evaluation isolated; the default delay is 50 ms. Never create one-shot `ScheduledTask`s: in the 15.0.1 kernel, several one-shot tasks coming due together (and recurring tasks that remove themselves at a high rate) can deadlock the kernel for good (see ACPLink's UPSTREAM-NOTES.md, "Kernel scheduler deadlocks"), and `{Now}` ones are silently dropped under load. Anything correctness-critical also has a periodic fallback in a housekeeping function (`acpRegisterHousekeeping`), e.g. finalizing a turn that ended more than 1 s ago, or ending a turn whose Stop got no answer within 10 s. Connection housekeeping (Connection.wl) decides no timeout in a run that comes after the kernel was blocked: more than `$acpStallThreshold` (1.5 s) since its previous run, or no previous run. Such a run is logged as `"HousekeepingGap"`. It can come right after the evaluation that blocked the kernel, in the same pump tick, while an answer that arrived meanwhile is still unread: ACPLink's readers are scheduled tasks too, and could not run either. Only one run in a row is skipped (`$housekeepingSkipped`): the next run decides even if it also came late. It is in a later pump tick, so the readers have run by then, and a kernel that stays busy (every run late) still times out. This applies to the setup, config, session list/load/delete, Stop and stuck-connect timeouts.
6. **R6. Live views never rebuild stateful widgets**: one `Dynamic` per entity, opener state in kernel state, no scroll panes or `DynamicModule` openers in live views. Window views with buttons or menus (toolbar menus, permission panel, status) only re-render when the part of the window state they show changes (`stableDynamic` in Rendering.wl, `acpWindowDerivedDynamic` in UI.wl).
7. **R7. Throttled publication**: handlers mark dirty (the views of a turn that is being finalized are frozen and no longer published, see [Finalization](#state-model)); every fourth pump tick (0.2 s), while a turn runs, a window connects, symbols are dirty, any ACP connection is open, a git or remote one-shot process runs (also one that drains, `acpBackgroundRunsQ`), a folder picker lists, or MCP tool calls wait in the queue or the MCP server runs (`acpMCPPendingQ`: its housekeeping stops the server once it is no longer used, see [MCP server](#mcp-server)), the pump bumps the change symbols and runs the housekeeping functions. Housekeeping must keep running while a connection exists, to detect closed windows and dead or orphaned connections, and while a process or a listing runs, to end one whose continuation was lost. The pump removes itself after 2 s with nothing queued and none of these, so windows that are not connected cost nothing; `acpSchedule` and marking symbols dirty start it again. While ACPLink is in use it has its own recurring task (the deferral pump) as well as one read task per connection.
8. **R8. Front-end-side flags**: the input text, the busy flag and the kernel session that owns the window are in the notebook's `TaggingRules`, so they survive kernel quits and re-attaching the input cell. So are the draft's attachments, and the text and attachments of a queued message and of one that is prepared: a rebuilt window record has the draft, and puts such a message back into the input field and the draft, with a notice (see [Attachments](#attachments)). A [prompt notebook](#prompt-notebook) keeps its owner and status in its own TaggingRules, and its docked cell reads them, and the owner's target and busy flag, with front-end-only Dynamics. The front end sometimes misses the busy flag's reset at the end of a turn (the Stop button stays); `settleBusyFlag` changes it once more, from `False` to `None`, half a second later. `acpCheckSession` runs on every entry point. After a kernel restart (logged as `"KernelRestart"`) it first rebuilds the window record, with its change symbols, from the `TaggingRules`. Then it replaces orphaned active cells with an "Interrupted" note and rebuilds the toolbar and input field (`acpMarkOrphanCells`). In this order the rebuilt views show the window's state at once and track symbols that exist.

Change symbols are created by name (not with `Unique`), and a new window is created invisible and registered before it is shown: the front end does not track symbols created while it evaluates a `DestroyAfterEvaluation` `DynamicBox` (such as the toolbar), so views built from such symbols would never update. After a kernel restart the front end evaluates the toolbar's `DynamicBox` again in a kernel that has no record of the window. `makeACPChatDockedCell[]` then gives a placeholder: the toolbar's frame without views, which creates no symbols and makes no front end calls. Its `Initialization` runs `acpInitializeWindow` in the pump, where `acpCheckSession` rebuilds the record and then the toolbar and input field. If `acpCheckSession` did not replace the placeholder (no restart, e.g. a window whose record was forgotten), `acpInitializeWindow` replaces it with `acpRefreshToolbar` once the record exists (`$placeholderToolbars` in UI.wl notes such windows; `acpForgetWindow` drops the note). `acpRefreshToolbar` finds the toolbar among the window's docked cells by its `"ACPToolbar"` cell tag (also when the tag is given in a list, or the docked cells are a single cell) and replaces it with a toolbar built in the pump. A window whose docked cells have no toolbar keeps them, and this is logged as `"ToolbarNotFound"` with the number of docked cells and their tags. The toolbar's Dynamic never loads ACPLink, connects, or runs git or ssh (rule R1); the only loading in it is the stylesheet's ``Needs["Wolfram`Chatbook`"]``.

## ACPLink

ACPLink is an optional dependency, loaded on demand by `acpLoadACPLink` (`State.wl`) the first time a window connects:

* `PacletFind["ACPLink"]` is used if the paclet is installed.
* Otherwise, if the environment variable `ACPLINK_DIRECTORY` points to an ACPLink paclet directory (the one containing `PacletInfo.wl`), it is loaded with `PacletDirectoryLoad`. This is the easiest way to develop against an ACPLink working tree: set it in the kernel's environment, or with `SetEnvironment["ACPLINK_DIRECTORY" -> "~/ACPLink/ACPLink"]` (expanded path) before the window connects. `Tests/ACPConnection.wlt` uses `~/ACPLink/ACPLink` if the variable is not set.
* ACPLink must be new enough to support `OpenACPConnection[..., "StandardInputPreambleTrigger" -> ...]` (`$acpMinimumACPLinkOption`; remote windows need it, and it comes with the permanent reader task of `UpdateInterval`); otherwise the window shows an `"ACPLinkTooOld"` error, local windows too. A missing paclet gives `"ACPLinkMissing"`.

ACPLink's public symbols are in ``System` ``, so they are only referenced through `acpLink["OpenACPConnection"]` etc., which avoids creating them in kernels (and the MX file) that never open an ACP window.

`Tests/ACPConnection.wlt` runs against a mock agent (`Tests/Data/ACP/MockAgent/mock_acp_agent.py`, needs `python3`) and is skipped when ACPLink or Python is not available. The script is an identical copy of ACPLink's `Tests/MockAgent/mock_acp_agent.py` (its docstring and ACPLink's `Tests/README.md` document it, including the OpenCode-like session options `listPageSize`, `listCursorOnLastPage`, `sessionTitle`, `titleFromPrompt`, `recordHistory`, `strictSessions` and per-session `histories`, the launch-phase options of ACPLink's preamble tests, such as `--stderr-line` and `--start-delay`, and the `mcp_request` step, which calls the session's HTTP MCP servers the way OpenCode does (`initialize` then `notifications/initialized`, the server's headers, JSON or event-stream answers, `"headers"` overrides such as a wrong `Authorization`; the answers are logged as `mcp_response` events and can be used by later steps as `${mcpText:as}`); change it in ACPLink and copy it here. The scenarios in `Tests/Data/ACP/MockAgent/scenarios/` are Chatbook's own (`cb-*`, plus copies of `base-hello` and `base-cancel`).

## OpenCode configuration

OpenCode is started as `opencode acp` in the project folder, with the user's environment (without variables ACPLink cannot pass, such as exported bash functions, which would fail the start with `envval`) plus `OPENCODE_CONFIG_CONTENT`, a JSON config that is merged with the user's own OpenCode configuration (`acpOpenCodeConfigJSON`, `Agents.wl`):

```json
{"$schema": "https://opencode.ai/config.json",
 "permission": {"edit": "ask", "bash": "ask", "WolframNotebooks_InsertCells": "ask",
                "WolframNotebooks_ReplaceCells": "ask", "WolframNotebooks_DeleteCells": "ask"}}
```

so file edits, shell commands and the notebook tools that change notebooks the user has open (see [MCP server](#mcp-server)) ask for permission, as long as `OPENCODE_CONFIG_CONTENT` reaches the agent: it does for the agent's own program and in remote mode, but not necessarily for an `"ACPAgentCommandLine"` that runs another program (see [Opening the window](#opening-the-window)), which therefore gets the MCP server only with `"ACPMCPServer" -> True`. `OPENCODE_CONFIG_DIR` is never used: it would replace the user's global configuration (and drop their MCP servers, such as the Wolfram MCP server). If the user has a Wolfram LLMKit subscription (an active Wolfram API key with the `LLMKitAPIs` grant, found or created through the Wolfram cloud while `$CloudConnected`), the config also gets an `llmkit` provider whose key is passed as `LLMKIT_API_KEY` and referenced as `{env:LLMKIT_API_KEY}`; the key is never logged or stored. A remote OpenCode gets the same two variables (the registry's `"Variables"`, `acpOpenCodeVariables`), exported by the launch script that is sent over ssh's standard input, and merges the config with its own configuration on that computer (see [Launching the agent](#launching-the-agent)).

Model, mode (build/plan) and reasoning effort are ACP session config options, shown as menus in the toolbar. Models are grouped by provider; each provider submenu is labeled with who pays for its models ("OpenAI (your account)", "Wolfram LLMKit", "OpenCode (free)", ...).

## Remote mode (SSH)

### Overview

With `"SSHSettings"`, a window's agent, project folder and git are on another computer (Linux or macOS), reached with the local OpenSSH client (`ssh`; on Windows `ssh.exe`). Source: `SSH.wl` (settings, ssh command, launch script, error classification, remote paths), `Remote.wl` (one-shot operations), `FolderPicker.wl` (the remote folder picker), and remote branches in `Agents.wl`, `Connection.wl`, `Git.wl`, `Review.wl`, `Sessions.wl`, `Rendering.wl` and `UI.wl`.

* **The agent:** one long-lived ssh connection per window. ssh's standard input and output carry the ACP stream, like a local agent's pipes. ssh runs a small bootstrap, which reads a launch script from standard input and runs `opencode acp` in the project folder (see [Launching the agent](#launching-the-agent)).
* **Everything else** (the git summary, "Review changes", the folder picker's listings): one ssh connection per operation, each running one sh script (`acpRemoteRun`, see [Remote operations](#remote-operations)). There is no persistent shell and no connection sharing (`ControlMaster`, which Windows' OpenSSH does not support).
* **The client can be Windows:** nothing in remote mode needs a local POSIX shell. The remote side needs `/bin/sh` and the usual POSIX tools (scripts were checked under dash, bash, busybox and zsh's sh emulation).

Decisions this follows:

* `"SSHSettings"` defaults to `None`: everything local, as before. There is no global "last SSH settings" preference.
* `"ACPAgentCommandLine"` stays independent of ssh: it is the agent's command on the computer that runs it.
* The window's environment for OpenCode (`OPENCODE_CONFIG_CONTENT`, with "ask" for edits and shell commands and the llmkit provider, and the LLMKit key) always reaches the remote agent, over ssh's standard input only, never on a command line.
* An unknown host key is an error with instructions. Chatbook never writes known_hosts.
* One ssh connection per operation, each operation's commands batched into one remote script.

### Settings and host identity

`acpSSHSettings[value]` (SSH.wl) validates and normalizes the setting. `ShowNotebookAssistance` calls it (`validateACPWindowSettings`) and passes the canonical form on; an invalid value gives `ShowNotebookAssistance::InvalidACPSSHSettings` with the reason. With `"SSHSettings"` in the same call, `"ProjectDirectory"` must be a remote folder path (absolute or `~/`: a `C:\...` or relative folder is refused) and `"ACPAgentCommandLine"` a command line that can be sent to the remote computer (`acpRemoteCommandLineQ`: no control characters, the program not starting with `-`, and not with `~` unless `~/`).

| Key | Values | Rules |
|---|---|---|
| `"MachineName"` | host name, IP address, or a `Host` of the user's ssh config (required) | letters, digits and `. _ : % [ ] -`, not starting with `-`, at most 255 characters. `"user@host"` is split at the last `@` (an error if `"Username"` is given too). A string setting `"host"` or `"user@host"` is short for `<\| "MachineName" -> "user@host" \|>` |
| `"Username"` | `Automatic` (default: ssh's default or the config's `User`), `None`, a string | letters, digits and `. _ @ + -`, not starting with `-`, at most 256 characters |
| `"Arguments"` | `{}` (default), `None`, `Automatic`, a list of strings or `File`s | ssh options, scanned like ssh's getopt (an option that takes a value takes the rest of the word or the next one). Refused: control characters; words that are not options (a host name, `--`); options that keep Chatbook's command from running or from reading its input (`-N`, `-n`, `-f`, `-s`, `-W`, `-M`, `-O`, `-G`, `-Q`, `-V`, and `-o` keys `StdinNull`, `SessionType`, `ForkAfterAuthentication`); unknown option letters; an `-o` that sets one of Chatbook's fixed options to another value (e.g. `-o StrictHostKeyChecking=no`; see [Security](#security)); `-S` with any value but `none` (unlike `-o`, `-S` replaces an earlier `ControlPath`, so it would override Chatbook's `ControlPath=none`: it is refused like `-o ControlPath=...`, also inside grouped flags such as `-vS path`; only the whole value `none`, in any case, is accepted, as ssh compares it). `-q`, `-E` and `-y` are accepted, but they take ssh's own messages out of its standard error, so ssh's failures are then classified less precisely. Relative key paths are relative to the local home folder (ssh's working directory) |
| `"Executable"` | `Automatic` (default), `None`, a path or command name (string or `File`) | the local ssh program. `Automatic` searches `PATH`, `/usr/bin`, `/usr/local/bin` and `/opt/homebrew/bin`, and on Windows Windows' OpenSSH Client, `%ProgramFiles%\OpenSSH` and Git for Windows' ssh (`acpFindSSH`; no RunProcess) |

Other keys are an error. `"@"` and `"*"` are metacharacters in Wolfram Language string patterns (`StringMatchQ["a b", (LetterCharacter | "@")..]` is `True`), so the validators use `RegularExpression`.

The canonical form is `<| "MachineName" -> _String, "Username" -> Automatic | _String, "Arguments" -> {___String}, "Executable" -> Automatic | _String |>`, keys in this order; `acpSSHSettings` is idempotent on it. It holds no secrets (at most the path of a key file) and is what the window record and the TaggingRules store, so a window rebuilt after a kernel restart is remote again. The accessors validate it again on every use (it takes microseconds). Invalid stored settings are a `Failure["InvalidSSHSettings", ...]`, which counts as remote: a window never falls back to local. Its connect fails with `InvalidSSHSettings` (no process is started), and its git summary is `"Unavailable"`.

**Accessors** (SSH.wl; pure, safe in reader handlers): `acpSettingsSSH[settings]`, `acpWindowSSH[window | nbo]` (`None` for a local window), `acpRemoteQ`, `acpWindowHostKey`/`acpWindowHostLabel`/`acpWindowShortHost` (`None` for a local window, `"?"` for invalid settings), `acpWindowRemoteHome`, `acpPathContext` (what pure path renderers need: `"Remote"`, `"Host"`, `"HostLabel"`, `"Home"`), `acpProjectDirectoryQ[dir, ssh]` (local: `DirectoryQ`; remote: the path's form only) and `acpNormalizeProjectDirectory`.

**Host identity.** `acpSSHHostKey[ssh]` is `[user@]machine[:port]`: the machine in lower case, the user from `"Username"` or else the first `-l` or `-o User=` of `"Arguments"`, the port from the first `-p` or `-o Port=` (omitted for 22). Two users of one host don't share a last folder, and `-p 22` is the same host as no port. Per-host preferences use it (`acpSSHPreferenceKey`, `acpLastProjectDirectoryKey`, `acpRemoteHomeKey`; writers skip invalid settings). `acpSSHHostLabel` is `user@machine` as given (for messages), `acpSSHShortHost` a DNS name up to its first dot, an IP address whole, or a config alias (for the folder row, the title and the status line), and `acpSSHTerminalCommand` the `<program> [-l user] <Arguments> machine` to type in a terminal (for the host key and sign-in instructions). The program is `"Executable"` if it is set, else `ssh`. Every word is quoted for this computer's system. On Windows a word goes in double quotes by the rules of the C runtime that ssh.exe parses its command line with: `"` as `\"`, and backslashes doubled before a quote and at the end. cmd.exe passes that on as typed, unless a word that contains `"` also contains `&`, `|`, `<`, `>` or `^` (see [Known limitations](#known-limitations)). Elsewhere a word goes in POSIX single quotes, with `'` as `'\''`. `acpSSHTerminalCommand[ssh, os]` gives the command for another system.

**Changing the setting of an open window** (`acpReuseWindow`; the pure `acpReusePlan` decides). A host switch is a different host key (local is the host `None`). Settings are compared in normal form (`settingNormal`), so `"u@h"` and `<| "MachineName" -> "h", "Username" -> "u" |>` are the same. For an idle window:

| Change | Folder | Command line | Session | Connects |
|---|---|---|---|---|
| local → remote, no folder in the call | the host's last folder, else none (the folder picker opens) | reset to `Automatic` (with a notice if it was set) | new chat | once, over ssh |
| local → remote, `"ProjectDirectory" -> "~/proj"` | `~/proj` (made absolute by the launch) | reset | new chat | once |
| remote → local (`"SSHSettings" -> None`) | the local last folder, else the source notebook's folder, else none | reset | new chat | once, locally |
| host A → host B, A was never reached | kept (a typo in the user name or port must not lose the folder) | reset unless the call gives one | new chat | once |
| host A → host B, A was reached | B's last folder, else none | reset unless the call gives one | new chat | once |
| same host, other `"Arguments"` or `"Executable"` | kept | kept | resumed | reconnect |
| same host, another `"ProjectDirectory"` | that folder | kept | new chat | once |

* "Reached" is the window record's `"RemoteVerified"` (kernel state: after a kernel restart it is `False` until the first connect).
* A host switch while a turn runs or a session loads is refused with a notice (`NoticeHostWhileRunning`, `NoticeHostWhileRestoring`): the call's `"SSHSettings"`, `"ProjectDirectory"` and `"ACPAgentCommandLine"` are dropped. Other SSH changes reconnect after the turn (`"ReconnectRequested"`, as for a new command line).
* `acpResetProjectDirectory` (Connection.wl) does the switch: a new chat in the new folder (or `"NoDirectory"` without one), without the resumable session, with the new host's persisted home folder, `"RemoteVerified" -> False`, an empty Sessions store, and the old host's folder picker closed. It does not connect: `acpApplyWindowSettings` connects once.
* An explicit folder that can't be used (a local folder that doesn't exist, a remote one that is not absolute or `~/`) is ignored with a notice (`NoticeDirectoryMissing`, `NoticeInvalidRemoteDirectory`).
* Any change of `"SSHSettings"` clears the host's failure latch (see [Remote operations](#remote-operations)): it is usually the fix of the failure.

### Security

* **No prompts.** `BatchMode=yes`, and every ssh process gets `SSH_ASKPASS_REQUIRE=never` (`acpSSHEnvironment`), so that no hop (e.g. a jump host, which command-line options don't reach) can open an askpass dialog. Keys must be loaded in an ssh agent or have no passphrase.
* **Host keys are always checked and never written.** ssh uses the first value of an option, and Chatbook's fixed options come first (`$acpSSHFixedOptions`), so neither the user's ssh config nor `"Arguments"` can change them: `StrictHostKeyChecking=yes`, `CheckHostIP=no` (old Windows ssh.exe would otherwise add IP addresses to known_hosts), `UpdateHostKeys=no` and `NoHostAuthenticationForLocalhost=no` (localhost's key is checked too). `VerifyHostKeyDNS` is left to the user's config: with `yes`, ssh may accept a host key from a DNSSEC-signed SSHFP record instead of known_hosts, which is a host key check too. An `"Arguments"` `-o` that sets them to another value is refused rather than silently ignored. An unknown host fails with `SSHHostKeyUnknown` and the `ssh ...` command to run once in a terminal. A host that the user's config sends to `UserKnownHostsFile /dev/null` (a common recipe for cloud machines) needs its key kept in a known_hosts file first.
* **No forwarding.** The fixed options also turn off agent, X11 and Kerberos credential forwarding and all port forwardings (`ForwardAgent=no`, `ForwardX11=no`, `GSSAPIDelegateCredentials=no`, `ClearAllForwardings=yes`), against the user's config too. The flags `-A`, `-X` and `-K` in `"Arguments"` still turn them on: that is the user's explicit choice, and LLM-driven commands on the remote computer can then use the user's ssh agent or Kerberos ticket.
* **Only Chatbook's command runs.** `RemoteCommand=none`, `PermitLocalCommand=no`, `ControlMaster=no` and `ControlPath=none` are fixed too (`-S`, which replaces `ControlPath` instead of being first-wins, is refused unless its value is `none`). Then come `-l user`, the user's `"Arguments"`, defaults that the user may override (`ConnectTimeout=20`, `ServerAliveInterval=15`, `ServerAliveCountMax=3`), `-T` (it beats a user's `-t`), `--` (a host name can't become an option) and the host (`acpSSHCommand`). The name validation also refuses everything that an old ssh would expand into a `ProxyCommand`.
* **Jump hosts** (`-J`, `ProxyJump`) take `BatchMode` and their host key policy from `~/.ssh/config` only: command-line options apply to the destination. Use `BatchMode yes` for them there.
* **Secrets only on standard input.** The LLMKit key and the OpenCode config are exported by the launch script, which ACPLink writes to ssh's standard input once the remote shell asks for it. No secret is on a command line (local or remote), in a Failure, in a window record or in the debug log; the launch script is built only in `openConnection0`. The bootstrap first turns off shell tracing (`set +xv`): an inherited `SHELLOPTS=xtrace` would print the launch line with the key to standard error, which feeds error details and Copy. Lines naming `LLMKIT_API_KEY` or `OPENCODE_CONFIG_CONTENT` are dropped from error output anyway.
* **One-shot scripts keep only absolute `PATH` entries** (the prelude): an empty or relative entry (`PATH=:/usr/bin`, `.`) would run a cloned repository's own `uname` or `tr` during every automatic git check. The agent keeps the account's `PATH`, as a local agent does.
* **Remote values are validated before they are kept.** A home folder, folder or agent path from the remote computer (launch markers, listings, git) is used, stored or persisted only if `acpRemoteAbsolutePathQ` (absolute, no control characters, at most 4,096 characters). A rejected value is logged as `"RemoteValueRejected"` with its key only.
* **Remote text never becomes boxes or code.** Paths, names and ssh's or the agent's output reach boxes only through `acpRemoteDisplayName` (line breaks and tabs as visible symbols, other control characters as U+FFFD, and as a visible `⟦U+XXXX⟧`, e.g. `⟦U+202E⟧` or `⟦U+E0041⟧`, the C1 controls, the line and paragraph separators U+2028 and U+2029, and every character of Unicode's Default_Ignorable_Code_Point set: the bidi controls (U+061C, U+200E-U+200F, U+202A-U+202E, U+2066-U+2069), zero width characters and joiners, the soft hyphen, the Hangul and other fillers, the deprecated format characters U+206A-U+206F, the variation selectors (an emoji's U+FE0F too, since a run of them can carry hidden text), the tag characters U+E0000-U+E007F and the reserved code points of those blocks (`$visibleCodePoints`, one regular expression character class); then `acpNeutralizeLinearSyntax`) or `acpNeutralizeLinearSyntax`. Nothing remote is `ToExpression`'d: numbers are read with `FromDigits` after a digits check. Buttons name remote folders by a hash, never by name.
* **Remote output is bounded:** caps on bytes, frames and records (also enforced on the Wolfram Language side, since a script's own caps only hold for an honest remote), incremental searches, and ssh's standard error is classified on its last 64 KB with linear-time patterns.
* **Nothing local is done with a remote path:** no `DirectoryQ`, `FileExistsQ`, `ExpandFileName`, `FileNameJoin`, `FileNameTake`, `$HomeDirectory` or `SystemOpen` (on Windows `ExpandFileName["/home/u"]` is `C:\home\u`). Remote paths are POSIX strings (`acpRemoteNormalizeDirectory`, `acpRemoteParent`, `acpRemoteChild`, `acpRemoteLexicalPath`, `acpRemoteAbbreviate`, `acpRemoteExpandHome`).
* Every ssh process runs in the local home folder with the kernel's environment (as a local agent, without the variables ACPLink refuses: `acpInheritedEnvironment`) plus `SSH_ASKPASS_REQUIRE`. Nothing of it reaches the remote computer except ssh's own `SendEnv` variables.

### Launching the agent

A remote agent's command (`remoteAgentSpec`, Agents.wl) is the local ssh running a bootstrap, in the local home folder:

```
ssh <fixed options> [-l user] <Arguments> <default options> -T -- host \
    "exec /bin/sh -c 'set +xv; echo chatbook-acp-ready >&2; IFS= read -r s || exit 125; set -f; IFS=; eval $s'"
```

1. **The trigger.** `acpConnect` makes a launch nonce (16 hex characters) and opens the connection with ACPLink's `"StandardInputPreamble"` (the launch script) and `"StandardInputPreambleTrigger" -> "chatbook-acp-ready"`. ACPLink writes nothing to ssh's standard input until that line appears on its standard error, i.e. until ssh has signed in and the remote shell runs. The preamble and every message sent meanwhile (`initialize`, sent right after the open as for a local agent, and ACPLink's answers to login-shell noise on standard output) are queued and then written in one write, preamble first. So no write can block on a pipe that ssh doesn't read yet, on any OS (Windows pipes may hold only 4 KB). See ACPLink's `ACPLink/JSONRPCProcess/README.md`.
2. **The bootstrap** (`$acpSSHLaunchCommand`; neither `"` nor `\`, which ProcessLink's Windows command line would rewrite) reads one line, one byte at a time, so the JSON-RPC stream after it is untouched, and evaluates it.
3. **The launch script** (`acpSSHLaunchScript`) is that line; every value is a single-quoted word, and a value with a line break or NUL gives `Failure["InvalidLaunchValue"]` (which holds no values). It exports the agent's variables (the registry's `"Variables"`, evaluated only here), reports `$HOME`, enters the folder (`~` and `~/` are relative to the remote home), reports `$PWD`, finds the agent's program (a path, or a name searched in the remote `PATH`, then `~/.opencode/bin`, `~/.local/bin`, `~/.bun/bin`, `~/.npm-global/bin`, `/opt/homebrew/bin` and `/usr/local/bin`; its folder is added to `PATH` when missing, which npm and nvm installs need), reports it, and runs it with its arguments.
4. **The agent is not `exec`'d:** the launch shell waits for it and exits with its exit code. An agent killed by a signal (e.g. the OOM killer on a small machine) then gives 128+n and the shell's `Killed` line, instead of ssh's silent exit 255, which would look like a lost connection. Standard input passes through to the agent unchanged.
5. **The `initialize` continuation** (`remoteLaunched`, a reader handler) reads the markers from `conn["StandardError"]` (`acpSSHLaunchMarkers`), sets `"ConnectDirectory"`, `"RemoteHome"`, `"RemoteAgentPath"`, `"RemoteVerified" -> True` and `"LaunchMarkers"`, replaces a `~` folder with the absolute one, clears the host's failure latch, and schedules the writes of the host's last folder and home folder. `session/new` and `session/resume` get the absolute folder. A remote folder is persisted only now, so a mistyped folder never becomes the host's default. Without an absolute folder (a `~` folder without a `cwd` marker) the connection fails with `SessionFailed`.

A launch that fails after its `home` marker (a missing folder, or an agent that is not found or exits) still corrects the home. `remoteExitError` (a reader handler) gives `<| "Error" -> error info, "RemoteHome" -> home |>`. The home is the launch's `home` marker, checked by `acpSSHLaunchMarkers`, when it differs from the window's `"RemoteHome"`; otherwise it is `None`. `remoteExitError` schedules the write of the host's `{"SSH", hostKey, "Home"}`, and `onAgentExited` sets the window's `"RemoteHome"` in its record update. So the first launch, even a failed one, corrects a home persisted for another machine with the same host name.

**Markers** are standard error lines `chatbook-acp:<nonce>:<key>:<value>`. Lines with another nonce (startup files, the agent) are ignored, and only the first 64 KB are read:

| Marker | When | Exit code |
|---|---|---|
| `home:<$HOME>` | first | |
| `error:no-folder:<path>`, `error:not-a-folder:<path>` | the folder is missing, or not a folder | 120 |
| `error:folder-access:<path>` | `cd` failed (the shell's message follows) | 120 |
| `cwd:<$PWD>` | after `cd` (the logical path) | |
| `error:no-agent:<program>` | the program was not found or is not executable | 127 |
| `agent:<path>` | right before the agent starts | |
| (none) | standard input ended before the script line | 125 |
| (none) | the agent exited (128+n if signal n killed it) | the agent's |
| (ssh's own lines, ending in CR LF) | ssh failed | 255 |

A `home` or `cwd` value is accepted only if another marker of the launch follows it (a path with a line break would otherwise pass for a shorter one). ACPLink's exit event has only the last 4 KB of standard error, so the window keeps the launch's markers (`"LaunchMarkers"`) and puts them back in front of it when they are no longer in it.

**Exit classification** (`acpSSHExitKind`; `onAgentExited` uses it through `remoteExitError` and `acpSSHExitError`). The text is the last 64 KB of standard error without the markers, `debug1:` lines, the trigger line and the warning of an ssh without GSSAPI; patterns are case-insensitive literal strings plus one linear regular expression. The first match wins:

| Rule | Condition | Kind |
|---|---|---|
| 1-3 | an error marker | `RemoteFolderMissing`, `RemoteFolderAccess`, `RemoteAgentNotFound` |
| 4 | after the setup: no exit code, or 255 with ssh's text for an established connection that ended (`not responding`, `closed by remote host`, `Broken pipe`, `Connection reset`, `client_loop:`, `packet_write_wait`, and ssh's own prefix `Read from remote host`, whatever system error text follows it, e.g. Windows' `Connection aborted`; bare error texts are not used, since after the setup the agent's own output is in the text); during the setup: the same after the `home` marker | `SSHConnectionLost` |
| 5-11 | ssh's own messages (also Windows' and macOS' resolver messages), only before the `home` marker: afterwards ssh had connected, and the text is the agent's. Before them all, ssh's own line for a TCP connection that couldn't be made (`ssh: connect to host <h> port <p>: <error>`) gives `SSHUnreachable` whatever the error text, unless it is `Connection refused` (that stays rule 9, `SSHConnectionRefused`). Without a connection ssh saw no host key and tried no sign-in, so a firewall's `Permission denied` (Linux EACCES, or Win32-OpenSSH's unmapped WSAEACCES) or Win32-OpenSSH's `Unknown error` is not `SSHAuthFailed`. A name that was not found has another prefix and stays `SSHHostNotFound` (rule 8). `SSHUnreachable` (rule 10) also takes Win32-OpenSSH's `Host is unreachable`, `Network unreachable` and `Network is down` | `SSHHostKeyChanged`, `SSHHostKeyUnknown`, `SSHAuthFailed`, `SSHHostNotFound`, `SSHConnectionRefused`, `SSHUnreachable`, `SSHBadArguments` |
| 12-13 | exit 125 or 255 without the `home` marker | `SSHFailed` |
| 14 | another exit code without the `home` marker: the login shell never ran the bootstrap (`nologin`, a restricted shell, `ForceCommand`, a `command=` key) | `RemoteScriptFailed` |
| 15 | otherwise | `RemoteAgentExited`, with the signal hint for exit codes 129 to 192 (or a silent 255) after the `agent` marker |

**Errors.** `acpErrorInfo` gives `"Code"`, `"Message"` (our sentence), `"Hint"` (our advice: the kind's `"Error" <> kind <> "Detail"` string and extra hints), `"Output"` (what ssh, the remote shell or the agent said: the last 12 lines, neutralized), `"Detail"` (hint and output, for the full view and logs), `"Actions"` and `"Data"` (with `"ExitCode"` and `"Host"`; the `"ConnectionFailed"` log entry has only the code and the exit code, never standard error). The messages name the host (`acpSSHHostLabel`), and the instructions give the terminal command (`acpSSHTerminalCommand`).

| Kind | When | Advice | Actions |
|---|---|---|---|
| `SSHNotFound` | no local ssh (`acpFindSSH`) | install the OpenSSH client (on Windows: type Optional features in the Start menu search, then add OpenSSH Client; this wording works on every Windows version), or give `"Executable"`. An `"Executable"` that is not found is named: `acpFindSSH`'s Failure has `"Path"` (the program), and the error says "`path` was not found or is not executable on this computer." (`ErrorSSHNotFoundPath`, display-safe) with the advice to check `"Executable"` (`ErrorSSHNotFoundPathDetail`) | Reconnect |
| `SSHStartFailed` | ssh could not be started | | Reconnect |
| `SSHHostKeyUnknown`, `SSHHostKeyChanged` | rules 6, 5 | connect once in a terminal and check the fingerprint; a changed key may mean interception | Reconnect |
| `SSHAuthFailed` | rule 7 | use a key in an ssh agent or without a passphrase, give it with `{"-i", path}`; also when the key file is readable by others or missing | Reconnect |
| `SSHHostNotFound`, `SSHConnectionRefused`, `SSHUnreachable` | rules 8 to 10 | check the name, the network, the server and the port; `SSHUnreachable` after a recent sign-in failure says that the server may refuse connections for a while | Reconnect |
| `SSHBadArguments` | rule 11 (ssh's usage text is dropped) | | Reconnect |
| `SSHConnectTimeout` | the setup timed out before the `home` marker | | Reconnect |
| `SSHConnectionLost`, `SSHFailed` | rules 4, 12 and 13 | | Reconnect |
| `RemoteFolderMissing`, `RemoteFolderAccess` | the folder markers | | Choose folder…, Reconnect |
| `RemoteAgentNotFound` | the `no-agent` marker | install it there, or give its path on the host with `"ACPAgentCommandLine"`, e.g. `{"/home/u/.opencode/bin/opencode", "acp"}` | Reconnect |
| `RemoteAgentExited` | rule 15 | the exit code; a signal may mean the host ran out of memory | Reconnect |
| `RemoteTimeout` | the setup timed out after the `home` marker (the agent did not answer) | | Reconnect |
| `RemoteScriptFailed` | rule 14; one-shot: no READY, or no BEGIN with an exit code other than 255 | the login shell did not run the command; for no READY: startup files print too much | Reconnect (launch) |
| `RemoteOperationTimedOut` | a one-shot run timed out | | |
| `InvalidSSHSettings` | invalid stored settings | the validation's reason | |

Sign-in errors of a remote agent (`AuthRequired`, `NoModels`) have a short message that names the host (`ErrorAuthRequiredRemote`, `ErrorNoModelsRemote`). The instruction is their advice, the error's `"Hint"` (`ErrorAuthRequiredRemoteDetail`, `ErrorNoModelsRemoteDetail`, from Connection.wl's `errorHint`): connect with the terminal command (`acpSSHTerminalCommand`), run `opencode auth login` there, then reconnect. The toolbar shows it in "Details" with "Copy", and the agent's own words stay as the line under the message. "Sign in…" of a remote window sets a notice with that instruction and the command (see [Everything else](#everything-else)); a local window keeps the local text, and a local agent's sign-in errors have no such advice.

The setup's response timeout (`$acpConnectTimeout`, 60 s) gives `SSHConnectTimeout` (ssh was still connecting or signing in, or a startup file blocked) or `RemoteTimeout`, from the standard error so far (`acpSSHTimeoutError`). For `initialize` the timeout counts from the launch's last progress. While `initialize` is unanswered, every housekeeping run counts the launch's progress lines on ssh's standard error: the trigger line and the markers with this launch's nonce (the window's `"LaunchProgress"`). When the count grows, the request's clock restarts (`observeLaunchProgress`, logged as `"LaunchProgress"`). So a slow sign-in, or a kernel that was blocked meanwhile, does not fail a launch that has just reached the agent. A launch reports only a handful of such lines, so the timeout restarts a few times at most. Reading the standard error there also writes a launch script whose trigger line arrived while ACPLink's reader could not run. Like every timeout, it is not decided in a run right after the kernel was blocked (see [Threading rules](#threading-rules), R5).

**The `initialize` grace period** (every window, local too). When writing `initialize` fails (the agent or ssh exited already: ssh rejects bad arguments within a millisecond), the window records `"InitSendFailedAt"` and stays `"Connecting"` for `$acpInitSendGrace` (2 s, through `acpSchedule`). The agent's exit event, which carries the exit code and standard error, arrives meanwhile and is classified as usual. Only if the window still holds the connection after that does it fail with `InitFailed`. Test hook: `$acpBeforeInitializeHook` (a function evaluated right before the write; the tests use `Pause[0.5] &`).

**Close, reconnect, kernel restart** work as for local agents: ACPLink closes ssh's standard input, waits 0.5 s and kills the local process tree, and the end of standard input ends the remote agent. A dropped network ends ssh after 45 to 60 s (`ServerAlive*`), and the window becomes `"Disconnected"` with `SSHConnectionLost` and Reconnect. Every connect is one login; `$acpMaxConnectAttempts` bounds retries. `initialize` keeps the client's `fs` and `terminal` capabilities off (they would make the kernel read local files for a remote agent), and sessions get no MCP servers: the remote OpenCode's own configuration decides about them.

In both modes, an agent never outlives its connection. If its JSON-RPC process cannot be closed, ACPLink's `CloseACPConnection` kills the agent's process group as a last resort before it forgets the connection, which also frees ssh's standard input. It signals the group only while the agent still runs, because once the agent was reaped its PID may belong to another process. For an agent that already exited it only frees ProcessLink's pipes (`KillProcess[process, 0]`; see ACPLink's `ACPLink/ACP/README.md`, "Closing, and agent death"). `acpConnect` opens at most one connection per attempt: a second run of the same attempt (e.g. one rescheduled by `checkStuckConnect`) does nothing while the window holds a connection (`"ConnectSkipped"`). An open that fails closes any connection that ACPLink registered during it with the window's command line (`"StrayConnection"`). The orphan sweeper closes the connections Chatbook opened that no window refers to. It does not look at ACPLink's JSON-RPC processes: Chatbook cannot tell them from other ACPLink users' processes, and ACPLink makes sure a process does not outlive its connection.

### Remote operations

`acpRemoteRun[ssh, body, continuation, opts]` (Remote.wl) runs the sh script `body` on the remote computer over one ssh connection (`ssh <options> -T -- host "exec /bin/sh -s"`) and evaluates `continuation[result]` (isolated) in the pump, always exactly once. Its users are git summary checks and change sets (`"Label" -> "Git"`) and the folder picker's listings (`"FolderList"`). Options: `"Timeout"` (`$acpRemoteTimeout`, 30 s), `"MaxOutput"`, `"MaxFrames"`, `"Owner"` and `"Request"` (as `acpGitRun`), `"Automatic"` (started by Chatbook, not by a click) and `"Label"`.

**The READY handshake.** The runner first writes one short line, `set +xv; printf '\n#ACPR1 <nonce> READY\n'` (about 70 bytes). The remote `sh -s` runs it as soon as ssh has signed in and forwards standard input. When `#ACPR1 <nonce> READY` appears on standard output, the runner writes the script and closes standard input. Nothing large is ever written before ssh reads; the cost is one round trip. If 64 KB of standard output (`$acpRemoteMaxBeforeReady`) arrive without the marker (startup files that print a lot), the run ends `"NoReady"`.

**Scripts.** The templates in `Assets/RemoteScripts` are read once per session (and kept in the MX file), CR is removed, and they are minified (`acpRemoteMinify`: comments, empty lines and indentation dropped). Values are inserted afterwards with one `StringReplace` (which never rescans inserted text, so a folder named `x@FULL@y` stays as it is) and are never minified; every value is a single-quoted word (`acpShellQuote`, `acpRemotePathWord`). A filled script must be under 16 KB (`$acpRemoteMaxScript`). The prelude (`prelude.sh`) sets `LC_ALL=C`, `umask 077` and `set -f`, filters `PATH`, turns signals into exits, starts the watchdog, makes a private folder for its temporary files (`chatbook.XXXXXX` in `$TMPDIR` or `/tmp`, removed at the end; without one the script stops with `tmpdir`), and defines the frame helpers (`cb_run`, `cb_emit`, `cb_value`, `cb_stop`, `cb_end`). Commands get `/dev/null` as standard input, and their output is cut at its cap (they stop through SIGPIPE).

**ACPR1**, the scripts' standard output, parsed by `acpRemoteParseFrames`:

```
<anything: login-shell noise, the READY line; ignored>
\n#ACPR1 <nonce> BEGIN\n
F <name> <exit|-> <outlen> <outtrunc> <errlen> <errtrunc>\n<out bytes><err bytes>\n     one frame per command
S <code>\n                                                                         the script stopped early (its last record: END follows)
#ACPR1 <nonce> END\n                                                               the script ran to the end
```

BEGIN is searched in the first MB (a decoy with another nonce is skipped), at most `"MaxFrames"` frames are read (`$acpRemoteMaxFrames`, 16; a full git change set allows 516), and an `S` record must be followed by END (`cb_stop` prints both; anything else after it, such as a second `S` or a frame, ends the parse with `"Malformed" -> "Record"`). So `S` records are bounded like frames: the parser reads at most `"MaxFrames"` + 2 records, whatever the remote prints. The `S` record does not count toward `"MaxFrames"`, so a run with exactly `"MaxFrames"` frames can still stop. A record line must match its pattern before its numbers are read, and a cut stream keeps its complete frames.

**Results:** `<| "Status", "Frames", "Stop", "ExitCode", "Error", "Host", "Duration" |>`. The statuses: `"OK"` (END was read), `"SSHFailed"` (no BEGIN: ssh, the sign-in or the login shell failed), `"StartFailed"`, `"TimedOut"` (the local timeout), `"RemoteTimedOut"` (exit 143: the watchdog), `"TooLarge"`, `"Cancelled"`, `"Incomplete"` (BEGIN without END), `"NoReady"` and `"Latched"`. `"Error"` (`acpRemoteErrorInfo`) has the shape of connection errors, with `"Actions" -> {}` (the picker adds Try again, the review window Refresh):

| Situation | Kind |
|---|---|
| no BEGIN, exit 255 | ssh's own failure, as rules 5 to 13 (`SSHAuthFailed`, ...) |
| no BEGIN, another exit code (no `/bin/sh`, `ForceCommand`, a restricted shell) | `RemoteScriptFailed` |
| `"NoReady"` | `RemoteScriptFailed` with the advice about noisy startup files |
| BEGIN, no END, exit 255 or none | `SSHConnectionLost` |
| BEGIN, no END, another exit code (output cut or malformed); `"TooLarge"` | `RemoteScriptFailed` without advice |
| BEGIN, no END, exit 143; the local timeout after BEGIN; a slot wait that timed out | `RemoteOperationTimedOut` |
| the local timeout before BEGIN | `SSHConnectTimeout` |
| ssh not found, not started | `SSHNotFound`, `SSHStartFailed` |
| `"Latched"` | the cached error of the latch |

**Bounds.** The timeout counts from the start of ssh. A remote watchdog terminates the script's process group at `Ceiling[timeout] + 10` s (`$acpRemoteDeadlineSlack`): a backstop for work whose local ssh was killed. `"MaxOutput"` (`$acpRemoteMaxOutput`, 64 MB) counts standard output and error together, and only the last MB of standard error is kept (`$acpRemoteMaxErrorKept`). At most 3 runs at once per host key (`$acpRemoteMaxRuns`); another run tries again every 250 ms through the pump (`$acpRemoteSlotRetry`), without a queue.

**Cancelling.** A run whose owner is gone or whose request was superseded is killed at its next poll once it has passed READY. Before READY (ssh may still be signing in) it is drained instead: its continuation gets `"Cancelled"` at once, standard input is closed so that the remote shell ends cleanly, its output is dropped, and it is killed only after 30 s (`$acpRemoteDrainTimeout`). It keeps its host slot until it is gone, and its end is logged as `"ProcessDrained"`. sshd would count a connection dropped before authentication as a penalty (below).

**The runner** is Git.wl's `acpProcessRun` (`acpGitRun` is a wrapper of it): `StartProcess` from the pump, non-blocking size-based reads every 50 ms, a timeout and an output cap, `KillProcess` at the end. Remote runs use its options `"Environment"`, `"Input"` (the READY line), `"InputAfter"` (`<| "Marker", "Bytes", "Limit" |>`: the bytes are written once the marker appears; each poll searches only its new output plus a short tail), `"Decode" -> False` (ByteArrays), `"ErrorKeep"` (only the end of standard error), `"CancelBeforeReady" -> "Drain"` (with `"DrainTimeout"`) and `"Arguments"` (results report `{"ssh", host}`, never the script).

**The host failure latch.** sshd's `PerSourcePenalties` (OpenSSH 9.8 and later, on by default) refuse a client address for up to 10 minutes once 15 s of penalties have accrued: 5 s for each failed authentication, 1 s for each connection closed before authenticating. With one connection per operation, a wrong key would get there quickly. So after `SSHAuthFailed`, `SSHHostKeyUnknown`, `SSHHostKeyChanged` or `SSHBadArguments` (of a one-shot run or of the agent's launch), the host key is latched (`acpRemoteNoteHostError`, `$acpRemoteHostErrors`):

* Automatic runs (git summary checks, the folder picker's automatic first listing) make no connection while the host is latched: they get `"Latched"` and the cached error.
* User actions clear the latch first (`acpRemoteClearHostError`): Reconnect, changed `"SSHSettings"`, "Choose folder…", every click in the folder picker, and the review window's opening and Refresh. So does a run that reaches its script, and a launch that reaches the agent. Agent connects never consult the latch: they are started by the user, or bounded by `$acpMaxConnectAttempts`.
* An authentication or host key failure is also remembered for 10 minutes (`$acpRemoteHostAuthFailedAt`, `$acpRemoteLatchMemory`), and user actions don't clear that. An `SSHUnreachable` in that time gets the hint that the server may refuse connections for a while: after the user fixes the key, the reconnect is the one that is refused (ssh says `kex_exchange_identification: Connection closed by remote host`).
* Administrators can exempt client addresses with sshd's `PerSourcePenaltyExemptList`. OpenSSH before 9.8 (e.g. Ubuntu 24.04's 9.6) has no penalties; the latch still avoids pointless logins.

### Git and Review over SSH

* A git request of a remote window carries its canonical settings (`"Remote"`). `gitRequest` passes it to `gitRemoteRequest`, which does no local check: one run of `git.sh` (after the prelude) per request. The script mirrors the local steps with the same read-only options, filled in from Git.wl's own constants (`gitRemoteScript`): finding git as `acpFindGit` does (the macOS `/usr/bin/git` stub only with the developer tools), its version, the `.git` hint (logical, then physical path), the filter drivers neutralized one by one (or the stop `unsafe`), rev-parse, status, numstat, the patch, the base commit, and the untracked files in batched passes (a NUL-safe awk counts lines; one `od` per file without one).
* The steps then replay its frames instead of running git (`$gitRemoteFrames`, `gitRemoteStepResult`, `gitRemoteUntracked`, one step per pump tick), so a remote change set is made by the same code as a local one and is equal to it, apart from untracked names with a line break (unreadable) and names that are not UTF-8 (read). At most `$acpGitMaxFiles` untracked records are used.
* Timeouts: 30 s per summary check and 90 s per full change set (`$gitRemoteSummaryTimeout`, `$gitRemoteTimeout`), per request rather than per command.
* Summary checks are automatic runs (a latched host is skipped). Full change sets come from the review window, a user action.
* The window's summary has `"Remote"` (the host key): a summary for another host or folder starts a new check, and results for another host are dropped. The first remote check waits until the window is connected (`"Ready"`, `"Running"` or `"Restoring"`) and its folder is absolute (the launch resolves `~`), so it never logs in in parallel with the agent's launch. Remote windows check at most every 5 s when files change and every 60 s when idle (`$gitRemoteMinCheckInterval`, `$gitRemoteIdleCheckInterval`; each check is a new sign-in), and checks pause after `SSHFailed` or `RemoteFailed` until the next trigger.
* Change sets have `"Remote" -> <| "Host", "Short", "Home" |>` (`None` for local folders), file records `"Remote" -> True | False` and POSIX `"FullPath"`s. `acpGitChanges[dir, continuation, key, ssh]` lists a remote folder without the window.
* Errors: `SSHFailed` (ssh or the sign-in failed; also a latched host), `RemoteFailed` (no READY, no temporary folder) and `StartFailed`, with `"SSHCode"` (the kind of the table above), `"Error"` (the one-shot error) and `"Stop"`. Invalid settings give `"Unavailable"` with `InvalidSSHSettings`.
* The review window keeps the settings in its TaggingRules (`{"ACPReview", "SSH"}`, no secrets): Refresh without the ACP window's record (closed window, kernel restart) lists the remote folder again and never looks for it on this computer, and the window is found again by folder and host key. Its header shows `host:path` (both display-safe, abbreviated with the remote home and kept from its end; the tooltip is `user@host:/abs/path`), remote files have no Open link, and the messages name the host ("Could not connect to `host`.", "Git was not found on `host`.").
* Test hooks: `$gitRemoteSystemDirectories` (the folders searched for git after the remote `PATH`) and `$gitRemoteNULSafe` (`False`: the portable path, one `od` per untracked file).

### Project folders and the folder picker

**Remote folders.** A remote project folder is absolute or starts with `~/`, without control characters, at most 4,096 characters (`acpRemoteProjectDirectoryQ`). Only its form is checked; the launch script checks that it exists (`RemoteFolderMissing`, `RemoteFolderAccess`, with "Choose folder…"). Four folders stay `~` folders: a new window's folder (`acpDefaultProjectDirectory`), the folder `acpConnect` launches with, a folder given for another host (`acpReusePlan`) and a folder rebuilt from the TaggingRules (`acpRebuildWindowRecord`). The launch script resolves them with the remote `$HOME`, and `remoteLaunched` stores the absolute folder. Only on the window's own host do `acpReusePlan` and `acpSetProjectDirectory` expand `~`, using the window's `"RemoteHome"`. So `~/x`, the window's `/home/u/x` and the window's unresolved `~/x` are the same folder and don't cause a reconnect (`sameRemoteFolderQ`). Until a launch reports the real home, the window's `"RemoteHome"` is the home persisted for the host, so it can still be another machine's (e.g. after an ssh config alias moved). A launch, even a failed one, corrects it (see [Launching the agent](#launching-the-agent)). Some folders are kept as given (`"Raw"`: a name may end in a space), apart from a trailing `/`: folders that the agent or the picker give, and a folder read back from the TaggingRules after a kernel restart (`acpRebuildWindowRecord`; it was normalized when it was stored). Only folders that the user types are trimmed. `Automatic` is the host's last folder; a missing folder that is the host's last one is forgotten (`acpClearPersistedLastFolder`).

**The folder row** (see [The toolbar](#the-toolbar)) shows `host:path`, with `user@host:/path` in the tooltip. The host is in its short form (at most 16 characters), muted and never cut. The path is abbreviated with the remote home (`acpRemoteFolderLabel`, which keeps a path of more than 200 characters from its end in whole names) and cut by the front end at its start to the room the row leaves, so the folder's own name stays visible. A warning about the folder (missing, the home folder, the root) has its own column between the folder icon and the folder, so a narrow window never hides it. Paths are drawn without operator substitution, and a local window's folder is display-safe too (`acpRemoteDisplayName`). A click on the folder (or on "Choose folder…" without one) opens the folder picker (the action `"ChooseDirectory"`, BoxID `"ACPChooseDirectory"`; local windows keep the front end's directory dialog). The warnings are for the remote home folder, `/`, and a missing folder (from the window's error), never from a check on this computer. The local folder chooser and "Locate OpenCode…" refuse remote windows.

**The folder picker** (FolderPicker.wl) lists folders on the remote computer:

* **Window.** One deployed notebook per ACP window, found by its TaggingRules (`{"ACPFolderPicker", "Owner" | "HostKey" | "Input" | "Path"}`, plus `ExcludeFromChat`). It is placed over the ACP window, centered, 40 points below its top and kept on the display (`acpFolderPickerPlacement`, pure); with the default width the picker (440 points, 520 on macOS) is inside the ACP window. A click on the folder in the toolbar (or on "Choose folder…") opens it, or raises the open one. It also opens by itself, once, for a new remote window without a folder and after a host switch that leaves none (`acpFolderPickerAutoOpen`), but not while the host is latched, the window shows an error, or after a kernel restart.
* **Layout.** A docked cell has these rows: the title with Cancel and Choose; the host with "Show hidden"; Up, Home, the path field, Go and Refresh; and the status line, which has the header's whole width. The docked cell turns line breaking on (`LineBreakWithin -> Automatic`, `LineIndent -> 0`), since the "DockedCell" style turns it off. So a long ssh error, fallback notice or path wraps at the window's width and never pushes the buttons out of the window. The path field stays one line (`LineBreakWithin -> False`, `AutoSpacing -> False` for its hint). The status line of a listing names the listed folder, since the path field shows the start of a long path. The name is its display-safe last name: `~` for the home folder, `/` for the root, shortened to 60 characters, with the path in the tooltip (`FolderPickerListedTooltip`). A "Current folder" badge follows it when it is the window's folder. Below it come the fallback notice, or "Link to …" the physical path when it differs. A navigation error (a typed folder that doesn't exist, isn't a folder or can't be opened) keeps the previous listing, so the status line still names that folder (with its badge) above the red line. Then the list: folders first in natural order (50 at a time, "Show 50 more folders"), then the files (muted, 20 shown), the counts and cap notes. Counts are singular or plural ("1 folder, 0 files"): the templates `FolderPickerFolderCount`, `FolderPickerFileCount`, `FolderPickerShowMore` and `FolderPickerMoreFiles` have a `...One` variant for 1, joined by `FolderPickerSummary` ("`folders`, `files`"). The path field is an `InputField` bound to the TaggingRules in the front end (no kernel call per keystroke; Return is Go, Escape is Cancel). The status, the buttons and the list are derived views with signatures (R6).
* **Listings.** Each listing is one `acpRemoteRun` of `list.sh`'s `cb_ls` (format ACPLS1: NUL-terminated `tag:value` fields; shell builtins only, so GNU and BSD systems give the same output; folders in their own pass first). At most 1,000 folders and 200 other entries per class (hidden or not) are listed, of at most 20,000 and 5,000 looked at, in at most 1 MB (`$acpRemoteListMaxFolders`, `$acpRemoteListMaxFiles`, `$acpRemoteListScanFolders`, `$acpRemoteListScanFiles`, `$acpRemoteListOutputCap`), and the parser (`acpRemoteListingParse`) enforces the caps again. The first listing starts at the window's folder, else the host's last folder, else `~`, and falls back to the nearest folder above it that can be opened. Navigation (Enter, Up, Home, Go, Refresh) starts after 150 ms (`$acpFolderPickerDebounce`): a newer click within it replaces the request without an ssh call, so Up, Up, Up is one connection. A newer request supersedes a running listing (drained before READY). A listing's wait for a free host slot and its ssh run are each limited to 30 s (`$acpFolderPickerTimeout`), so a listing that has to wait for a slot can take up to about 2 × 30 s. Each listing uses the window's SSH settings as they are when it starts (`pickerRun`), so fixing `"Arguments"` or `"Executable"` for the same host with `ShowNotebookAssistance` on the open window reaches "Try again", Refresh and the next navigation without reopening the picker; the settings are written to the store's `"SSH"`. Settings of another host (or invalid ones) close the picker without running ssh. Hidden entries are always listed; "Show hidden" only filters the view.
* **Store:** the window record's `"FolderPicker"` (`acpFolderPickerOf`), changed through `acpWindowUpdate`: `"Status"` (`"Loading"`, `"Ready"`, `"Error"`), `"Request"` and `"LastRequest"` (token, path, base, kind, fallback, automatic), `"Path"` (the logical path, `$PWD` after `cd -L`), `"RealPath"`, `"Home"`, `"Entries"` (each with a hashed `"Key"`, which buttons use instead of the name), `"Counts"`, `"Capped"`, `"Warning"`, `"ListingStatus"`, `"Notice"` (the fallback notice), `"Error"`, `"ShowHidden"`, `"Shown"`, `"InputShown"`, `"Version"`, `"Automatic"`.
* **Errors.** Navigation errors keep the previous listing: `Missing`, `NotFolder`, `NoAccess`, `BadPath`, and `Tilde` (`~user` is not supported). The picker's own errors (`Timeout`, `Tmp`: no writable temporary folder, `Failed`: a listing that can't be read) come with "Try again". ssh's errors (the error info of the table above) are shown with `acpErrorView`'s full view, wrapped, with "Try again" and a copy button that carries no text. For `SSHHostKeyUnknown`, whose advice is to run the ssh command in a terminal, it is "Copy command" (`"FolderPickerCopyCommand"`: `acpSSHTerminalCommand` of the store's `"SSH"`). For other errors it is "Copy" (`"FolderPickerCopyError"`: the hint and ssh's text from `acpErrorParts`, as the toolbar's "Copy" gives them). `CopyToClipboard` runs only from the button, and only with a front end. Without a listing the status is `"Error"`; with one it stays `"Ready"`, and Choose works for the folder shown.
* **Choose** (`acpFolderPickerChoose`) takes the listed folder, if it can be listed (not "unreadable" or "unlisted"), is on the window's host, has no control characters, and no turn runs and no session loads. It becomes the window's folder (`acpChangeProjectDirectory` with `"Raw" -> True`): a new chat there. The same folder again reconnects a window in `"Error"`. The launch then persists it for the host.
* **Actions** (`ChatbookAction["ACP", name, owner, args...]`): `"FolderPickerEnter"` (with an entry's key), `"FolderPickerUp"`, `"FolderPickerHome"`, `"FolderPickerGo"`, `"FolderPickerRefresh"`, `"FolderPickerToggleHidden"`, `"FolderPickerShowMore"`, `"FolderPickerChoose"`, `"FolderPickerCancel"`, `"FolderPickerClosed"`, `"FolderPickerCopyError"`, `"FolderPickerCopyCommand"`. Go (`pickerGo`) reads the path field. The text the last listing put there (the listed path, shown display-safe) lists that folder again. That text followed by `/` and more (e.g. `/src` appended) means the raw listed path plus the appended part (trailing white space trimmed), so typing works below folders whose names are shown with substitutes (a tab as U+2409, bidi characters as `⟦U+202E⟧`). Any other text is taken literally as a path, relative to the listed folder.
* A listing's home folder is persisted for the host and becomes the window's `"RemoteHome"` when the host keys match, replacing a different home (a stale persisted one, e.g. from an ssh alias that now points to another machine) (`pickerKeepHome`). A home that the listing parser rejects is neither persisted nor given to the window. The pump keeps running while a picker lists, and housekeeping (`"ACPFolderPicker"`) ends a listing whose continuation was lost with the timeout error, only after 75 s (`pickerLostAfter[]`: twice `$acpFolderPickerTimeout`, because the slot wait and the ssh run are limited separately, plus 15 s). Closing the ACP window closes its picker; after a kernel restart the picker is rebuilt from its TaggingRules, or closed if the window's host changed (`acpFolderPickerRecover`). Without a front end (tests), `acpFolderPickerOpen` gives `"Opened"` and the listings run as usual.

### Everything else

* **Status line and title.** "Connecting to OpenCode on `host`…" and "OpenCode 1.2.3 on `host`" (the short host); the window title is "`project` on `host` — OpenCode".
* **The toolbar's error view** (every window). The compact view is a column of lines that wrap: the message, one line under it (the last line of the output, e.g. ssh's `Permission denied (publickey).`, else the first line of the hint, cut to 200 characters), and the buttons on their own row, with "Details" when there is more to see. "Details" shows the hint and the output (at most 12 output lines and 1,500 characters) with "Copy" (`acpErrorParts`). The window's `"ErrorDetailOpen"` holds `acpErrorKey` of the error whose details are open, so a new error starts closed; the actions are `"ToggleErrorDetail"` and `"CopyErrorDetail"` (`CopyToClipboard` only from the button). "Disconnected" with an error shows the error and Reconnect. The full view neutralizes the message and the detail. The status row is a full-width `Pane`, so a long message wraps instead of pushing the model and mode menus out of the window. Docked cells get `LineBreakWithin -> False` from the "DockedCell" style, and a string's own `LineBreakWithin` inside a `Row` does not reach the line that the `Row` makes. So both views turn line breaking on for everything they contain (`$errorTextStyle` in Rendering.wl: `LineBreakWithin -> Automatic`, `LineIndent -> 0`), and so does the status row's pane. Both views and the details draw their text without operator substitution (`PrivateFontOptions -> {"OperatorSubstitution" -> False}`), which would draw `-` as a long minus sign and `->` as an arrow in ssh commands and paths. Remote windows get no "Locate OpenCode…".
* **Notices with a command.** A window's `"Notice"` (the line above the input field) is a string, or `<| "Text", "Command" |>` for a notice with a terminal command, such as the one that "Sign in…" of a remote window sets. The command is shown as typed, in the code font and without operator substitution, with "Copy command": the action `"CopyNoticeCommand"` (`acpCopyNoticeCommand`) copies the command of the window's notice, so the button carries no text. Every notice's text is drawn without operator substitution too, so a "Can't send the message: …" notice shows an ssh command's `-` and `->` as typed.
* **Permissions.** For remote windows the "Always allow" scope text resolves paths with string operations on the host's paths (`~` with the remote home folder), never on this computer, and shows the external folder abbreviated with the remote home.
* **Sessions.** A remote window's projects are grouped by POSIX paths (trailing `/` dropped) and named by their last component. Remote folders are never shown as missing (a missing one shows up as `RemoteFolderMissing` when it is used), and the "open folder" button is hidden (`"SessionsOpenFolder"` gives `Missing["Remote"]`). The header says "OpenCode on `host`", the tooltips "`path` on `host`". Restore and "+" pass the listed `cwd` exactly (`"Raw"`); a `cwd` that is not a remote folder path gives `NoticeInvalidRemoteDirectory` and `Failure["InvalidFolder"]`. A host switch empties the store.
* **Resource links and other content blocks** (every turn). The agent's names, URIs and block types are neutralized. Only `http(s)` links, and the `file:` links of a local turn, are clickable. A remote turn's `file:` link shows its name, with "On `host`: `path`" in the tooltip; other schemes (e.g. `ms-msdt:`, `javascript:`) show their URI in a tooltip only. Markdown links in the agent's text keep their targets, and a markdown image shows as a link to its source (labeled with its alt text) instead of being fetched: the agent's answer is formatted with the untrusted-content formatter (`withUntrustedContent`, `Formatting.wl`), which imports no image, evaluates no special box (`DateObject` options, Wolfram|Alpha and resource lookups) and decodes no HTML entity. The private-use characters of the front end's linear syntax in the agent's answers, thoughts and tool text (and in the code of a code mode call) are replaced with U+FFFD before anything is formatted or shown, in the live, final and replayed views (`acpNeutralizeLinearSyntax` in `finishedItems`, `streamingItems`, `codeBlock`, the tool views, the tool titles and the status line, see [Tool cards](#tool-cards); Chatbook's formatter does the same for all text it formats, and for the characters it makes from the text, such as TeX's `\char`, `neutralizeLinearSyntax`). This, not the untrusted-content switch, is what keeps such text from becoming boxes chosen by the agent: the front end evaluates the box expression of linear syntax (with any code in it) when it turns code into boxes, and turns linear syntax in a string of a cell into boxes when it shows the cell.
* **Tool paths** of a remote turn (one whose `"Remote"` is set) are POSIX strings: `displayPath` takes their last name with string operations, whatever the system of this computer, so a backslash is part of a name. A local turn's paths are this computer's paths, so `displayPath` takes the last name with `FileNameTake` (on Windows, `C:\Users\me\proj` gives `proj`).

## The toolbar

The toolbar (`makeACPChatDockedCell`, UI.wl) has three rows: the main row, the folder row and the status row. The main row and the folder row are derived views (R6) whose one-line labels are cut by the front end with `acpFitText` (see [Tool cards](#tool-cards)), so they follow the window's width and magnification without the kernel.

**The main row:** New and Sessions (icon and label, like the Notebook Assistant's New and History buttons), then the model, mode and effort menus at the right (`acpConfigMenusView`). The row can't shrink, so the model's name takes one line, cut at its end to the room that the other parts leave (`modelLabelWidth`: the labels of New, Sessions and the other menus measured in the front end, plus `$mainRowReserve` and `$menuReserve` for each menu); a name that was cut is in the tooltip, with the menu's tooltip. The label's clipping panes have a number of points as their largest width (`$menuLabelMaxWidth`, acpFitText's `"MaxWidth"`) rather than `Full`: inside an `ActionMenu`, `Full` is a fixed width of about 376 points times the magnification whatever the room in the row (measured in a real front end: 417 pixels at 0.85, 501 at 1, at any window width), so a name cut to a wider room was clipped there without its ellipsis ("…adaptive thinking," at 580 to 800 points at magnification 0.85, the macOS default of 600 among them). In a narrow or magnified window New and Sessions show only their icons (their tooltips say what they do): when the row with their labels and two menus of a typical width (`$menuLabelsAllowance`, 80 points) would leave less than `$minModelLabelWidth` (40 points) for the model's name (`toolbarNarrowWidth`). The buttons and the menus are separate views, so the buttons use the typical width rather than the menus' labels; the model menu's width uses the same test (`acpFitWidthSwitch`), so it gets the labels' room when they are dropped. All of it is decided in the front end (`acpFitSwitch`). A long model name or a narrow or magnified window therefore doesn't push the effort menu out of the window (in a real front end on Linux: 480 and 600 points up to magnification 2, 360 points up to 1.5, the model's name cut with its ellipsis 5 to 16 pixels before the next part of the row; with the numeric largest width, a long name at 580 to 800 points (0.85) and 600 to 800 points (1), 800 × 1.5 and 600 × 2 ends with its ellipsis or is whole); only in a very narrow window (360 points at magnifications 1.75 and 2) are the icons and menus alone too wide: the model's name is a bare "…" and the effort menu is clipped.

**The folder row** (`acpDirectoryRowView`): the folder icon, a warning (its own column), the project folder, which is the control that changes it (`acpFolderControl`), and "Review" (see [Reviewing changes](#reviewing-changes)) at the right end.

* **The control.** A local window's folder is the `Appearance` of a `FileNameSetter` (rule R1: the front end runs the directory dialog; its setter runs `"SetProjectDirectory"`), a remote window's an `acpActionButton` (`"ChooseDirectory"`, BoxID `"ACPChooseDirectory"`) that opens the [folder picker](#project-folders-and-the-folder-picker). Both have `ImageSize -> Automatic`: a button in the row's full-width pane would take the pane's whole width and center its label. The look is the toolbar buttons' (`blueHueButtonAppearance`): a frame and background under the mouse, and the path in the buttons' blue (the color is given inside the label's own style; the color of `"WorkspaceChatToolbarTitle"` would win over an outer one). While a turn runs or a session loads, the control is disabled and the label is shown in the same frame without the hover look. Without a folder it reads "Choose folder…" in the buttons' style. With invalid stored SSH settings there is only the label (no folder can be chosen until the settings are fixed).
* **The tooltip** is outside the control, so it also shows while the control is disabled: "Project folder: `path`" ("Project folder on `user@host`: `path`"), or that there is none, and a muted line: "Click to choose another folder", or why the folder can't be changed now (`NoticeDirectoryWhileRunning`, `NoticeDirectoryWhileRestoring`; the reason is part of the row's signature).
* **The label** (`folderLabel`) takes one line: the path (home abbreviated, display-safe with `acpRemoteDisplayName` before anything is cut) as much as fits, cut by the front end at its start with an ellipsis (`acpFitText` with `"Side" -> Left`), so the folder's own name stays. A remote window's `host:` prefix is muted and never cut. The pieces of the cut are the path's characters and `acpRemoteDisplayName`'s markers (`folderLabelPieces`: a `⟦U+202E⟧` is cut whole or not at all); the kernel keeps only the last 200 of them (`$acpFolderLabelMaxLength`). The width (`folderLabelWidth`) is what the row leaves after the icon, a warning and the Review button (its label and counts measured in the front end, in their fonts: `acpReviewButtonTexts`, Review.wl) and the control's frame (`$folderRowReserve`, `$folderWarningReserve`, `$reviewButtonReserve`). The control is in a `Fit` column whose pane (at most the column's width, `ImageSize -> {{0, Full}, Automatic}`: a pane of `Full` width made the column wider than its room in a narrow, magnified window and pushed "Review" out of it) draws a label that is still too wide smaller (`ImageSizeAction -> "ShrinkToFit"`), the safety net if a width is off.
* **The reserves** are `{ screen, scaled }` like the titles' (see [Tool cards](#tool-cards)), measured in the docked toolbar of a real ACP window (`fe.py` on Linux, Xvfb at 96 dpi) at window widths of 360, 480 and 600 points and magnifications 0.85 to 2. A docked cell's `"ViewSize"` is the window's whole width (there is no scroll bar beside it). The main row's room for the model's name is the space between Sessions and the model menu when the name is long (the menus are right-aligned), and is `ViewSize - 3 - (scaled + texts) * magnification`: `$toolbarScreenReserve` (3) screen points, and in points at magnification 1 `$mainRowReserve` (41), `$menuReserve` (27) per menu and `$buttonLabelReserve` (5.2) for each of New's and Sessions' labels that is shown. An earlier all-scaled reserve cut the name with up to 53 pixels left at magnification 2 ("Cl…"). The folder row's label ends where the main row does, the menus' right margin from the window's edge: `$folderRowReserve` is `{2.25, 35}`; `$folderWarningReserve` and `$reviewButtonReserve` were measured headless and scale. The counts of the Review button are drawn in the toolbar's font (Source Code Pro, measured), the labels in the buttons' style.

## Tool cards

**They look like Chatbook's tool call openers** (the design of PR #1686: `openerView` in FrontEnd.wl, `makeToolCallBoxLabel` in Formatting.wl). A card is a line without a frame: a chevron (Chatbook's `openerRight` and `openerDown`), the tool's icon, the title, then the summary ("86 files", or "exit 1" in amber), the badge ("Allowed once", "Awaiting approval" in amber, ...) and a failed tool's red cross; a completed tool has no check mark, its title says what it did as Chatbook's "Used ..." does. An open card shows its body (Input, Changes, Output, Details) beside Chatbook's divider (a button with its `VerticalDividerTool...` ninepatch images, `openerViewDividerAppearance`) and a "Hide" line below it (an up chevron and the `"FormattingHide"` text resource); the header, the divider and "Hide" all close it (`cardBody`). A standalone permission card has the same line with the chevron's room left empty (`cardHeaderGrid` with `None`), so its icon lines up with the cards'.

* **Icons** (`toolIconName`, `toolIconView`) are Chatbook's `"ToolIconCall..."` function resources: `FileReader` (read, list and the notebook tools that read), `DocumentationSearcher` (glob, grep and the other searches, a script of documentation tools), `WebFetcher`, `WebSearcher`, `DocumentationLookup` (skills), `WolframLanguageEvaluator` and `WolframAlpha` (also in scripts), `CreateNotebook`, and `GenericTool` for the rest. Each is a `DynamicBox` of the resource applied to `CurrentValue[FontColor]`, so it has the color of the title. Chatbook has no icons for edits and shell commands: they get glyphs of the same kind (16 by 16 points, lines of 1 point: a pencil and a terminal, `editGlyph` and `shellGlyph`) without a color of their own, whose graphics take the title's color (`textColorGraphics`), and the tools that had a character (`?`, a check box, an arrow, `{ }`, a warning sign) keep it, in the title's color.
* **Colors.** The line has Chatbook's tool call colors (`openerViewColors["Tool"]`): "Default" for the text and the icon and the fainter "Default2" for the chevron, "Hover" for all of them under the pointer and "Pressed" while the mouse button is down there. They are options of a `StyleBox` around the line (`openerStyle`): `FontColor`, and the `BaseStyle` of its graphics (`GraphicsBoxOptions`), whose chevrons have no color of their own. Each color is a `LightDarkSwitched` of two `Dynamic`s (light, dark) with `Evaluator -> None` that choose by the `CurrentValue` of `"MouseOver"` and `"MouseButtonTest"`, which is the `StyleBox`'s: the whole line changes together, in the front end, also in a saved or copied final cell. A `Dynamic` that gives a `LightDarkSwitched` color did not work (the front end drew no such color for graphics, and for the text of some lines), and Chatbook's own openers (`NotebookTools`Mousedown`) show one of three copies of the line, which would store each card's title, with its fit `DynamicBox`, three times. The "Hide" line has the same colors (`hideLine`). A running card keeps them (it is a clickable opener, which shows its input), where Chatbook's running "Using ..." line, which can't be opened, is drawn in one fixed color; its progress animation follows the summary and the badge. Tried and dropped: `"MouseEntered"`/`"MouseExited"` handlers that set `DynamicModule` variables (a card whose header was clicked kept its hover colors after the pointer left: the click changes the card's layout and the front end sent no `"MouseExited"`).
* **Clicks.** A final card's header toggles on `"MouseClicked"` (the release of the button, like Chatbook's openers, which are buttons; the line has the "Pressed" color while the button is down), its divider and "Hide" set the variable to `False`, all with the front end's own functions (`staticOpener`). A live card's header, divider and "Hide" toggle the kernel's open state (`toggleHandler`, the `"ToggleOpen"` action).

**Titles take one line.** A tool card's title ("Searched for `pattern`", "Read src/a.wl", "Ran `command`"), a permission card's title and the Working header's activity never wrap: the title is cut to the width that the rest of its line leaves (the chevron, the icon, the summary such as "86 files", the badge, the status glyph), with an ellipsis at the edge, and a tooltip with the title and the object's first lines only when something was cut (an object of several lines shows its first line and " …", and always has the tooltip). Commands, patterns and queries lose their end; paths lose their start, so the file name stays ("Read …/ParserHelpers/StringEscaping.wl").

* **Parts.** `acpToolTitleParts` (Transcript.wl) gives the title as `"Prefix"`, `"Object"` (the command, pattern, path, query, tool list, the agent's own title, "the to-do list" of the to-do tools (a fixed text, but an object, so that the front end can cut it: as part of the prefix, the whole title was clipped without an ellipsis at 600 points and magnification 2, and the card overflowed its line, cutting off its check mark and "+", at 480 × 2 and 360 × 1.5), ...), `"Kind"` (`"Code"`: in the code font; `"Path"`: cut at its start; `"Text"`), `"Suffix"`, `"Truncated"` and `"Tooltip"`. A title with no object and no code spans (a pending tool's "Preparing a command…" while its input is still coming, or an agent's own title without one) is cut as a whole: the views make it its own text object (`wholeTitleObject` in Rendering.wl; as a prefix it was clipped without an ellipsis at 480 × 2 and 360 × 1.5). Its card keeps a badge only while the whole title fits beside it, as before: with the room of an object, a real front end showed "Stopped: … [Stopped]" instead of the title without its badge. The templates of the labels get a marker (`$titleObjectMarker`, U+E000) for the object, so the parts follow localized labels too. `acpToolTitle` is the string form (code in backticks), for the markdown export, the final cell's data and the status line's phrase (`acpToolAction`).
* **Kernel limits** (the front end cuts to the width; these only keep pathological text out of the boxes): an object's first line, at most 200 characters (`$maxTitleObjectLength`; a path keeps its end, `shortenPath`, at a folder separator); its tooltip at most 10 lines (`$maxTitleTooltipLines`) and 1,000 characters (`$maxTitleTooltipLength`); the status line's phrase ("You declined: run `…`") at most 60 (`$maxActionObjectLength`). The tools of an execute call, an MCP tool's name and an agent's own title (agents without OpenCode's `"name"`) have the limit too.
* **The front end cuts.** `acpFitText` (Rendering.wl, declared in Common.wl for other views, e.g. the toolbar's folder label) makes a clipping `Pane` (`ImageSize -> {{0, Full}, Automatic}`, or a number of points instead of `Full` with `"MaxWidth"`, for a line in a box whose `Full` is not the room in its row: see [The toolbar](#the-toolbar); `ImageSizeAction -> "Clip"`, no line breaks) around a `DynamicBox` with `Evaluator -> None` that only uses front end functions: `FEPrivate`StringWidth` (with explicit font options; the text, code font and surrounding font of each part are measured separately, so mixed fonts are exact), and a bisection over the list of the object's characters (`FEPrivate`Take`, `FEPrivate`StringJoin`: the front end has no string functions, about Log2 of the length measurements). Each text is measured at the size the front end draws it, its font size times the magnification (`fitFontOptions`), and the width divided by the magnification (`fitWidth`; the bisection compares drawn widths): the front end fits glyphs to the screen's pixels, so a text's width is not proportional to its font size (at magnification 0.85, 13-point text is about 4% wider than 0.85 times its width at magnification 1, 12-point text about 3%, measured in a front end on Linux). A width measured at magnification 1 and scaled left the ellipsis of a cut title beyond the edge at the window's default magnification, where the object's pane clipped it. The cut text is a string literal box that the front end joins itself (`"\"…ies/TOML.wl\""`, the pieces escaped as `ToBoxes` escapes them, `fitEscape`; an earlier version used `ToBoxes` there, which needs a kernel: a copy without a kernel showed the cut title blank, or "Read n.p" without an ellipsis after a resize). When the prefix ("Read ", "Searched for ") would leave the object less room than two ellipses (a very narrow or magnified window), the prefix is dropped and the object gets its room ("…ain.py" rather than a "Searched" clipped without an ellipsis; a remote folder label keeps its host, `"DropPrefix" -> False`). It is evaluated where it is shown and again when the window's size or magnification changes, needs no kernel (a saved or copied final cell keeps working: checked in a real front end by resizing a copy after the kernel had quit) and costs the kernel nothing. The boxes when everything fits and the function of the cut text are the arguments of the `DynamicBox`'s function, not its body, so tests can find their text.
* **Safety nets.** The width is computed, not measured, so it can be off (see below). The line is a grid of the prefix, the object in a clipping pane of its own, and the suffix (`fitLineBoxes`): if the width is too large, the object's pane takes the room that the prefix and suffix leave and clips the object on the side where it is cut (a path keeps its file name, a command loses its end), and the outer pane clips whatever is still too wide. Nothing is pushed out of the card.
* **Widths.** `acpFitWidth[ { screen, scaled }, texts ]` is, in points at magnification 1, `( ViewSize - screen - $fitSafetyMargin ) / magnification - scaled - texts`: the width of the window's content area (`"ViewSize"`, without the scroll bar), less what the layout puts around the line, less the measured widths of `texts`. Magnification scales most of that layout but not all of it, so a reserve has two parts. `screen` is in screen points, which magnification does not scale: in a real front end every cell reserves about 5 points at its right whatever the magnification (a top-level cell, and each inline cell inside a `BoxData`, measured in nested test cells), frame lines have absolute thicknesses, and the Working header's progress animation does not scale. `scaled` is in points at magnification 1 (margins, frame margins, icons, spacings, in ems). An earlier version treated all of it as scaled: the width was too large below magnification 1 (at 0.85 a cut title's ellipsis was clipped by the object's pane, one of its three dots left) and too small above it (titles cut with room left at 1.5 and 2, "Read …y" for main.py, the toolbar's model label down to "…"). The safety margin, 4 screen points, takes up the rounding of each part to whole pixels: at 0.85 a line got up to 4 pixels less room than its parts add up to.
  * **How the reserves were measured** (a real front end, `fe.py` on Linux, Xvfb at 96 dpi, the ACPChat stylesheet, Wolfram 15.0.1): the room of a line is the width of a long red text (or bar) in the title's clipping pane, and the room of a card that of a `Full`-width bar in the card's place, in final and live cells at window widths of 360, 480 and 600 points and magnifications 0.85, 1, 1.25, 1.5 and 2. The room is linear in the magnification, `room = ViewSize - screen - scaled * magnification`, apart from the rounding at 0.85. `$contextReserve` (outside a card) is `{17, 52.5}` live, `{16.5, 75}` in the "Worked for" opener, `{9.75, 50.25}` below it; inside a card everything scales (`$cardReserve`, `$headerGap`, `$badgeChrome`, `$progressIconWidth`); `$workingReserve` is `{13.25, 93}`. For the cards of Chatbook's design `$cardReserve["Tool"]` is 38.5 (it was 51 for the framed cards with the opener at their right, which also had a check mark after the summary): measured again with a red bar as the whole line of a "Read ... 1 line" card's title, in the "Worked for" opener and in a live view at 360, 480 and 600 points and magnifications 0.85 to 2, the computed width leaves 2.35 to 4.08 drawn points of the room unused, the same at every width (the measurement of the framed cards gave their old rooms within 1.5 points). A standalone permission card (`permissionEntityCell`, the chevron's room and no opener) has `$cardReserve["Permission"]` 35.5: its title's room in a live view, measured the same way (in a static copy of the live cell, without its `Dynamic`s), leaves 2.75 to 6.55 drawn points unused (`Fit-MeasuredRooms-Permission` keeps these rooms). Checked afterwards, with the framed cards (reserve 51), by drawing each cut title's object on a yellow background: at every width and magnification above, live, final and below the opener, with and without a badge, the object ends 0 to 20 pixels (one character at magnification 2, plus the margin) before the room's end, never beyond it (`Fit-MeasuredRooms` keeps these rooms as a test).
  * `FEPrivate`CellDisplayWidth` was not used: it is 0 for the inline cells that hold the cards in the "Worked for" opener, and for a top-level cell it differs from the width its content gets. In another notebook's stylesheet (a copied cell in a Default.nb or Chatbook notebook, whose cells have other margins) the computed width is too large; the panes clip then (a path at its start).
  * When the window is too narrow for a card's fixed parts (360 points at magnification 2 in the "Worked for" opener, where the linear model still gives the title about 33 drawn points: the chevron, the icon and "1 line" leave it less than that), the card is wider than the window, and the title is clipped or shows only "…".
* **Narrow windows.** When the title's object would get less than `$minObjectWidth` (24 points: an ellipsis and a few characters), the card's badge ("Allowed once", "Awaiting approval", ...) is dropped and its room goes to the title (`headerTitleAndBadge`, with `acpFitSwitch` and `acpFitWidthSwitch`, in the front end), so the status glyph stays in the card. The dropped badge leaves an empty column in the header's grid, which still takes the grid's spacing: the title's width while the badge is dropped reserves one `$headerGap` more than a card without a badge (`headerTitleWidth` with `"Dropped"`). Without it, the ellipsis of such a card lost its last dot at magnifications 1.5 and 2 (the live card awaiting approval at 600 × 2 and 360 × 1.5, the final declined card at 480 × 2). Checked afterwards with the room probes in a real front end, with the framed cards: the live card awaiting approval ends 5 to 15 pixels before its room at 360, 480 and 600 points and magnifications 0.85 to 2, the final declined card 10 to 21 pixels, every ellipsis whole.
* **Agent text.** Every part of a title, the status line (its stop reason and the declined tool), the activity label, the markdown export and the final cell's compact data are neutralized (`acpNeutralizeLinearSyntax`), and `titleView` and `acpFitText` make what they get display-safe (`acpSafeText`, see [Agent text as it is shown](#agent-text-as-it-is-shown)), tooltips included. A title's object is cut by characters and by whole markers (`safeTextPieces`: a `⟦U+202E⟧` is never cut in half). The status line (`statusLineView`) is an inline text cell (`Cell[TextData[{..., StyleBox[code, code font], ...}], "Text", FontSlant -> Italic, ...]` in the final cell's boxes), whose lines break between words like a paragraph's, so no line starts with ". Tell OpenCode what to do instead.": as a row of boxes (`titleView` of a string), the front end broke the line between the code span and the "." after it, also with a word joiner. It hides string characters (a copy in a notebook whose stylesheet shows them showed the quotes and escapes), draws operators as typed, keeps code spans upright in the code font, and is a built-in cell, so it renders anywhere; the permission panel's headline is still `titleView` of a string.

**Tool input and output are shown whole.** The Input section (an evaluator call's code, a script, a shell command, long values, markdown arguments) and the Output section show whole lines, never a line cut at a number of characters, with a note of what was left out outside the code block, never in it (Copy and Insert take the block's text): below a head, above a tail (output's "… n earlier lines"). They are `codeView`, `tailView` (output, its last lines) and `markdownView` (a subagent's prompt), with `codeHead`/`codeTail`. The limits (`$codeViewLimits`): live views the first 20 lines and 1,000 characters (the live code block template clips at 400 points, and live views have no scroll panes, R6; output keeps its last 12 lines), final cells up to 2,000 lines and 200 KB (output its last 200 lines). The permission panel's 120-line, 20,000-character limit bounds only a request's raw-input values (`rawInputGrid`, the requests without a command, diff or script), which have no "View full" link; a request's command, diff and script have their own, smaller previews with a "View full ..." link (12 lines and 4,000 characters for a command, 80 lines for a script, a script's markdown arguments 12 lines — see [Large requests](#large-requests)). Only a first line longer than the characters' limit is cut inside the line. Wolfram Language code that was cut and is not complete (`SyntaxQ`) is shown as text: as code, its open brackets and strings would be colored as syntax errors.

* **Details** is the tool call as the agent sent it, as JSON, for debugging, and is kept small since the other sections show the texts (`detailsSection`): string values longer than 2,000 characters are shortened with an ellipsis (`$detailsValueLength`; the JSON stays valid, and the note below the block says how many characters were left out), the content is left out when it only repeats the raw output's text (OpenCode sends a tool's output in both; `detailsContent`), and the view has its own limits of 400 lines and 20,000 characters in final cells (`$detailsLimits`). For a turn that reads 20 files of 120 KB (each sent as the content and as the raw output, as OpenCode does; measured in a kernel, `acpFinalCell` without front end formatting), Details keeps the final cell's strings at about 0.53 MB (2.9 MB with Details unlimited, which makes the cell 4.3 MB); with the grid cards, which keep each header once (see [State model](#state-model)), and the front-end-only "Worked for" opener, the whole cell is about 2.38 MB with the cards of Chatbook's design (`ByteCount`; 871,000 characters as `InputForm`; 1.99 MB and 801,000 characters with the earlier, framed cards; 1.95 MB with Chatbook's `ThoughtsOpener` template as the opener; an earlier card structure gave 1.74 MB, and about 2.35 MB with the header in both panes of each framed card). A 40-read turn with long paths is about 3.4 MB (633,000 characters as `InputForm`) with 40 fit `DynamicBox`es (one per card): the chevrons, the colors of the openers' states, the divider and the "Hide" line take about 3,600 characters per card (2.6 MB and 489,000 characters with the framed cards, and about 4.2 MB, 753,000 characters and 80 fit `DynamicBox`es with their header twice; `FinalCell-SizeRegression`).

* **Height.** In final cells every view is in a `Pane` with `ImageSize -> {Automatic, UpTo[480]}` and `Scrollbars -> Automatic` (`heightLimited`). In the ACP window, the code block template (`ChatCodeBlockTemplate` of WorkspaceChat.nb) scrolls its code at 400 points, so code never gets two scroll panes; in a notebook whose template has no pane (a cell copied into a Chatbook notebook), this pane scrolls.
* **As written.** The agent's Wolfram Language code is shown, copied and inserted as it was written: `codeBlock` formats it inside `withCodeAsWritten`, which turns off what Chatbook's own chats do to a model's code (`autoCorrectWLCodeBlock`'s CodeCheckFix, `preprocessSandboxString`, `inlineExpressionURIs`, the In/Out grid of `parseCellGroupBlock`, `adjustBoxSpacing`). This also removes their cost from the pump (CodeCheckFix took 27 s for 96 KB, `adjustBoxSpacing` 20 s for 126 KB; the front end's parse takes under a second). Linear syntax stays neutralized.
* The streaming form of Wolfram Language code (live views, and Chatbook's own streaming) shows the quotes of strings (`ShowStringCharacters -> True` in its "ChatCodeActive" cell, as in the finished "ChatCode" cell).
* A direct call of the Wolfram MCP server's evaluator (`Wolfram_WolframLanguageEvaluator`, whose `"Name"` is in lower case) gets the evaluator's icon, and its Input section shows the `"code"` argument as Wolfram Language (`wolframEvaluatorInputView`: Chatbook's code formatting, as written, with Copy and Insert, like a call in a script), its other arguments as a grid.

**Copies and pastes.** A final cell is copied and pasted like any cell (an answer copied into a notebook, or the whole cell with its "Worked for" opener open), so its boxes must also paste quickly in any notebook. Three constructs made the front end spin when a copy of a final cell whose "Worked for" opener was open was pasted; with the opener closed, the same copy pasted at once:

* **A `TemplateBox` with an inline `DisplayFunction`.** The tool cards were `TemplateBox[{header, body}, "ACPToolCardOpener", DisplayFunction -> ...]` (a `DynamicModule` and a `PaneSelector` in the function, to store the header once): the paste never finished (WolframNB's main thread at 100% CPU, its memory growing, until it was killed) into a Default.nb notebook, an ACPChat notebook and a Chatbook chat notebook, with a kernel or with `Evaluator -> None`. It did with the `DynamicModule` outside the template too, and a template whose function was only a `FrameBox` of `#1` took 36 s for 8 cards. The cards are now built from built-in boxes (see [State model](#state-model)): a `DynamicModule` over a pane (no frame since the cards look like Chatbook's tool call openers) and a grid, the header written once.
* **Chatbook's `"ToolIcon..."` templates.** Their `DisplayFunction` is a `DynamicBox` of `FEPrivate`FrontEndResource`, which the front end evaluated for about 2 s per icon while pasting: 7 to 8 s for a copy with 4 read cards as plain frames, 50 s with HEAD's openers, 15 s for 2 cards with the header in both panes and 28 s with the current grid, and a copy with 40 cards never finished. The cards' icons were then the same `DynamicBox` without the template (`chatbookIcon[name, False]`), and those pastes took about half a second. They are now, as Chatbook's own tool call openers' icons, `DynamicBox`es of the `"ToolIconCall..."` function resources applied to a color (the title's: `CurrentValue[FontColor]`); with them and the openers' colors (see above), a copy of the 40-card cell with "Worked for" open pastes in 1.03 s into Default.nb (token paste, fe.py), where its cards open and close (also by the divider and "Hide") and change color under the pointer, as in a notebook with `Evaluator -> None`.
* **Chatbook's `ThoughtsOpener` template as the "Worked for" opener.** A copy with the opener open, pasted (Ctrl+V) into a Default.nb notebook when no kernel was running, started a kernel and showed the cell once it was up; pasting the same clipboard again after the kernel was quit again never finished (WolframNB at 100% CPU, its memory growing 1 to 2 MB/s, no kernel started): 4 of 4 times in one check, 1 of 1 in another (438 to 489 MB in 38 s). It did not with the opener closed, and needed many dynamic boxes inside the open opener (42 plain front end resource `DynamicBox`es were enough, 14 were not); a Text cell with the same 42 boxes needed no kernel at all. The "Worked for" opener is now ACP's own front-end-only opener (`workOpenerBoxes`, see [State model](#state-model)), and those re-pastes finish: 3 of 3, with the 14-card cell of a mock-agent turn (twice) and a 40-card one.
* **Not the opener: the kernel wait.** Any final cell pasted into a notebook without a running kernel starts one and appears only when it is up (16 to 24 s in this setup, where the kernel loads the development Chatbook from source), with the old or the new opener, open or closed, and also without code blocks and without thought openers: the cell is a `ChatOutput` cell, and Chatbook's `ChatOutput` style has an `Initialization` that attaches the chat menu, which the front end evaluates in a kernel before it shows the cell. The same cell with the `"Text"` style pasted in 0.8 s and started no kernel. Chatbook's style is not changed (see Known limitations).
* **With a kernel**, a copy of the 40-card cell with "Worked for" open pastes in 0.76 to 1.1 s into Default.nb, 0.43 s into an ACPChat notebook, 0.79 to 0.84 s into a Chatbook chat notebook and 0.66 s into a notebook with `Evaluator -> None` (token paste, fe.py). Pasted copies now keep "Worked for" open (the copied `DynamicModule` box has its variable's value), in every notebook; with the template that was only so in ACPChat notebooks. ## Permissions

OpenCode sends `session/request_permission` for edits, shell commands, access outside the project and the notebook tools that change open notebooks (see [MCP server](#mcp-server)). The request is recorded in the window's `"PendingPermissions"` and attached to the matching tool card (which shows an "Awaiting approval" badge). The first pending request is shown in an amber panel above the input field, with the command, diff or script and the agent's options ("Allow once", "Always allow", "Reject"); "1 of 2" shows when several are queued. The buttons are preemptive and ignore clicks for 0.4 s after the panel appears (and again after it is shown with new content, such as the titles of [Scripts and the notebook tools](#scripts-and-the-notebook-tools)).

* "Always allow" is remembered by OpenCode for the project (also in future sessions); the text below the buttons (and the button's tooltip) says what is saved. ACP does not send OpenCode's saved patterns, so they are derived the way OpenCode does: for shell commands, one `"<prefix> *"` pattern per subcommand (e.g. `cd build && rm -rf dist` saves `"rm *"`; the prefix length comes from OpenCode's arity table, e.g. `"git status *"`, `"npm run build *"`), skipping directory changes; for access outside the project, the directory (or the repository that contains it); for edits, all edits in the project; for an MCP tool (also one that a script asks about), every later use of that tool in the project. For a remote window, the directory outside the project is found with string operations on the host's POSIX paths (`~` is the remote home folder, `acpPathContext`), never on this computer, and is shown abbreviated with the remote home. A command is split into subcommands by reading it as tokens (quoted strings, escapes, comments, here-document operators, separators, brackets; `shellSplitCommands`, linear in its length). Comments and the body of a here document (`cat <<EOF ... EOF`, also `<<-`, quoted words and several documents on one line; at most 16) are not commands, as in OpenCode, which takes only the command nodes of tree-sitter's parse: a command that writes a large file that way saves `"cat *"` and the patterns of its other commands. But the text must never name fewer patterns than OpenCode saves (an agent could hide a command behind something that only looks like a comment or a here document), so they are left out only where the shell certainly reads them so, and anywhere else their words are read as commands, which can only add patterns: a comment is a `#` at the start of a word; a here document needs `<<` at the start of a word and a plain word (letters, digits and `_`, maybe quoted as a whole), neither of them inside `${...}`, `$[...]`, `((...))`, `$((...))`, `[[...]]` or backquotes (where `<<` is a shift or `#` a character of a word), and its body is skipped only if the line break after the operator is outside them too, at the same depth of parentheses, and a line with the word follows. The text names at most 8 patterns, then "and n more". It is computed once per card, for the text and the tooltip.
* Reject marks the tool "Declined" (neutral, not an error) and the turn ends with "You declined: ...".
* Stop cancels the prompt and answers all pending requests as cancelled; unfinished tools become "Stopped". A request of the turn that is still pending when the turn is finalized (e.g. one that arrived after Stop, before the agent's response) is answered "cancelled" and removed from the panel.
* A request withdrawn by the agent (`$/cancel_request`) disappears from the panel.
* A request from a background subagent that arrives when no turn is running is cancelled, with a notice.

### Large requests

The panel is part of the attached input cell, which the front end lays out again on every keystroke in the input field (it writes the TaggingRules continuously) and on every update of the window's views (the derived views' watchers): a panel with a 400-row diff grid made typing take 0.3 to 0.55 s per keystroke in a real front end, although its scroll pane showed only about 15 rows. So the panel shows only a few lines of a large request (`permissionPreview0`):

* **Diffs:** the first 12 rows of each of the first 3 files (the first change with its context; `$permissionDiffLines`, `$permissionDiffFiles`), rows cut to 160 characters (`$permissionLineLength`) and display-safe like the review window's (bidi controls and line separators as markers, `acpReviewSafeLines`, as in every diff view; in the panel, `$safeDiffLines`, the path through `acpRemoteDisplayName` too), "… n more lines" and "and n more files".
* **Shell commands:** the first 12 lines, of those at most 4,000 characters (lines are wrapped; a longer text ends there with "… n more characters"), and a note of the rest.
* **Scripts:** as before, the first 80 lines (see [Scripts and the notebook tools](#scripts-and-the-notebook-tools)).
* Measured with `Rasterize` under `UsingFrontEnd` (layout only, in a 480-point pane): 0.38 to 0.62 s for the 400-row panels before, 0.03 to 0.05 s now; the panel's kernel time for a one-line edit of a 10,000-line file went from 10.6 s (past the front end's 6 s `DynamicEvaluationTimeout`) to 0.09 s.

When the preview leaves something out (`permissionFullKind`), a **"View full diff"** ("View full command", "View full script") link below it opens the **permission details window** (`PermissionDetails.wl`): `ChatbookAction["ACP", "PermissionDetails", nbo, key]`. The key (`acpPermissionKey`) is a hash of the request instance (its id, turn, arrival time and tool call: JSON-RPC ids repeat after a reconnect), never the agent's text; the action looks the request up among the window's pending requests and opens nothing for one that was answered meanwhile (`"PermissionDetailsNotPending"` in the debug log). The panel's signature includes the arrival time too, so that another request with the id of the one shown is shown.

* **Read only:** the request is answered in the panel. The window shows the headline, the number of files (or lines), and the whole diff (not the whole file), the command or the script. Its content is static (front-end-only openers, lazily rendered diffs that load Chatbook), so it stays readable after the request was answered and after a kernel restart. A window that was still being written when the kernel was restarted keeps what it got: its header loses "Loading…" and says "Incomplete: loading was interrupted", and so does a note after its last cell (in place of the "Loading…" of a window that got no content yet). Its job is kernel state, and the link that could open it again is gone with the pending request, so `acpRefreshWindowUI` schedules `acpPermissionDetailsRecover`, like the recoveries of the Sessions window and the prompt notebooks: a details window of the ACP window whose TaggingRules still say `"Loading"` and that has no job in this kernel is marked incomplete (`detailsIncomplete`; the header is kept in its TaggingRules, `{"ACPPermissionDetails", "Header"}`, display-safe and made so again when shown). A step that fails ends the job the same way.
* **One window per ACP window,** found by its TaggingRules (`{"ACPPermissionDetails", "Owner"}`), also after a kernel restart: another link replaces its content and keeps its place (`acpReviewPut`). It closes with the ACP window (`acpWindowClosed`, `acpCloseWindow`).
* **Like the review window:** a deployed, non-editable, unsaveable notebook with the review stylesheet, `ExcludeFromChat` (so the Notebook Assistant and the [notebook tools](#notebook-tools) leave it alone), the ACP window's kernel as `Evaluator`, `WindowElements -> {"VerticalScrollBar", "MagnificationPopUp"}`, placed like a new review window (`acpReviewWindowGeometry`). Nothing in it (or in the review window) is spell checked (`ShowAutoSpellCheck -> False` in the stylesheet's `"ACPReviewBase"` and on the text cells): a command is not prose.
* **The whole diff, bounded:** each file is a card (`acpReviewFileCard`) with the first 400 rows of its diff, with line numbers (`acpDiffRows` with numbers, display-safe and cut to 300 characters, as the data of `acpReviewDiffView`), and the rest of its rows follow the card as text cells of 500 lines in the code font, with the old and new line numbers (`"  12   14 + line"`): a grid row takes about a millisecond to lay out, a line of text much less. The first card starts open; later cards start open if they have at most 300 rows and the open cards stay under 1,200 rows, the others are rendered when first opened (`acpReviewLazyDiff`, their first 400 rows; the text of their other rows is below them all the same). Commands and scripts are text cells too, display-safe and not cut. A window holds at most 2 million characters of text (`$detailsMaxText`), then "… n more lines" or "… n more characters" for the rest of that file (or text); later files still get their cards.
* **Built in steps** of about 0.15 s in the pump (`detailsStep`, through `acpSchedule`): the link shows "Loading…" at once, the first step replaces the notebook with the header and the first cards, later steps append cells after the last one, and the header loses its "Loading…" with the last step. A file's card is one item of the job, and its text follows in items of 500 lines (as do the lines of a command or script), so a step does little more than 0.15 s of work also for a file of 100,000 lines: the file's item makes only the rows of its card, from a row source of the diff (`acpDiffRowSource` in Rendering.wl: the cached line diff, its line numbers and collapsed context computed on packed arrays, about 0.05 s for 100,000 lines; `acpDiffSourceRows` makes any range of the rows that `acpDiffRows` gives), and its text items hold row ranges, whose rows are made when they are written; the characters that a note of the text budget counts are counted only when the budget runs out (`detailsLeftChars`). Before, the first step of a new file of 100,000 lines made all its rows and chunks, about 1.3 s. A step that computes a line diff that is not in the cache (the permission panel usually computed it already) takes as long as that comparison. Another link replaces a running job.
* **Interrupted turns:** the cards that the final cell of an interrupted turn (Reject or Stop of a big edit) shows expanded below its opener are laid out at once, so their diffs keep 40 rows, as live cards do (`$expandedFinalCard`); the closed cards of the final cell keep 400.

### Diffs

`acpLineDiff` (Transcript.wl) compares the old and new texts of a diff line by line. OpenCode sends the whole old and new file with every edit, so the lines the texts have in common at their start and end are matched first (on the line lists), and only the lines between them are compared, with `LongestCommonSequencePositions`: a longest common subsequence, so the fewest lines are removed and added. It takes time in proportion to the number of pairs of equal lines (quadratic for a file whose lines are all the same), so it is used within a budget of 2 million pairs per diff (about 0.2 s). Past it, the lines that occur once in each text are matched first, in the longest order both keep (a patience diff), and each stretch between them is compared with what is left of the budget (each charged with its own pairs of equal lines, counted unless the stretch is small). A stretch that can't be compared is shown as its old lines removed and its new lines added, and the view says that "Some changes are shown as blocks of removed and added lines" (`acpLineDiffInfo`'s `"Aligned"`). An edit of one line of a 10,000-line file takes about 0.05 s and shows that line (all old lines removed and all new ones added, past 4 million line pairs, before). The last 16 results are cached by their texts (looked up by hash; the texts are compared on a hit; the oldest are dropped while the entries take more than 32 MB in all, but the newest result is always kept), so the panel, the stats in the tool cards' headers, an opened card, the final cell and the details window share one comparison. Unchanged runs are collapsed to 3 lines of context in linear time, with packed arrays (`collapseContext`). Line counts are computed by the views from the cached diff, never in reader handlers.

### Scripts and the notebook tools

In code mode (OpenCode's default) the agent calls MCP tools from JavaScript that it passes to OpenCode's `execute` tool (see [The agent's side](#the-agents-side)), and OpenCode 2.0.26 asks for the permission of an MCP tool (e.g. `WolframNotebooks_InsertCells`, see [Security of the MCP server](#security-of-the-mcp-server)) with `toolCall` `{name: "execute", title: "execute", kind: "other", rawInput: {code}}`: the request names neither the tool it asks about (OpenCode only sends the permission's action when the request has no tool part) nor the tool's input (OpenCode checks MCP tools with empty metadata), only the script. So the panel shows what the script shows, and always the script itself:

* **The headline** names every tool that the script names, anywhere in it, also in comments and strings, so that a decoy can't take the place of a real call: "OpenCode wants to run a script that may use WolframNotebooks: DeleteCells, WolframNotebooks: ListNotebooks". The notebook tools that change open notebooks (`$acpNotebookEditTools`, for which Chatbook's rules make OpenCode ask) come first, and at most 6 are named; such a tool also counts when the script only names it (in a string, a comment or a computed name). "and other tools" follows unless these are surely all (`scriptToolsShownQ`): when the script may also reach tools in ways that can't be read (any use of `tools`, of an alias or of the server's name `WolframNotebooks` that is not part of a reference or alias that can be read, such as `tools[name]`, a comment between `tools` and its `.`, `(0, tools)`, `x || tools`, `f(tools)`, `(p = tools.WolframNotebooks)[name]` or a destructuring; more than 20 definitions of aliases), is longer than 100,000 characters, has more than 100 references, or names none of the tools that change notebooks (then the tool that OpenCode asks about is reached in a way that can't be read, or the request is about a rule of the user's own). Only a word in a comment or a literal is no use, except a string literal that is the word or a path that starts with it (`"WolframNotebooks.DeleteCells"`). A script that names no tool gives "OpenCode wants to run a script".
* **Below it**, each reference to a tool (the edits first, at most 12, then "… n more references to tools") with its arguments: for the notebook tools their parameters in a fixed order (`notebook`, `cell`, `position`, `cells`, `offset`, `limit`, `markdown`; other keys are not used by the tools), for other tools all of them, and the code of the Wolfram MCP server's evaluator. A value is shown as it is written where it is a literal (a string, decoded; a number; `true`, `false`, `null`; a list of those); anything else (a variable, a template literal with substitutions, an expression) is "(computed)", and so are the keys before a spread (`...x`), a computed key or `__proto__`, which add a "…" row. A reference that is not called with an object literal (or that is in a comment, a string, or after a token that JavaScript may read differently, see below) has "(computed)" arguments, and its notebook is not resolved. The markdown is a plain code block of at most 12 lines.
* **The script** follows as a plain code block, at most 80 lines with "… n more lines". Its lines are wrapped, never cut (the end of a long line can hold a call); only a script whose first 80 lines have more than 20,000 characters ends there with "… n more characters". Then "View full script" shows all of it in the [permission details window](#large-requests). The script, the markdown and the other values are the agent's text: they are shown as plain strings (`plainCodeBoxes`, `codeText`; the front end's linear syntax neutralized, `acpNeutralizeLinearSyntax`), never through Chatbook's formatter.
* **The notebook** of a call of the notebook tools is shown with its window title and id once the pump has resolved it. Resolving takes front end calls, which a reader handler must not make (rule R2): `onPermissionRequest` (Connection.wl) schedules `resolvePermissionNotebooks` for a local window's request that names notebook arguments (`acpPermissionNotebooks`, the string literals of the calls), and the pump calls `acpNotebookTitles` (NotebookTools.wl), which resolves them as the tools do (an id or the start of it, a window title or a file of one of the notebooks that ListNotebooks lists) and leaves out the arguments that don't name exactly one notebook. The titles go into the request's entry of `"PendingPermissions"` as `"NotebookTitles"`, which is part of the panel's signature, so the panel is shown again with them (a request answered meanwhile gets nothing). Until then, and for arguments that were not resolved, the argument is shown as it is. Remote windows resolve nothing (their agent can't reach this computer's notebooks).
* **A direct call** of a notebook tool (code mode off: `toolCall` name `WolframNotebooks_InsertCells`, its input as `rawInput`) gets the headline "OpenCode wants to use WolframNotebooks: InsertCells" and the same arguments; a `"command"` or path in its input is neither shown nor taken for the scope of "Always allow".
* **"Always allow"** of a script saves the tool that OpenCode asks about, one of the script's (its text says so and names them, with "and other tools" as in the headline), for every later use of that tool in the project, in any script; of a direct call, that tool. The options are the agent's, as for every request: Chatbook does not ask again or hide any.
* The tool cards of the transcript show the same arguments, without titles: an `execute` card's Input section (from the script while the call runs, from OpenCode's metadata of the calls once it has completed), and the card of a direct call.

**How a script is read** (`acpExecuteScript`, Transcript.wl, pure). The references are found by regular expressions over the text: `tools.S.T`, `tools["S"]["T"]`, `tools["S"].T` and `tools.S["T"]` (any quotes, optional chaining `?.`, any of JavaScript's white space, also `globalThis.tools`), and `nb.T` or `nb["T"]` for a namespace alias that a declaration of its own defines: `const nb = tools.S;` (or `let`, `var`) on one line that ends there, with `;` or `}`, or at the end of the line before a name, `}` or the end of the script. `tools.S` assigned in any other way (in an expression, such as `(p = tools.S)[name]`, with a comment or another member after it, or over several lines) is a use of `tools` that can't be read. A name in brackets is only read if it is a name (letters, digits, `_`, `$`, `-`, after decoding): a path (`tools["S.T"]`), an octal escape or a string with quotes, brackets or operators (whose quotes may end two literals with code between them) can't be read. Every other occurrence of the word `tools`, of an alias or of the server's name counts as a use that can't be read (see the headline), except in a comment or a literal. Unicode escapes in names (`\u0074ools`, `\u{74}` with any number of digits) are decoded for the tools that are named, in a copy in which every word counts (an escape in a string can stand for a quote). The script's tokens (comments that end at any of JavaScript's line terminators, string and template literals, names, numbers, single characters; a comment or literal that is not closed runs to the end, so that the tokens are found in one pass) are only used up to the first token after which JavaScript may read the script differently: a `/` that may start a regular expression, whose text may have quotes or comment marks (a `/` is a division after a number, a literal, `]` or a name that is not a keyword such as `return` or `typeof`; after any other token, such as `)`, `}`, an operator or such a keyword, it may start one), `<!--` or `-->` (HTML-like comments), `#`, a string literal that is not closed, or a template literal that is not closed or has a substitution with comments (also HTML-like ones), slashes or backslashes, or more than 4 levels of template literals and braces (which may hold a backtick that ends it elsewhere; string literals, braces and template literals in substitutions are read as JavaScript does), and only the first 20,000 tokens are used. Up to there the tokens are JavaScript's: a word in a comment or a literal is only text there, and a call's arguments are only read there, when its callee and its `(` are tokens, with a subset of JavaScript (a value that is not a literal may only contain names, numbers, strings, template literals, brackets and a few operators; an argument that is not one object literal followed by `)` or `,` is "(computed)" as a whole), so that a value shown is the one that JavaScript uses, and a decoy in a regular expression or in a template literal's text is not taken for a call. Reading the arguments of all references looks at 5,000 tokens at most (comments count too), and reads lists of at most 1,000 items; reading follows at most 20 definitions of aliases and reads the names of the first 101 references through `tools` and through each alias (with more, the references are not complete anyway), so that a script of 100,000 characters takes well under a second to read, whatever it is; the last 16 results are cached. `onPermissionRequest` reads the script in the reader handler (`acpPermissionNotebooks`), and the panel's views then find it in the cache. The headline and the arguments are only a summary of text that the agent wrote, which can reach a tool in ways no reader follows (`eval`, names computed at run time): what the user approves is the script.

## Reviewing changes

The ACP window keeps a summary of the uncommitted changes in its project folder. While there are changes, the project folder row of the toolbar shows a **Review** button with the line counts ("Review +40 −2"; the tooltip says how many files changed). It opens the **review window**, which lists the changed files and shows their diffs. Nothing in it changes the repository: it lists, shows diffs, refreshes and opens files. The backend is `Git.wl`; the button and the window are `Review.wl`. For remote windows, git runs on the remote computer, one ssh connection per check (see [Git and Review over SSH](#git-and-review-over-ssh)); what is compared and how is the same.

**What is compared.** Everything that differs from `HEAD`: staged and unstaged changes of tracked files, as one diff against `HEAD` (like `git diff HEAD`), plus untracked files that are not ignored, one by one (`--untracked-files=all`). Git runs in the project folder with the pathspec `.`, so only changes inside the project folder count when it is a subfolder of the repository; paths in change sets are relative to the project folder (and `"RepoPath"` to the repository root). In a repository without commits, the diff is against the empty tree. Changes made before the session are included. Dirty submodules are not inspected (`--ignore-submodules=dirty`: a submodule shows up when its commit changed, but changes inside it are not listed). Statuses are relative to `HEAD`, although git status gives two letters (index and working tree): a file that was added to the index and then deleted from the working tree (`AD`, `CD`) is not listed at all, and a file that was renamed and then deleted (`RD`) is listed as its original path, deleted. git status finds renames between `HEAD` and the index, `git diff HEAD -M` between `HEAD` and the working tree: a rename that only the diff finds (a copy added to the index, the original deleted only in the working tree) becomes one renamed file, and a rename that only status finds (renamed, then rewritten) counts the lines of both files. After `git rm --cached`, a path is a deleted file and an untracked file; the untracked one shows its own content.

**Read-only.** Nothing writes to the repository, so the checks never get in the way of the agent's own git commands (e.g. with `index.lock exists`):

* every command is read-only and runs with `--no-optional-locks` (except `git --version`, which does not look at the repository and runs bare, so that a git too old to know the option is reported as too old), so `git status` neither refreshes `.git/index` nor takes `index.lock`;
* `git diff` writes the refreshed index even with `--no-optional-locks` (when files' timestamps changed), so it also gets `-c diff.autoRefreshIndex=false`;
* commands never create objects (`hash-object -w`, `stash create`, `add`, ... are never used); a partial clone can't fetch missing objects: `-c protocol.allow=never` turns off all transports (with any git version), and git 2.45 or later also gets `--no-lazy-fetch`.

`Tests/ACPGit.wlt` checks that `.git/index` stays byte-identical through a summary check and a full change set of a repository with a modified file and a file whose timestamp changed, so that `git diff` runs too (and that the same plain `git diff` does change it).

**Repository config cannot run programs.** A repository's `.git/config` and `.gitattributes` (which the agent can edit) could otherwise make `status` and `diff` run programs. Every command gets `--no-pager`, `-c core.fsmonitor=false` (no hook, no fsmonitor daemon), `-c protocol.allow=never` (no transports: a partial clone would otherwise fetch missing objects with the upload-pack, ssh command or credential helper of the repository's config), `-c core.quotepath=off`, `-c diff.relative=false` and `-c diff.suppressBlankEmpty=false` (predictable output); diffs get `--no-ext-diff`, `--no-textconv`, `--no-color`, `--src-prefix=a/ --dst-prefix=b/`, `--submodule=short`, `-M` and `-U3`. Filter drivers (e.g. Git LFS, or anything configured in the repository) run programs whenever git reads a file of the working tree, and there is no option to turn them off, so each check first lists the configured drivers (`git config -z --get-regexp '^filter\.'`) and neutralizes each one with `-c filter.<name>.clean= -c filter.<name>.smudge= -c filter.<name>.process= -c filter.<name>.required=false` (an empty process also disables the clean command; the name can be empty, `[filter ""]` for the attribute `filter=`). Git splits `-c` arguments at the first `=`, so a driver whose name contains `=` can't be turned off this way: then the check fails with the error `"UnsafeConfig"` ("The changes are not listed: ...", with the driver's name) instead of letting git run it. All drivers are neutralized, also the user's global ones: trusting Git LFS from the global config would let the repository's config run programs through it (`lfs.extension.<name>.clean`). So a Git LFS file whose timestamp changed (or that was checked out within the same second as the index was written) is compared as raw content with its pointer and listed as modified, binary, until a `git status` of the user or the agent refreshes the index. The user's `status.*`, `diff.*` and `color.*` settings don't matter.

**Finding git** (`acpFindGit`): the directories of `PATH`, then `/usr/bin`, `/usr/local/bin` and `/opt/homebrew/bin` (Windows: `Git\cmd` and `Git\bin` under Program Files and the per-user install folder). On macOS, `/usr/bin/git` is a stub that opens an "install the command line developer tools" dialog when they are missing, so it is only used if `/Library/Developer/CommandLineTools/usr/bin/git` or Xcode's git exists. The result is memoized per kernel session (git that was not found is looked for again after a minute). Git older than 2.25 counts as unavailable. Before any process is started, the project folder must exist and have a `.git` entry in it or one of its parents (`acpGitWorkTreeRoot`: the path as given, then with symbolic links resolved, since git works in the physical folder: a project folder that links to a subfolder of a repository is in that repository); git decides the rest.

**Running git** (`acpGitRun`, a wrapper of the general runner `acpProcessRun`, which Remote.wl's one-shot runs use too): never `RunProcess`, which can hang while an ACP reader is active. Commands are started with `StartProcess` from the pump and polled every 50 ms with `acpSchedule`; each poll drains standard output and error with non-blocking reads, with ProcessLink's `$processRunningQTimeout` blocked to 0, like ACPLink. ProcessLink writes a process's output to files (`~/.Wolfram/ApplicationData/ProcessLink/Streams`), so git never blocks on a full pipe, and a `ReadByteArray[..., EndOfBuffer]` read goes on for as long as the process keeps writing (a fast `git diff` of 250 MB came back in one 5-second read): each poll reads exactly the bytes that are available (the file's size minus the stream position), at most 4 MB per stream, so the output cap and the timeout hold and memory stays bounded. Output is decoded as UTF-8 (invalid bytes as ISO 8859-1), `"\r\n"` becomes `"\n"`, and the private-use characters of the front end's linear syntax are replaced (see below). Each command has a timeout (10 s in summary checks, 20 s otherwise) and an output cap (16 MB); then the process is killed (and output beyond the cap is dropped). A command whose window record is gone, or whose request was superseded, is killed too. Finished processes are released with `KillProcess` as well: in the 15.0.1 kernel every `StartProcess` otherwise leaks file descriptors.

**Change sets.** `acpGitChanges[dir | nbo, continuation]` (or `acpGitChanges[dir, continuation, key]`) queues a request; the pump runs `git --version` (once per executable), `rev-parse --show-toplevel --show-prefix --show-object-format` (once per project folder), the filter driver listing, `status --porcelain=v2 -z --branch`, `diff <HEAD | empty tree> --numstat -z` and `diff <HEAD | empty tree>` (the patch, skipped when only untracked files changed), then parses the patch, reads untracked files in the kernel, builds the change set and calls `continuation[changes]`, each in its own pump tick (the patch 2000 files per tick), so that no evaluation of the pump takes long: the parsers are linear in the size of the output (one file with 50,000 changed lines splits in milliseconds, 20,000 renames parse in a fraction of a second), and with 16,000 renamed or 20,000 modified files the longest pump evaluation of a request took about 0.6 s (it took seconds to minutes before). Requests are single-flight per requester: a newer request with the same key (the review window, or `{mode, nbo}` for an ACP window's summary checks and full requests) supersedes a running one, which stops at its next step (its git command is killed) and passes a change set with the error `"Superseded"` to its continuation. The change set lists the first 500 files by path in git's order (`"MoreFiles"` tells how many more), sorted in natural path order (`gitNaturalOrdering`: folder by folder, so the files of a folder stay together, ignoring case, and runs of digits by their value, so `src/mod2.py` comes before `src/mod10.py`; sorting only the listed files keeps it cheap), with status, line counts, git's extended header and hunks per file (`"Patch"` starts at the first `@@` line), and the text of untracked files. Files that only differ in mode, pure renames, binary files, submodules, untracked folders (nested repositories) and files that could not be read get a `"Note"` instead of a diff. Untracked files are read only if they are regular files (never devices or pipes), at most 1 MB each and 16 MB per request (the same in summary checks and full change sets, so the button and the review window count the same lines); a NUL byte in the first 8000 bytes means binary, as in git. Untracked symbolic links are never followed (the file they point to can be anywhere, and git would add the link, not the file): they are listed as one added line, like git, with the note "A symbolic link to <target>" (the resolved path) or "... to a file that does not exist". All keys are documented at "Change Sets" in `Git.wl`; `acpGitBuildChangeSet` makes change sets from git output (for tests). With a window, the request also updates the window's summary.

**The window's summary** (`acpGitSummary[nbo]`, the window record's `"Git"` key, kernel state only): `"Status"` (`"Unknown"`, `"Checking"`, `"Unavailable"` (no usable git), `"NotRepository"`, `"Clean"`, `"Changes"`, `"Error"`), `"FileCount"`, `"Added"`, `"Deleted"`, `"Branch"`, `"Detached"`, `"Initial"`, `"Root"`, `"Prefix"`, `"Error"`, `"Directory"`, `"CheckedAt"`, `"Duration"`, `"StartedAt"`, `"InFlight"`, `"Token"`, `"Stale"`, `"Paused"`. A summary check runs status and numstat (no patch); one runs at a time per window, and results whose token or folder are no longer the window's are dropped. Checks start (housekeeping, every 0.4 s while the pump runs):

1. when the project folder is set or changes (new window, directory change, record rebuilt after a kernel restart);
2. after a turn ends (`acpFinishTurnState` marks the summary stale);
3. during a turn, when a tool call that may have changed files completes or fails (edits, writes, patches, deletes, moves, shell commands, subagents, and tools of unknown kind such as MCP tools; not reads, searches or fetches): the reader handler only marks the summary stale (`acpGitNoteSessionUpdate`), and a check follows at most every 2 s;
4. periodically while the window is idle: every 15 s, or every 30 times the duration of the last check if that is longer; after a check timed out (or its output was too large) periodic checks stop until another trigger;
5. explicitly, with `acpGitCheck[nbo]` or `acpGitChanges[nbo, f]` (the review window).

Housekeeping only runs while the pump does (while the window connects, is connected or a turn runs), so a disconnected window is not checked periodically. A check that never finished is given up after 150 s. Updating the summary marks the window dirty; views that show it re-render only when their signature changes (R6). `$acpGitEnabled = False` turns all of this off.

Large working trees: status output is parsed column-wise and untracked files stay paths until they are listed, so a project with 200,000 untracked files costs about 0.3 s of kernel time per check.

**Text from the repository never becomes boxes.** File names, file contents, diff lines, branch names and git's messages can contain the private-use characters of the front end's linear syntax (U+F7C0 to U+F7CD); ToBoxes turns them into backslash escapes in box strings, which the front end parses as boxes chosen by whoever wrote the text (styles that hide or disguise text, or dynamic content that evaluates code when the window is shown). `acpNeutralizeLinearSyntax` (Rendering.wl) replaces them with U+FFFD: `acpGitDecode` applies it to all of git's output and every untracked file, the review window's labels apply it again, and so does `acpDiffView` for every diff line (also the chat's diffs). Untracked files whose names contain these characters can't be read ("The file could not be read.").

**Names are display-safe, also for local folders.** The review window shows every path and name through `acpRemoteDisplayName` (see [Security](#security)): the file list, the card headers, a renamed or copied file's old path, the tooltips ("Renamed from ...", "Open ...", "Show ... in its folder"), a symbolic link's target, the header's folder and its tooltip, the remote header's host, the branch, the git version and the window title. A bidi control or another invisible character therefore shows as `⟦U+XXXX⟧`, so `old<U+202E>txt.exe` can't pass for `oldexe.txt`. Diff lines, the contents of untracked files and git's or ssh's messages (a remote error's advice and ssh's output, a start failure's message) go through `reviewSafeText`. It shows the same way only the bidi controls (U+061C, U+200E, U+200F, U+202A-U+202E, U+2066-U+2069) and the line and paragraph separators (U+2028, U+2029). So a line of code can't look different from what it is (the "Trojan Source" trick), and each diff line stays one row. Tabs, line breaks, carriage returns, zero width joiners and variation selectors are kept, because they are parts of ordinary text such as emoji. A diff is made safe after it is cut to 400 lines of 300 characters (`reviewTruncatedText`): a replacement in megabytes of text would take a second. A marker makes a line longer, so a line that grew past 300 characters is cut again before a marker that would not fit (`reviewCutMarkedLine`), and ends with an ellipsis. Its first 300 characters end with a whole marker or none. The diff view (Rendering.wl) also cuts lines at 300 characters and therefore never shows half a marker. The actions keep the raw values: the Open link's path, and the folder in the window's `TaggingRules` that Refresh lists. `Tests/ACPReview.wlt` covers this in `Review-DisplaySafe-*`. `Review-DisplaySafe-DiffLines` also checks long lines with a bidi control near character 300, a whole marker or none, and the error messages. The window geometry is covered in `Review-Window-*`. `Review-Window-FrontEnd` opens a real window and runs only under a front end, as in CI; without one it gives `Missing["TestSkipped"]`.

**The button** (`acpReviewButton`, at the right end of `acpDirectoryRowView`): only while the summary's status is `"Changes"`, otherwise nothing (no space taken). The directory row's signature includes `acpReviewButtonSignature` (`{FileCount, Added, Deleted}` with changes, else `None`), so checks that find nothing new don't re-render the row; while the button is shown, the folder's label gets less room (its texts are measured in the front end, see [The toolbar](#the-toolbar)). Clicking it runs `ChatbookAction["ACP", "ReviewChanges", nbo]` (`acpReviewChanges`).

**The review window** (`acpReviewChanges`): one per ACP window, found by its `TaggingRules` (`{"ACPReview", "Owner"}` is the ACP window's `NotebookObject`, `{"ACPReview", "Directory"}` the folder it shows), so it is found again after a kernel restart; the button raises an open one and lists the changes again. A new window shows "Loading changes..." right away; A new window gets `reviewWindowGeometry[owner]`. Its size is 760×820 points (`$reviewWindowSize`), clamped to the usable area of the display the ACP window is on. The display is found with ``NotebookTools`NotebookDisplayIndex``, else the first display is used. The usable area is the display's `"Region"` from `CurrentValue["ConnectedDisplays"]` (without taskbars and menu bars), else its `"FullRegion"`. The clamping leaves 16×48 points for the window frame (`$reviewWindowFrame`: borders, title bar; `WindowMargins` include the frame, `WindowSize` does not) and 8 points at each edge (`$reviewScreenGap`), with a minimum of 320×240. The window is centered on that area with a left and a top margin (`reviewPlacement`, pure). It never gets a bottom margin: a window manager that adds the title bar after placing a window would make it taller. Without a front end answer, the window gets 760×820 and the front end's placement. A fixed 760×820 window used to be centered by the front end with its title bar and header above a 750-point-high display. `acpGitChanges` runs in the pump and its continuation replaces the whole notebook with `NotebookPut[acpReviewNotebook[changes, owner, False], review]` (`reviewPut`: the window keeps its size, and the notebook gets the window's current left and top as `WindowMargins -> {{left, Automatic}, {Automatic, top}}`. `NotebookPut` without `WindowMargins` would center the window again, so a window the user moved stays where it is) and scrolls to the top with `FrontEndTokenExecute[review, "ScrollNotebookStart"]` (after `NotebookPut` the window would show the end of the notebook; moving the selection before the first cell would scroll too, but the front end then shows its caret above the file list). Only the result of the window's latest request is shown (`$reviewWindows` holds its token); a new request supersedes the running one (its git command is killed, so clicking Refresh repeatedly does not pile up work), and results for closed windows are dropped. A change set is shown in steps of about 0.15 s, one per pump tick (`reviewStep`): the rows of the file list, then `NotebookPut` of the notebook with the list and the first cards, then the remaining cards in batches, written after the last cell with `NotebookWrite[NotebookLocationSpecifier[cell, "After"], cells, None, AutoScroll -> False]` (which works in the non-editable window and leaves the selection and the scroll position alone); a newer request or a closed window drops the job. For 600 changed files the longest step took about 0.3 s (the whole notebook used to be built and put in one 6-second evaluation). **Refresh** (`ChatbookAction["ACP", "ReviewRefresh", EvaluationNotebook[]]`) shows the loading state in the header and lists the changes of the owner's current project folder, or, when the owner has no window record in this kernel (closed window, kernel restart), of the folder the window shows. The window is not a chat notebook: `Saveable -> False`, `Editable -> False`, the kernel of the ACP window as `Evaluator`, no cell insertion menu and no visible insertion line between cells (`CellInsertionPointCell -> None`, `CellInsertionPointColor` is the background color), no horizontal scroll bar (`WindowElements -> {"VerticalScrollBar", "MagnificationPopUp"}`; long lines wrap), and a private stylesheet (based on `Default.nb`) with the review cell styles and one `TemplateBox` style per file icon used (`"ACPReviewIcon" <> name`), so each icon's boxes are stored once. Colors are `LightDarkSwitched` (the palette of `Rendering.wl`, `acpColor`), so it works in dark mode.

* The docked header: the project folder, a Refresh button, and a status line: the branch ("On branch main", "HEAD detached at 1a2b3c4", "No commits yet"), "N files changed +a −d", and "Updated 14:03" (or "Loading changes..." while a request runs). The folder, local or remote, is kept from its end (at most `$reviewMaxFolderLabel`, 80 characters; the whole path is in the tooltip) and takes the room Refresh leaves: a `Fit` column whose pane draws a folder that is still too wide smaller (`ImageSizeAction -> "ShrinkToFit"`), so a long folder never pushes Refresh out of the window.
* The file list: one row per file (icon, path with the folder part muted, "old → new" for renames and copies, a status badge, "+a −d" spaced like in the cards). Clicking a path scrolls to the file's card with `FrontEnd`NotebookLocate` (run by the front end, no kernel needed); the path is underlined under the mouse and has a "Go to the diff" tooltip. The `Mouseover` is outside the link's buttons (one per pane), whose `Evaluator -> None` would otherwise apply to it. "and N more files" when the change set has more than `$acpGitMaxFiles` files, and notices when git's patch or line counts are incomplete.
* One card per file (cell tag `"ACPReviewFile-" <> i`): a header (opener, icon, path, status, counts) with an **Open** link, and the diff (`acpDiffView` with `"Header" -> False`, `"FullWidth" -> True` and `"LineNumbers" -> True`; untracked text files as new files) or a note: binary, mode change ("from 100644 to 100755"), renamed or copied without changes, empty, submodule commit (with its diff), untracked folder, symbolic link, too large, not read, not a regular file, unreadable, no differences, patch unavailable. Openers are front-end-only `DynamicModule`s (the closed pane only has the header). Cards start open unless the diff has more than 300 lines, the file is binary, or more than 30 files changed (then all start closed).
* Bounds: at most 400 lines of at most 300 characters per diff (with "… n more lines"), and 4 million characters of diff text per window; later files say that there are too many changes to show. The diffs of cards that start open are in the cell; the others are rendered when the card is first opened: the closed pane of a `PaneSelector` is not evaluated, and the open pane holds `Dynamic[ChatbookAction["ACP", "ReviewDiffView", data]]` with the (truncated) diff text, so a window with many or large changes stays small.
* **Open** (`ChatbookAction["ACP", "ReviewOpenFile", path]`, not for deleted files): Wolfram Language files (`.nb`, `.cdf`, `.wl`, `.m`, `.wls`, `.wlt`, `.mt`) open in the front end, documents, images and plain-text formats in their default application (`SystemOpen`), plain folders (e.g. submodules) in the file manager, and anything else (scripts, executables, unknown types, which the system might run) is shown in its folder. Symbolic links are resolved first, so the file that would actually be opened decides. A folder whose name has an extension, or that has `Contents/Info.plist`, is never passed to `SystemOpen` (on macOS, an app bundle such as `Tool.app` would be launched): the nearest plain folder above it is shown instead. The link's tooltip ("Open name" or "Show name in its folder") comes from the same decision (`reviewOpenAction`).

Patches are rendered with `acpPatchRows` (`Transcript.wl`, also used for ACP diffs and `acpDiffStats`): file headers are only recognized before the first hunk and after an `Index:`/`diff --git` line, so a removed line `-- comment` (`--- comment` in the patch) is shown as a removed line.

The review window's diffs use two `acpDiffView` options that the chat's diff views don't: `"FullWidth"` (the frame fills the card, the line column takes the rest of the width with `ItemSize -> Fit`, so the line backgrounds span the card and long lines wrap at its edge) and `"LineNumbers"` (narrow, muted, right-aligned columns with the old and new line numbers, counted from the start lines of the hunk headers `@@ -a,b +c,d @@`, or through the line diff for old and new texts; blank where a side has no line, and a column without any numbers is left out, so new and untracked files only have new numbers and deleted files old ones). Numbering happens before the `"MaxLines"` cap, so lazily rendered and truncated diffs keep their numbers.

**File icons** (`acpFileIcon[path]`, about 16 points): `DefinitionNotebookClient`'s file manager icons (the `"FileManagerIcons"` asset, as used by its `FileTreeCells`; loaded once per session) mapped like its `fileFormat`: Wolfram Language files, `.mx`, `.nb`, `.cdf`, `PacletInfo.wl`, text-like files (`.txt`, `.md`, C sources, `.sh`, and files without an extension), `.js`, `.css`, HTML, XML, SVG and images, and a folder for untracked folders. Other extensions get the same page with the extension (up to 4 characters) written on it in the icons' blue; longer extensions a plain page. The white page is dark gray in dark mode. Without the component (e.g. some Wolfram Engine installations), simple drawn pages and folders are used.

## Sessions

The agent keeps its sessions (OpenCode: in its database, per project folder). The window lists them through its own connection, can show any of them again with its history (restore), start a new session in a folder, and delete sessions. The backend is `Sessions.wl` (store, replay, write job, actions) and `Connection.wl` (the requests); the Sessions window that shows them is a separate notebook beside the ACP window. A remote window lists the sessions of the agent on its host; its folders are never checked on this computer (see [Everything else](#everything-else)).

**Requests.** Like every other request, raw `SendACPRequest`s with `"cb-..."` IDs on the window's connection, continued in the connection-level response handler (request kinds `"SessionList"`, `"SessionLoad"`, `"SessionDelete"`). No second agent process is started for listing, and nothing waits.

**The store** (the window record's `"Sessions"`, `acpSessionsOf[window]` fills in defaults): `"Status"` (`"Idle"`, `"Listing"`, `"Ready"`, `"Error"`, `"Unsupported"`: the agent does not advertise `sessionCapabilities.list`, `"NotConnected"`), `"Items"` (newest first: `<| "SessionID", "Cwd", "Title", "UpdatedAt", "Hidden" |>`; IDs and folders exactly as the agent sent them, titles neutralized), `"ListedAt"`, `"Error"`, `"Stale"` (a listing is wanted), `"RecheckAt"`, `"Open"` (a Sessions window is open), `"Notice"` (delete errors), `"Deleting"` (outstanding deletes: session ID -> the connection they were sent on; housekeeping forgets those of an earlier connection, whose requests a disconnect dropped, so a session can't stay "Deleting..." after a reconnect or an agent crash; the next listing shows whether it was deleted). A listing is `session/list` without `cwd` (all folders), page after page with `nextCursor` until there is no cursor or a page is empty (OpenCode sends a cursor on its last non-empty page too), at most 20 pages (`"SessionListCapped"` in the debug log). The reader handler only stores a page; the next page and the completion are pump steps. Listings happen only while the Sessions window is open (`acpSessionsOpened`/`acpSessionsClosed`): when it opens, on Refresh, when the connection becomes ready, after a turn (and once more 10 s later: OpenCode titles new sessions asynchronously and never says when), and after a restore, a new session or a delete; housekeeping (`"ACPSessions"`) debounces them (one listing at a time). `updatedAt` (ISO 8601 with milliseconds and `Z`) is parsed with `FromDateString`'s automatic format into an `AbsoluteTime`. Sessions that were never used (OpenCode's fallback title `New session - <ISO time of creation>`) and subagent sessions (`Child session - ...`) are hidden, except the window's own (its current, restoring, pending or resumable session). The fallback title alone does not prove that a session was never used (OpenCode keeps it if it could not make a title, e.g. when the title model fails), so a session with that title whose `updatedAt` is more than 10 s after the time in its title is shown (Chatbook's own model and effort setup changes a new session within a fraction of a second; a later model change alone also makes a never-used session appear). `acpSessionsProjects` groups the visible sessions by folder (paths compared without trailing separators), projects ordered by their newest session, the window's folder always included.

**Restore** (`acpRestoreSession[nbo, sessionID, cwd]`, action `"RestoreSession"`): refused while a turn runs, a permission is pending, the window connects or restores (`acpSessionsBusyState`), or if the agent does not advertise `loadSession`; the window's own session is a no-op. The session's listed `cwd` is passed to `session/load` unchanged (OpenCode requires the session's exact directory), with the same MCP servers as `session/new`.

* Same folder, connected: `session/load` on the window's connection; the window is `"Restoring"` (Send queues the prompt, which is sent once the session is written; New, the folder chooser and the config menus are disabled; the status line says "Loading the session..."). The replayed `session/update`s of the loading session go to an accumulator in the window record (`"Restore"`, chunks of 256 updates, at most 20,000 updates or 32 MB, the oldest are dropped), not to a turn. The load response ends the replay: the window's session becomes the loaded one (resumable, also in the notebook's TaggingRules) with the config options of the response (nothing is re-applied: `session/set_config_option` would move the session to the top of the list and switch it away from its own model; the same holds for `session/resume`), the session that was left is closed (`session/close`), and a pump job (`acpRestoreWriteStep`, about 0.15 s per step) starts a new conversation and replaces the transcript with the last 30 turns (a user cell and the final cell each; a note says how many earlier messages are not shown). A turn starts at each user message with a new `messageId`; agent output and tool calls go through the Transcript reducer with synthetic times, so their openers say "Worked" and "Thoughts" instead of durations; tools that failed with OpenCode's text for a declined call show "Declined"; a turn without output says "No reply.". On an error the window keeps its session and transcript and shows the error as a notice. A message that was not sent yet is not sent into the restored session, which is another chat: the queued one and the one whose attachments are being prepared go back to the input field and the draft with the notice, and the message of a prompt notebook that is being prepared is not sent (its status says so), as for a session of another folder (`acpReturnPendingMessages`, also for "Same folder, not connected"). Before, a message that was being prepared went into the restored conversation.
* Another folder: the project folder changes (disconnect, clear, reconnect) with a `"PendingRestore"`, and the new connection sends `session/load` instead of `session/new`; if that fails (error or timeout), the window continues with a new session there and shows the error. A session whose folder no longer exists is not restored (notice).
* Same folder, not connected: the window reconnects with a `"PendingRestore"` (the folder and the transcript stay until the load succeeds) and the new connection sends `session/load` instead of resuming the window's session; if that fails, the window resumes its session (or creates one) and shows the error.
* Config values chosen before the restore (a model change still waiting for its response, or one made while disconnected) belong to the session that is left and are dropped when the load starts; responses to config requests of a session the window has left only record the user's choice as a preference (they don't change the loaded session's options). Values chosen while the session loads are applied to it; once it is loaded (while its turns are written), changes are sent right away.
* While the turns are written, the old transcript stays until the first restored cells are written after it, so the input field (where the user may be typing the next prompt) is not moved; a session without turns clears the transcript at once, like New. When the turns are written, the window scrolls to the top and the selection moves after the last cell (which scrolls just enough to show the last turn above the input field; `"ScrollNotebookEnd"` would leave only the bottom of the last cell at the top of the window), then back into the input field.
* The load times out 60 s after the last replayed update (not after the request: a long replay arrives over many reader ticks) and then fails like an error response. Its request is kept as `"AbandonedLoad"` (for at most 10 minutes), so that a late successful response closes the session the agent attached (`session/close`). Housekeeping finishes a write job that made no progress for 60 s and resets a window that is "Restoring" without a restore.

**New session in a folder** (`acpNewSessionIn[nbo, cwd]`, action `"NewSessionIn"`): New in the window's folder, otherwise a project folder change. Same preconditions as restore.

**Delete** (`acpDeleteSession[nbo, sessionID]`, action `"DeleteSession"`): only if the agent advertises `sessionCapabilities.delete` (also when it can't load sessions), never the window's current, resumable or restoring session; `session/delete` on the window's connection (any ID, also one this connection never listed); the item disappears when the agent confirms and the list is fetched again; an error or a timeout (30 s) becomes the store's `"Notice"`. A listing that times out (30 s per page) sets the store's `"Error"`.

**Kernel restarts and closing.** The store is kernel state: after a kernel restart it starts out empty; the Sessions window (found by its TaggingRules `{"ACPSessions", "Owner"}`) is rebuilt when the ACP window recovers, like the toolbar (`acpSessionsRecover`), and lists once the window is connected. Closing the ACP window closes its Sessions window.

### The Sessions window

**Opening.** The toolbar button "Sessions" after New (`acpSessionsButton`, BoxID `"ACPSessionsButton"`, the Notebook Assistant's History icon and a label, like New and the Notebook Assistant's History button, `acpToolbarButtonLabel`; only the icon in a narrow main row, see [The toolbar](#the-toolbar); tooltip "Browse saved sessions") runs the action `"ToggleSessions"` (`acpToggleSessions`): it closes the open Sessions window of the ACP window, or opens one (`NotebookPut` from the preemptive button) and calls `acpSessionsOpened`. An open Sessions window that other windows hide (more than half of it: a maximized notebook the user clicked into, or the ACP window itself in the `"Overlap"` placement) is placed beside the ACP window again and brought to the front instead (`acpSessionsCoveredQ`, pure, decides from the windows in front of it: `Notebooks[]` lists the windows front to back, which is trusted only if the ACP window, whose button was just clicked, is the first visible non-palette window; otherwise the button closes the window). Closing it (toolbar or close box: its `"WindowClose"` event runs `"SessionsClosed"`) stops the listings. There is one Sessions window per ACP window.

**Placement** (`acpSessionsPlacement[owner, {xmin, xmax}, width]`, pure; `acpSessionsGeometry[owner]` reads the ACP window's resolved `WindowMargins`, `WindowSize`, `Magnification` and its display's `"FullRegion"` the way `attachToLeft` does): the window gets the ACP window's top margin and height (`WindowSize`; both windows have the same kind of frame; copying the bottom margin instead made it taller on Linux, where the window manager adds the title bar of a new window after placing it) and a width of 300 points (375 on macOS) scaled by the ACP window's magnification, and goes left of the ACP window if that fits on its display (`"Left"`); otherwise, if the display is wide enough for both, at the display's left edge with the ACP window moved right just enough (`"SlideOwner"`, what a real sidebar does: the ACP window usually sits at the display's left edge); otherwise at the left edge over the ACP window (`"Overlap"`). The windows touch: the width of the frame's side borders (what the ACP window's horizontal margins and width leave of its display, if that is 0 to 24 points; `WindowMargins` include the frame, `WindowSize` does not) is added to the offsets. An unknown display is assumed to end at the ACP window's right edge, so the ACP window is never moved off it. The window is placed when it opens and does not follow later moves (there is no move event; following would mean polling the front end).

**The notebook** (`acpSessionsNotebook[owner, geometry]`, pure): one content cell; `Deployed -> True`, `Editable`, `Selectable`, `Saveable`, `ClosingAutoSave` and the save dialog off, no cell brackets or insertion point, `WindowToolbars -> {}`, a vertical scroll bar and a magnification menu (`WindowElements -> {"VerticalScrollBar", "MagnificationPopUp"}`), `StyleDefinitions -> "Default.nb"`, the ACP window's kernel (`Evaluator`), magnification (when it opens; the menu changes it later) and background (`NA_NotebookBackground`, light and dark), `WindowTitle` "Sessions", and TaggingRules `"ACPSessions" -> <|"Owner" -> acpWindow|>` plus `"ChatNotebookSettings" -> <|"ExcludeFromChat" -> True|>` (otherwise the Notebook Assistant would read it as a user notebook and `ShowNotebookAssistance[..., "ACPWindow"]` could attach the ACP window to it; being deployed, the Notebook Assistant sidebar never opens in it). Escape cancels a delete confirmation. The review window ("Review changes") got the same `Deployed -> True` and `ExcludeFromChat` (its cells set `Deployed -> False`, so their text stays selectable).

**The content cell** (`acpSessionsCell[owner]`) is one self-contained cell, so that it can become the content of a front end sidebar panel later: no style name, every option inline (fonts, colors, margins, `Deployed`), no private stylesheet, icons inline (`acpFileIcon`, drawn icons) or from Chatbook's `ChatbookExpressions` front end resources, the owner in the cell's own TaggingRules, cell tag `"ACPSessions"` (`acpSessionsRebuildWindow` writes a fresh cell over it after a kernel restart). Its view is a derived view like the toolbar's: a watcher `Dynamic` tracks the window symbol and bumps the view's symbol (`acpEntitySymbol[acpWindowKey[owner], "Sessions"]`) only when `sessionsViewSignature` changes (listing steps that change nothing visible, turn updates and usage don't re-render it, so hover states and clicks survive a streaming turn); both `Dynamic`s load Chatbook first, since after a kernel restart they may be evaluated before anything else loaded it. The view (`sessionsContent[owner, window, now]`, pure apart from `DirectoryQ` on the listed folders of a local window):

* Header: "Sessions", the agent's name (muted) and a Refresh button (`"SessionsRefresh"`); a status line when needed: "Loading sessions..." (nothing listed yet), the listing error, "Choose a project folder to see sessions" (no project folder), "Sessions are listed when OpenCode is connected", "OpenCode can't list sessions"; the notice of a failed delete (dismissable).
* Projects (`acpSessionsProjects`): chevron, folder icon, folder name (the window's project in the accent color), the number of sessions; the full path (home abbreviated) in the tooltip. The window's project is open, the others closed (the first one if the window has no project); what the user opens or closes is kept in the store (`"Expanded"`), so re-renders don't reset it. On hover: "+" (new session in this folder, `"SessionsNew"`) and open folder (`"SessionsOpenFolder"`, Review.wl's `acpReviewOpenFile`, which never launches an application bundle). A folder that no longer exists is muted and both are disabled.
* Sessions (indented under the folder name): the title in one line (shortened to 40 characters with an ellipsis and clipped, the whole title in the tooltip; "Untitled session" without a title), and the time since the last update, muted on the right (`acpShortRelativeTime`: "now", "3m", "2h", "5d", then "Mar 4", or "2025-12-01" in another year; the date in the tooltip). The store's `"Minute"` is part of the signature, so the times are refreshed every minute while the window is open (and the pump runs). The window's own session (or the one being restored, with "Loading...") is highlighted (tint and an accent bar) and has no actions. On hover, other sessions are highlighted like the Notebook Assistant's History rows and the trash button replaces the time (only if the agent can delete and the window is connected); clicking the title restores the session (`"SessionsOpen"`; the ACP window then gets the focus). An open project shows its newest 25 sessions (and the window's own session wherever it is) and "Show 25 more" (`"SessionsShowMore"`, store key `"Shown"`): rendering hundreds of rows takes seconds (about 0.15 s with the limit, whatever the number of sessions).
* Delete asks inline: the row becomes "Delete this session?" with Delete and Cancel (`"SessionsConfirmDelete"`, store key `"ConfirmDelete"`); Cancel is where the trash button was, so a double click on the trash cancels, and Delete (`"SessionsDelete"`) only works 0.4 s after the confirmation appeared (like the permission buttons). Escape or Cancel (`"SessionsCancelDelete"`) restores the row; a session being deleted shows "Deleting...".
* While the ACP window is busy (a turn runs, an approval is pending, it connects or restores), sessions can't be opened or deleted and "+" is disabled; the rows are muted and the tooltip says why ("Wait for the current turn to finish", ...). Without `loadSession` the rows are muted, the tooltip says that the agent can't open saved sessions, and the trash button still appears on hover if the agent can delete them.
* "Show 25 more" counts the sessions the next page adds (the window's own session, shown wherever it is, is not counted again).

The window's buttons pass a key (`sessionsKey`, a hash of the session ID or folder) instead of the agent's strings, and the actions (`acpSessionsWindowAction`) look it up in the store, so no text from the agent is ever part of button code; IDs and folders still reach `acpRestoreSession`, `acpNewSessionIn`, `acpDeleteSession` and `acpReviewOpenFile` unchanged. Every action first runs `acpCheckSession` (a click after a kernel restart recovers the ACP window).

**A real sidebar (FE 15.1).** The Sessions window is a separate window because the front end's sidebars only know two panels: the front end binary maps the PanelID of `FrontEndTokenExecute[nbo, "SwitchSidebar", <|"PanelID" -> id, "PreferredSize" -> w|>]` to its content, and it knows only `"NotebookAssistant"` (`ChatbookExpressions` resource `"NotebookAssistantSidebarCell"`) and `"NotebookProperties"` (`NotebookToolbarExpressions` resource `"NotebookPropertiesSidebarCell"`); `FE`toggleSidebar` in the front end's `GetFEKernelInit.tr` is only the toolbar's toggle for these two. What the front end would need: a PanelID such as `"ACPSessions"` whose content is a `ChatbookExpressions` front end resource (e.g. `"ACPSessionsSidebarCell"`, like `"NotebookAssistant`Sidebar`NotebookAssistantSidebarCell"` for the Notebook Assistant) that asks the kernel for `acpSessionsCell[acpWindow]` (an action for that, e.g. `ChatbookAction["ACP", "SessionsCell", EvaluationNotebook[]]`, is not registered yet), and a way to show the panel on the left of the window. The cell is mostly ready for that: its look depends on nothing but its own options and Chatbook's resources, and its owner is the ACP window the sidebar would belong to; the toolbar button would then switch the panel instead of opening a window. Two things come from the Sessions window, not from the cell, and a sidebar would have to provide them: the listing lifecycle (`acpSessionsOpened` when the panel is shown and `acpSessionsClosed` when it is hidden: without `"Open"` there are no automatic listings or minute refreshes, only Refresh lists) and Escape cancelling a delete confirmation (the window's `NotebookEventActions`; the cell's content is not selectable, so a cell-level key handler would not get the key).

## Attachments

A message can have attachments: open notebooks and files of this computer, several per message. The "+" at the left of the input field (`acpAttachButton`, BoxID `"ACPAttachButton"`, the Notebook Assistant's Sources icon) opens a menu that is built when it is clicked: the open notebooks that the [notebook tools](#notebook-tools) would list, front to back (those in the draft are checked and disabled; at most 15, then "and n more"), and "File..." ("File on this computer..." in a remote window), the front end's file dialog (a `FileNameSetter` with `"OpenList"`, run by the front end, never a dialog from a preemptive evaluation; several files at once). The menu is a cell attached to the button (`AttachCell` of `EvaluationBox[]`, removed by a click outside it), above the input field, or below it when the window is empty. Its notebook buttons pass the key of an entry of the menu (`$attachMenuEntries`), never a title.

**The draft** is the window record's `"Attachments"`: references, never content (`<| "Kind" -> "Notebook", "Key", "Notebook" -> nbo, "Name" -> its file's name or window title, "Cells" |>` or `<| "Kind" -> "File", "Key", "Path", "Name", "Size" |>`; keys are hashes), mirrored in the TaggingRules (`{"ACP", "Attachments"}`, R8). It belongs to one message. The chips above the input field (`acpAttachmentsArea`, a derived view, R6) show each attachment's icon (the front end's notebook icon, or the review window's icon for a file's extension), its display-safe name (`acpRemoteDisplayName`, shortened to 32 characters) and its kind and size in the tooltip (and its path); "x" removes it (`"RemoveAttachment"`), and a click on a notebook's chip raises the notebook (`"ShowAttachment"`). Their buttons pass keys only.

**Send** (`evaluateACPChat`) with a draft works also without typed text. It takes the input and the draft at once (`acpPrepareMessage`): the window record's `"Preparing"` (`<| "Token", "StartedAt", "Input", "Text", "Attachments" |>`), its copy in the TaggingRules (`{"ACP", "PreparingPrompt"}`), Busy (Stop instead of Send, so there is no second send), a note above the input field ("Preparing 2 attachments..."), and a main link job (`acpMainLinkRun` of MCP.wl, R3) that prepares the attachments: `acpPrepareAttachmentsJob`. Converting notebooks (CellToString takes about a second per megabyte of boxes) and rasterizing graphics make front end calls and can take seconds, which no preemptive evaluation may do (R1); the job waits behind the user's own evaluations, like the tools. Another Send while a message is prepared keeps its text in the input field with a notice. The job checks before each cell that its preparation is still the window's, and gives its result to the pump (`acpSchedule` of `acpPreparedPrompt`), which claims the preparation and starts the turn, or queues the message while a turn runs or a session loads, like a message without attachments (and behind a queued message sent before it, see "Click order" below); a failure gives the message back (its text before what was typed since, its attachments into the draft) with the failure's notice. Stop (when no turn runs), New, a folder or host change, a restored session and housekeeping (after 180 s, `$acpPrepareTimeout`) cancel a preparation the same way; the job's result is then dropped. A job whose window was closed meanwhile creates no window record (its result is not claimed). A turn that ends while a message is prepared leaves the window busy (`acpFinishTurnState`), so Stop stays. An abort (Alt+.) of the job hands over a failure.

**What is prepared** (`acpPrepareAttachments`, also for a [prompt notebook](#prompt-notebook)'s message; the prepared attachments are the turn record's `"Attachments"`):

* An open notebook: its cells, as the front end writes the notebook's text (see "Reading notebooks" below), converted to markdown by NotebookTools.wl's `acpNotebookMarkdown`, ReadNotebook's conversion with other limits: no `<cell>` blocks, ids, labels or selection markers, no cut per cell, output cells cut at 5,000 characters, cells with more than 4 MB of boxes left out with a note; when the message's characters run out, the last cells are left out (a first cell with text is cut), with notes that say so. A notebook that was closed meanwhile fails the preparation.
* Its graphics (`GraphicsBox`, `Graphics3DBox`) are rasterized by the front end (144 dpi; `displayBoxes`, below) and sent as images, "[image n]" in the text (n counts the images of the whole message), if the agent may accept images (`acpPromptCapabilities`: its `promptCapabilities.image`, or not known yet); beyond the message's images, and without a front end (Rasterize would start one in a kernel's pump), they are "[graphics]", as ReadNotebook reads them. Images count against the message's cap while they are made: once the images and the text so far fill it, the rest are "[graphics]", and when the notebook's text is done, images from the last one on are dropped (their "[image n]" becomes "[graphics]") until the message fits, with a note for the agent (`fittedImages`). An image whose cell was left out or cut is not sent, and the images are numbered without gaps.
* A file: a regular file (never a device or pipe) within the size cap, read once. `.nb` and `.cdf` files (up to 64 MB, `$maxNotebookBytes`, the cap of open notebooks too: only their text and some graphics go into the message) are read like open notebooks (see "Reading notebooks"). Image files (PNG, JPEG, GIF, BMP, WebP and TIFF by their signature) are images, refused if the agent does not accept images. Text files (UTF-8, no NUL in the first 8000 bytes, at most 30% control characters; a byte order mark is dropped, line ends become `\n`) are their text. Other files are refused (an agent gets nothing from them: OpenCode drops binary files that it can't show).
* Every image is decoded and encoded again (`acpReencodeImage`, `acpEncodeImage`): at most 1568 pixels on its longer side, as PNG, or as JPEG when the PNG is larger than the cap, made smaller until it fits. An image block that the agent can't decode fails the whole prompt at the agent (OpenCode: "Image could not be decoded"), so a file that can't be decoded fails the preparation instead.
* Caps (`$acpAttachmentLimits`), far below OpenCode's (20 MiB per attachment, 32 MiB per ACP message, which ends the connection), counting the UTF-8 of the text and the base64 of the images (4/3): local windows 8 MB per message, 600,000 characters of attachments' text (a notebook or file beyond it is cut with a note), 8 MB per file, 10 images of at most 3 MB; remote windows (ACPLink writes a message with one write, over ssh) 2 MB, 300,000 characters, 2 MB, 4 images of at most 1 MB. A message over its cap is refused with a notice.

**Reading notebooks** (Attachments.wl's `notebookTextCells`). An attached notebook may come from anywhere (a notebook the user opened, a file of a download folder), and its boxes can hold any expression: in options, interpretations, dynamic content, or in place of boxes. Nothing in it is evaluated:

* `NotebookRead` (and `NotebookGet`) would hand the kernel an open notebook's cells as an expression, which the kernel evaluates (a crafted cell runs code then). So the front end writes an open notebook (unsaved changes included) as the text of a notebook file (`` FrontEnd`ExportPacket[nbo, "NotebookString"] ``), which is read like a notebook file.
* The text is parsed held (`inertHeld`, a `HoldAllComplete` head), and only if it has no linear syntax (`\!`, `\(`, `\*`, or their characters U+F7C0-U+F7CD) outside its strings and comments: the parser interprets such boxes, which runs code (a TemplateBox's `InterpretationFunction` runs although the result is held); the front end never writes that. Strings and comments are found with one regular expression in linear time (an unclosed one ends with the text). The text must be comments and one `Notebook` expression (a front end's file is `Null`s for its comments and the `Notebook`); its new symbols go to a context of their own, which is removed afterwards.
* Every symbol of the held cells that is not inert (`$inertSymbols`: cells and their structure, the heads of boxes (an explicit list, `$inertBoxNames`), the options of boxes, cells and graphics (the kernel's `Options`) and the values of options and graphics directives; no arithmetic, no evaluation functions) becomes `inertSymbol["context`name"]` (`inertCells`, which compares symbols by name without evaluating them), `CompressedData[...]` becomes `inertCompressed[...]` and `NCache[exact, number]` its number. Only then are the cells evaluated, within 30 s and 1 GB. So nothing that is in them can run: not their evaluation, not their conversion (CellToString evaluates the interpretations of some boxes), not the front end when it rasterizes their graphics.
* `acpDefusedCells` (NotebookTools.wl, shared with ReadNotebook): CellToString parses and evaluates some strings, so linear syntax in strings is replaced with U+FFFD (`acpNeutralizeLinearSyntax`), and so is a `\!` typed as two characters (it evaluates a string literal with it); an inline WL code template (`ChatbookWLTemplate`, whose code CellToString runs) is its code; videos and audio are "[video]" and "[audio]" (it imports them); a raw data cell is its text; a TemplateBox's inline `InterpretationFunction` and `DisplayFunction` are dropped (a crafted one runs when the box is interpreted; a normal kernel box carries neither). The rules are applied until nothing changes, so a construct nested in what another rule returns (a template whose input is a template, a video box in a template's input) is defused too.
* `displayBoxes`: the graphics that are rasterized get their compressed data decompressed (`Uncompress[s, inertHeld]` within 256 MB, `$maxDecompressedBytes`: a short text can decompress to gigabytes; the data made inert like the cells, arrays such as `NumericArray[...]` made since graphics boxes hold their arguments), lose what makes them interactive (dynamic content: a list in a `DynamicBox`, such as a bar's mouse-over style and the bar, keeps its primitives; interpretations, tags, tooltips), options with inert values and inert primitives. Graphics with anything inert left elsewhere are "[graphics]" (the front end would draw an error).
* What this costs: outputs that the kernel's code formats (a `Dataset`, a `Manipulate`) are read as their boxes are (e.g. `DynamicModule[«6»]`), and strings with linear syntax show its characters as U+FFFD. Reading a 21 MB notebook (an image of 1200×1200 pixels and a plot) took 5 s, most of it the rasterizing.

**The prompt** (`acpPromptBlocks`, pure, used by `acpSendPrompt`): a message without attachments is exactly the one text block it always was. With attachments the text block is the typed text, then one block per attachment, then the images as image blocks (`mimeType`, base64 `data`), in the order of their numbers. The text block comes first: OpenCode's slash commands and the mock agent's scenario selection read it.

```
Review these

<attachment type="notebook" name="Spec.nb">
# Spec
...
</attachment>

<attachment type="file" name="data.csv" path="/home/u/data.csv">
a,b
...
</attachment>
```

The path is only given in a local window (a remote agent can't read this computer's files). Attribute values are escaped (`&amp;`, `&quot;`, `&lt;`, `&gt;`, line breaks as spaces), and `<attachment` and `</attachment` (any case) in the content and in the typed text are made inert (`acpInertAttachmentTags`: `<` as `&lt;`, with one more `amp;` for text that already looks like that escape, reversed exactly by `acpUninertAttachmentTags`), so nothing closes a block early or passes for one. An agent that does not accept images gets no image blocks, and a note says that the placeholders stand for images that were not sent.

**The queue.** The messages sent while a turn runs are a list in `"QueuedPrompt"`, in the order of their Send clicks: `<| "Text", "Attachments", "At" |>` (`acpQueuePrompt`; a String or one `<| "Text", "Attachments" |>` is read as one message; a prompt notebook's new message replaces its queued one, `acpReplacedPromptAttachments`). They are sent after the turn as one message (`acpSendQueuedPrompt`): texts joined with a blank line, attachments appended, the images numbered again (`acpRenumberImages`, since each message numbers its own from 1). But only as many of them are merged as stay within the caps of one message of the window (`queuedBatch` with Attachments.wl's `acpMessageSize` and `acpMessageFitsQ`: bytes, images and the attachments' characters, as for one message's attachments; at least one message), and the others are sent as the next turns, in order: each message was checked against the caps when it was prepared, but merged they could exceed them (a remote window's 2 MB, or OpenCode's 32 MiB, which ends the connection). The note above the input field shows them as one ("+2 attachments"), and Cancel gives them all back (the text before what was typed since, the attachments into the draft).

**Click order.** A window's messages go in the order of their Send clicks, also when the attachments of one are prepared while another is sent: a message is queued while a turn runs or a session loads, and also behind a message that was sent before it and still waits, prepared or queued. The input field's prepared message (`acpPreparedPrompt`, sent at its `"Preparing"`'s `"StartedAt"`) goes behind a queued message sent before it; a prompt notebook's (`acpSendPreparedMessage`, sent at its job's `"StartedAt"`) goes behind those and behind the input field's message if that one was sent before it and is still being prepared (that one's turn starts first, and the queue follows it); typed text goes behind any queued message (e.g. one that waits for the connection). A queue that waits while no turn runs is sent when the window is ready (a window that lost its connection connects again, `acpKickQueue`), but never ahead of a message that was sent before it and is still being prepared (`queuedBatch`). Main link jobs run in order, so the preparations usually finish in click order; before, a prompt notebook's message whose preparation finished first was sent ahead of an input field message sent before it. Its text and the references of its attachments are also in the TaggingRules (`{"ACP", "QueuedPrompt"}`, `acpPersistQueuedPrompt`): after a kernel restart, `acpRebuildWindowRecord` puts a queued message and one that was prepared back into the input field and the draft, with a notice (before, a queued prompt was lost although the input was cleared). A folder change, a host switch or a restored session (also one of the same folder), which switch the window to another chat, give the queued messages and the one that is being prepared back the same way, with a notice ("The chat changed, so the message ... is back in the input field.", `acpReturnPendingMessages`; before, the reset dropped the queued message). Only typed text leaves the input field when it is queued: a prepared message (with attachments, or a prompt notebook's) left it before, or never was in it, so the input field, where the next message may be typed meanwhile, is not touched.

**The user cell** (`acpUserCellExpr`): the typed text and a row of static chips (icon, display-safe name, tooltip with kind and size; inline options, front end resources and built-in boxes only, no kernel symbols or buttons, so a copied or saved cell renders anywhere). A `TagBox` around the chips has `"CellToStringData"` in its TaggingRules ("[Attached notebook: Spec.nb]", one line per attachment), so a chat converted from the window, and its text, name the attachments.

**Restored sessions.** OpenCode replays a message's text in full and its images as image chunks. The replay (`acpReplayTurn`, Sessions.wl) parses the `<attachment ...>` blocks out of the text (`acpParseAttachmentBlocks`: blocks at the start of the text or after a blank line, names and paths unescaped), drops the image chunks of such a message (they are its attachments' images), and shows the attachments as chips (names and paths display-safe). Other content blocks (a session made in OpenCode's own interface) are chips too, named by `name`, `filename` or the last part of a URI (percent-decoded); text chunks with an `annotations.audience` (OpenCode's synthetic parts, such as embedded context for the model) are not the user's text.

**Prompt notebooks** ([Prompt notebook](#prompt-notebook)) are never sources: a notebook whose `"ChatNotebookSettings"` have `"ACPPromptNotebook" -> True` has the exclusion reason `"ACPPromptNotebook"` (`$exclusionTests`, ChatModes/Context.wl), which is not "Usable" (unlike `"Excluded"`): the notebook tools, the attach menu and the Notebook Assistant's Sources overlay never list it, also after the Notebook Assistant's inclusion toggle.

Tests: `Tests/ACPTranscript.wlt` ("Prompt Blocks": no attachments, order, capabilities, local and remote, escaping, the inert tags, caps, the images' share of the cap and their numbers (`ACPTranscript-PromptBlocks-ImageBudget`, `-RenumberImages`), image re-encoding, text files), `Tests/ACPConnection.wlt` (`Prompt-AttachmentBlocks`, `Prompt-QueuedAttachments`: the blocks the mock agent gets), `Tests/ACPSessions.wlt` (`ReplayTurn-AttachmentChips`, `ReplayTurn-ContentBlockChips`), `Tests/ACPWindow.wlt` (`Attachments-*` (also `Attachments-PreparedClosedWindow`: no record for a closed window), `QueuedPrompt-MessageCaps` (merged only within the caps, the rest as the next turns), `EvaluateACPChat-QueueBehindWaiting`, `PromptNotebook-ClickOrder` (two preparations finishing in either order), `InputCell-Attachments`, `InputArea-AttachmentChips`, `EnsureWindowRecord-RebuildDraft`, `EnsureWindowRecord-RebuildPendingPrompts`), `Tests/ACPSessions.wlt` (`Restore-SameFolderReturnsPending`), `Tests/ACPRendering.wlt` (`ACPRendering-UserCell-*`), `Tests/ACPNotebookTools.wlt` (`ACPNotebookTools-PromptMarkdown`, `ACPNotebookTools-NotebookTextCells` and `ACPNotebookTools-DisplayBoxes`: crafted notebooks run nothing, `ACPNotebookTools-PromptNotebookExcluded`, and with a front end `ACPNotebookTools-PrepareAttachments` and `ACPNotebookTools-PrepareAttachments-Safe`: a file the front end saved, a crafted file and an open notebook opened from one) and `Tests/ACPMCP.wlt` (`ACPMCP-Queue-MainLinkJobs`).

## Prompt notebook

For a long message (a spec, say), the button next to Send (`acpPromptNotebookButton`, BoxID `"ACPPromptNotebookButton"`, the Notebook Assistant's "open as a separate window" icon, action `"OpenPromptNotebook"`) opens a prompt notebook: a regular notebook, with all of the front end's editing, whose docked cell sends it (`PromptNotebook.wl`). Sending it is sending a message whose only content is this notebook as an [attachment](#attachments).

**Opening** (`acpOpenPromptNotebook`, preemptive): one prompt notebook per ACP window, found by its TaggingRules (`acpPromptNotebookOf`); if one is open, the button raises it. Otherwise a new one (`acpPromptNotebook`, pure apart from the owner's kernel) gets the input field's text, which leaves the input field (`acpPromptNotebookCells`: a string as one `"Text"` cell per paragraph, typed boxes as one `"Text"` cell like the user cell's; the draft's attachments stay), and is placed beside the ACP window (`acpPromptNotebookPlacement`, pure, with Sessions.wl's `acpOwnerGeometry`: right of it if the display has room for at least 360 points there, else left of it, else where the front end puts it; at most 720 points wide, with the ACP window's top and height). It is the user's notebook: editable and saveable (the usual save dialog), `"Default.nb"`, the user's default magnification, new cells in the `"Text"` style (`DefaultNewCellStyle`), the ACP window's kernel as its `Evaluator` (its buttons run there), never closed by the ACP window (also not when that is closed), and unchanged by sending.

**Its TaggingRules**: `"ACPPrompt" -> <| "Owner" -> the ACP window, "State", "StatusText" |>` (written by the kernel) and `"ChatNotebookSettings" -> <| "ACPPromptNotebook" -> True, "ExcludeFromChat" -> True |>`, so it is never a source notebook (see [Attachments](#attachments)): the agent's notebook tools, the attach menu and the Notebook Assistant's Sources never list it, also after its `"ExcludeFromChat"` is reset.

**The docked cell** (`acpPromptDockedCell`, pure) is self-contained, since the notebook may be saved and opened anywhere: inline options, built-in boxes, the front end's notebook icon and Chatbook's resources, front-end-only Dynamics, and ChatbookAction buttons that load Chatbook first and pass the click's `EvaluationNotebook[]` (a saved notebook opened later is another `NotebookObject`). So it keeps working after a kernel restart, and in a saved notebook. It shows:

* "Prompt notebook" and the target, where Send goes: the owner's `{"ACP", "PromptTarget"}` ("OpenCode · ~/projects/app", "OpenCode · host:~/projects/app", "OpenCode · no project folder": `acpPromptTargetLabel`, display-safe, the folder's end kept), which the ACP window keeps in its own TaggingRules whenever its title is updated (`acpSyncPromptTarget`, called by `acpUpdateWindowTitle`: a new window, a folder change, a host switch, a session restored from another folder, housekeeping; written only when it changed). The front end reads it alone, through the stored owner (`CurrentValue[CurrentValue[EvaluationNotebook[], {TaggingRules, "ACPPrompt", "Owner"}], {TaggingRules, "ACP", "PromptTarget"}]`), so it follows the window at once. A notebook whose owner is gone (it was closed, or the notebook was saved and opened in a later front end session; a closed notebook's `CurrentValue` is `$Failed`, tested with `` FEPrivate`MatchQ ``) shows "Not linked to an agent window" and "Open agent window" (`"PromptNotebookOpenWindow"`: `showACPWindow` with the notebook as its source, as `ShowNotebookAssistance[pop, "ACPWindow"]` would do it: the open window or a new one, beside the notebook; the notebook is linked to it). Nothing makes the docked cell's Dynamics update when the owner closes (they read only TaggingRules), so closing the ACP window unlinks its prompt notebooks (`acpPromptNotebooksOwnerClosed` sets their `"Owner"` to `None`): their docked cells then say at once that they are not linked, without the owner's busy note (they kept the old target and "OpenCode is working" before). "Open agent window" is a queued button, the others are preemptive: it is the button of a notebook that is not linked, e.g. a saved one opened when no kernel runs, where a preemptive click only started the kernel and the window opened at the second click.
* Send (`"PromptNotebookSend"`).
* The status line: `{"ACPPrompt", "StatusText"}` (with Cancel, `"PromptNotebookCancel"`, while it is "Preparing"), and while the owner is busy (its `{"ACP", "Busy"}`, which the input field's Send/Stop button reads too) "OpenCode is working: Send queues the message." (not while this message is queued). Every Dynamic of the docked cell is front-end evaluable: `CurrentValue`, `FEPrivate`If`, `FEPrivate`SameQ`, `FEPrivate`MatchQ` and `TrueQ` (checked in a headless front end with these blocked in the kernel, `` MathLink`CallFrontEnd[FrontEnd`Value[...]] ``: the front end evaluates `TrueQ` itself, not `StringQ`, say), and a closed owner's `CurrentValue` is `$Failed`, so its busy note goes away and its target shows "Not linked to an agent window".

**Send** (`acpPromptNotebookSend`, preemptive): the owner is the stored ACP window while that is open (`acpWindowQ`). A notebook that is not linked is linked to the open ACP window (`findCurrentWorkspaceChat["ACP"]`) and asks for another click ("This notebook now goes to OpenCode · ~/proj. Click Send again to send it there."), since its docked cell showed no target: a message never goes anywhere that the docked cell did not show. Without an ACP window it says "Not sent. No agent window is open."; a window without a project folder or with an error sends nothing either ("Not sent. Choose a project folder first."). One message of a notebook is prepared at a time (`$promptJobs`, which also keeps the target that the docked cell showed). A main link job (`acpMainLinkRun`, R3; `acpPromptNotebookJob`) prepares the message like an attached notebook: `acpPrepareAttachments` with the owner's caps and capabilities (markdown, graphics as images), the notebook named as in the attach menu (`acpNotebookAttachmentRef`: its file's name, else its window title, such as "Untitled-3"); the snapshot is the notebook when the job runs, which is at once unless the user's own evaluation holds the main link. The pump gets the result (`acpPromptNotebookPrepared`, claimed by the job's token): an empty notebook, a failure (with its notice), a window that was closed meanwhile or whose target is no longer the one the job kept (another folder or host) send nothing; otherwise `acpSendPreparedMessage` (UI.wl) starts the turn, or queues the message while a turn runs or a session loads, as for a message of the input field, and also behind messages that were sent before it and still wait (see [Attachments](#attachments), "Click order"): the docked cell's "Send queues the message" holds while the input field's message is being prepared too. The prompt is the notebook's `<attachment type="notebook" name="...">` block, with its images. The user cell, with the notebook's chip, is written after the last cell (an addressed write, `acpWriteUserCellAddressed`, never `writeWorkspaceChatInputCell`), so the input field is never cleared or moved, and the window is not "Preparing": the next message can be typed and sent meanwhile. A message that is being prepared when the window switches to another chat (New, a folder change, a host switch, a restored session) is not sent: `acpCancelPromptNotebookJobs` drops its job. Send while the notebook's message is queued queues the new version in its place (`acpReplacedPromptAttachments`), so the agent never gets the notebook twice in one message; if the new version is cancelled or fails, the queued one stays (and its status says "Queued").

**Status** (`setPromptStatus`): "Preparing the message...", "Queued: sent when OpenCode is done.", "Sent at 14:03.", or "Not sent." with the reason: Cancel; the queued message was removed (with its Cancel in the ACP window; a prompt notebook's message never goes into the draft); the agent window switched to another chat (New, a folder change, a host switch or a restored session, for a queued message and one that is being prepared); preparing the message took too long (housekeeping, 180 s, `acpPromptNotebookHousekeeping`); the kernel was restarted (the queued message of a rebuilt window record, `restorePendingPrompts`, and a message that was prepared, `acpPromptNotebookRecover`, which `acpRefreshWindowUI` schedules); the agent window was closed (`acpPromptNotebooksOwnerClosed`); the preparation's notice. UI.wl sets "Sent" and "Queued" whenever it starts or queues a message with a prompt notebook's reference (`"Prompt" -> True`; `acpNotePromptNotebooks`), so a queued message says "Sent" once it went out after the turn. While a new message of the notebook is being prepared (Send again while its message was queued), what happens to the message from before (sent after the turn, or removed with Cancel in the ACP window) does not replace "Preparing" and its Cancel: it is kept in the job (`"Earlier"`), the new message's result sets the status, and if the new one is not sent, a message from before that was sent says "Sent at ..." again (`promptNotSent`). Before, the status said "Sent" or "Not sent" while the new message was still being prepared, and Cancel was gone.

**Sending again**: the notebook stays open and unchanged. Send again is a follow-up in the same session (the agent sees both versions); after New it is the first message of a new session. ACP has no way to edit or take back a message (see [Known limitations](#known-limitations)).

Tests: `Tests/ACPWindow.wlt` (`PromptNotebook-*`: the notebook and its docked cell (self-contained, registered actions), cells and placement, the target, opening and raising, Send, the job's result (sent with the chip after the last cell, queued, ignored, not sent), the status of messages that were dropped, a new chat (`PromptNotebook-NewChat`, `PromptNotebook-FolderChange`), Send again while queued (`PromptNotebook-QueuedAgain`), the status while a new message is being prepared (`PromptNotebook-StatusWhilePreparing`), the click order (`PromptNotebook-ClickOrder`), a closed owner unlinks its notebooks (`PromptNotebook-OwnerClosedUnlinks`), the queued "Open agent window" (`PromptNotebook-OpenWindowQueued`); `InputCell-PromptNotebookButton`, `UIStrings-Coverage-PromptNotebook`, the dispatch table), `Tests/ACPNotebookTools.wlt` (`ACPNotebookTools-PromptNotebookNeverListed`, with a front end: a real prompt notebook is never listed, also after its `"ExcludeFromChat"` is reset, and its conversion) and `Tests/ACPConnection.wlt` (`Prompt-PromptNotebook`: through the mock agent, sent at once and queued behind a turn, the input field untouched).

## Notebook tools

`acpNotebookTools[]` (`NotebookTools.wl`) gives six `LLMTool`s that let an agent read and edit the notebooks that are open in the user's front end, unsaved changes included, for the [MCP server](#mcp-server) that runs in the front end's kernel (AgentTools turns them into MCP tools; an in-memory `MCPServerObject[<| "Name" -> ..., "Location" -> None, "LLMEvaluator" -> <| "Tools" -> acpNotebookTools[] |> |>]` gives valid tool schemas). A tool's function takes the arguments as an Association (what `LLMTool` passes it, with `Missing["NoInput"]` for optional parameters that were not given; the functions can also be called directly) and gives a string: JSON for the tools that list or change things (an agent in OpenCode's Code Mode gets it parsed), markdown for ReadNotebook. An error is a `Failure["NotebookToolError", ...]` whose `"String"` is the error text for the agent; AgentTools sends it as the tool result's text with `isError`.

| Tool | Parameters | Result |
|---|---|---|
| ListNotebooks | none | JSON array, front to back: `{"id", "title", "file" (null if never saved), "modified", "cells", "selected"}`; `"selected"` is true for the first one, the notebook the user is working in. Without a front end: `[]` |
| ReadNotebook | `"notebook"`; `"offset"` (first cell, default 1), `"limit"` (cells, default 100) | markdown (below) |
| CreateNotebook | `"markdown"` | JSON `{"id", "title", "cells"}`: a new, unsaved notebook, opened in the front end |
| InsertCells | `"notebook"`, `"markdown"`; `"cell"` (an anchor), `"position"` (`"after"`, the default, or `"before"`) | JSON `{"notebook", "cells"}`: the ids of the new cells. Without `"cell"` at the end of the notebook (`"before"`: at its beginning) |
| ReplaceCells | `"notebook"`, `"cells"`, `"markdown"` | JSON `{"notebook", "cells", "replaced"}`: the new cells go where the first of the cells is (in the notebook's order), then the cells are deleted |
| DeleteCells | `"notebook"`, `"cells"` | JSON `{"notebook", "deleted"}` |

`"cells"` is a list of cell ids separated by commas, semicolons or white space (brackets and quotes are ignored, so a JSON array in a string works too). `$acpNotebookEditTools` (`{"InsertCells", "ReplaceCells", "DeleteCells"}`) are the tools that change notebooks the user already has open: whether the agent may run them is decided by the agent's permissions, never by a dialog.

**Which notebooks.** Only the notebooks that ListNotebooks lists can be reached, by any of the tools: `SourceNotebookObjectInformation[]`'s `"Included"` notebooks (not excluded from AI with `"ExcludeFromChat"`, which also leaves out the Review, Sessions and folder picker windows; visible; normal windows, not palettes or dialogs; no workspace chats, such as the ACP window and the Notebook Assistant; no prompt notebooks of the ACP window, `"ACPPromptNotebook"`, see [Attachments](#attachments)), without the Messages window, help pages (`"DocumentType"` `"Help"`) and deployed notebooks, front to back as `Notebooks[]` gives them.

**Ids.** A notebook's id is the start of its UUID (`First @ nbo`), a cell's the start of its cell UUID (`First @ cell`): 8 characters, more where that is needed to tell it from the other listed notebooks or from the notebook's other cells (`uniqueIDs`). Notebooks or cells that share a UUID (a copy of a notebook file opened twice, cells written with the same `ExpressionUUID`) also get their instance UUID (`<uuid>.<instance>`). The tools accept the id, the whole UUID (in any case, with or without quotes) or any start of it with at least 6 characters that matches one notebook or cell; for notebooks also the exact window title or the file's full path. Several matches are an error that lists them. The agent never sees `NotebookObject[...]` expressions, and nothing it sends is `ToExpression`'d.

**Reading.** ReadNotebook gives a header (title, id, file, unsaved changes, number of cells, where the user's selection is, and a one-line legend) and then each cell as `<cell id='...' style='...' label='...'>...</cell>` (the label is the cell's In/Out label, taken out of the cell). The content is `CellToString`'s markdown (`"ContentTypes" -> {"Text"}`, at most 8000 characters per cell and 1000 per output, with `" ... "` where text was left out; Wolfram Language code in ```` ```wl ```` blocks), so it is the same kind of markdown that the tools that write cells take. Before the conversion the cells are defused like an attached notebook's (`acpDefusedCells`, see "Reading notebooks"): an open notebook may come from anywhere, and CellToString would run an inline WL code template's code, import a video or audio box, or interpret a crafted box. (`NotebookRead`'s own evaluation of the cells' option values and a `DynamicBox` in a cell, which CellToString's box fallback evaluates, are open issues: see Notes/ACPImplementation.md.) Graphics and images (`GraphicsBox`, `Graphics3DBox`) are read as `[graphics]`, and the expression URIs that `CellToString` makes for other content it can't show as text (video, audio, dynamic content), which refer to the kernel's `$attachments`, as placeholders such as `[video]`. The user's selection is marked like the Notebook Assistant marks it: `<selection>...</selection>` around selected text or around a selected cell's content (the Notebook Assistant's `insertSelectionMarkers`), `<selection></selection>` at the cursor, also between cells. The selection is found without asking the front end about every cell (``Developer`CellInformation`` for all the cells of a notebook with 10,000 cells takes 2.7 s; `selectionCursors`): `SelectedCells` gives the selected cells and the cell with the cursor or selected text, wherever they are, and only a cursor between cells is looked for with ``Developer`CellInformation``, 50 cells at a time, in the cells from 1000 before the cells read to 1000 after them (`$cursorScan`), and if it is not there, next to the first and the last cell, with one call for both (`cursorAtEnds`: before the first and after the last cell are where the cursor of a new notebook, or of one whose last cell the user just evaluated, is); when it is not found, the header says `none in cells X-Y`. For a cursor or selected text in an inline cell (such as a formula in a text cell), `SelectedCells` gives the inline cell, which `Cells` does not list, and the front end gives no `"CursorPosition"` for the cell that has it: the inline cell's `"InlineCellPosition"` gives its position in each inline cell that has it and finally in the cell, and as many `ParentCell` steps (at most 10, `topLevelCell`) lead to that cell, the header says `the cursor or selected text is in an inline cell (such as a formula) of cell N (id ...)`, and the whole inline cell is marked as selected (at that last position, `selectedCursor`). An attached cell (such as an input field or a menu attached to a cell) is not taken for an inline cell: `ParentCell` leads from it to the cell it is attached to too, but its position is -1, so the cursor is then looked for between cells. A cell is only marked if it gets both markers: `insertSelectionMarkers` leaves out the marker of a position right before an inline cell that starts the cell's text, and such a cell is shown without a mark rather than with half of one. Text in the notebook never passes for the read's structure: in the cells' text, and in the title and file name of the header, the `<` of anything that looks like its tags (`<cell`, `</cell`, `<selection`, `</selection`, in any case) is written as `&lt;` (`inertTags`; other `<`, as in code, are kept), and text that already looks like such an escape (`&lt;cell`, `&amp;lt;cell`, `&amp;amp;lt;cell`, ..., in any case) gets one more `amp;` so it stays distinct from an escaped tag; the write tools remove one `amp;` from each of these, and turn `&lt;` before a tag name back into `<` (`uninertTags`), so text read from a cell can be written back unchanged. The selection is first marked with markers that the notebook can't have (letters and a random UUID, `selectionMarkers`), which become `<selection>` tags after that. `CellToString` takes time in proportion to the size of a cell's boxes, also of the parts it leaves out (about a second per megabyte), so a cell with more than 1 MB of boxes, once its graphics are replaced, is read as `[this cell is too large to read: N MB]`. Cells are read from the front end 50 at a time, and a read has at most 1000 cells (a larger `"limit"` is lowered, `$maxReadLimit`), stops before 60,000 characters of cells, and reads no more cells after 5 seconds (`$readTimeBudget`; it shows at least one cell); the result then ends with `Showing cells X-Y of N; call again with offset=Y+1 to read more.` CellToString runs without touching the state of chats (`withoutChatState`): its base prompt bookkeeping (`needsBasePrompt`) is turned off and its expression URIs go to a temporary `$attachments`, so a tool call can't change the base prompt of a chat it interrupted.

**Writing.** New cells are made from markdown only, like the cells of Chatbook's own CreateNotebook tool: `FormatChatOutput`, `ExplodeCell` and `InlineTemplateBoxes` (headings become Title, Section, Subsection and Subsubsection cells, ```` ```wl ```` blocks Input cells, which are not evaluated, other code blocks cells of their language). The formatter runs in its untrusted-content mode (`withUntrustedContent`, a switch in `Formatting.wl` shared with the ACP window's own rendering of agent text): for a chat answer it would import markdown images (from a URL, a file or a cloud object, with no time limit), and its special forms of Wolfram Language code (`formatSpecialBoxes`, for code blocks and inline code) would query Wolfram|Alpha (`\[FreeformPrompt]`), the resource system and the paclet repository, and evaluate `DateObject[...]` expressions with their options, which can be any code. Under the switch none of that happens: each markdown image becomes a text cell with a link to its URL or file, labeled with its alt text; code is kept as it is written; and HTML entities are not decoded (so the escaping that the read applies, `inertTags`, is reversed exactly by `uninertTags` and every other `&...;` is kept verbatim). Text that looks like a `Cell[...]` expression stays text. The private-use characters of the front end's linear syntax are replaced first (`acpNeutralizeLinearSyntax`): in a cell's string they would make the front end show boxes chosen by the agent, such as a `DynamicBox` that evaluates code when the cell is shown. Cells with anything else that can run code (dynamic boxes and expressions other than the formatter's front end resources, `ActionMenuBox`, event handlers, button functions, initialization and evaluation options) are refused with an error. Markdown is at most 20,000 characters per call (`$maxMarkdownLength`), and its conversion is stopped after 10 seconds (`$markdownTimeLimit`) with an error and nothing written: the formatter is made for chat answers and takes a few milliseconds for each piece of inline markup (about 7 ms for an emphasized word, 14 ms for a link), and `ExplodeCell` fails beyond about 4000 pieces. Cells are written with `NotebookWrite[NotebookLocationSpecifier[cell, "After" | "Before"], cells, None]` and deleted with `NotebookDelete`, so the user's selection does not move (only an empty notebook gets its selection moved to its only place). The tools refuse notebooks that are not editable, and deleting or replacing cells that are not deletable or that are being evaluated. Everything is checked before anything is changed. The new cells' ids are those of the cells that were not in the notebook before the write. Converting the markdown can take seconds, during which the front end stays usable, so InsertCells and ReplaceCells convert it first and then look at the notebook's cells, resolve the cell ids, check the cells and write, back to back (`writeCells`): a cell that the user adds during the conversion is not taken for a new one (which a later DeleteCells of the agent could delete), and a cell that the user starts to evaluate or makes undeletable meanwhile is not replaced.

**Where the tools run.** Every tool makes front end calls (`Notebooks`, `Cells`, `NotebookRead`, ``Developer`CellInformation``, `NotebookWrite`, and inside `CellToString` and `FormatChatOutput`), which a SocketListen handler or an ACPLink reader handler must never make (rule R2), and reading a long notebook can take a while, which in the pump (or any other preemptive evaluation) would block the front end's `Dynamic`s for as long. So the tools must run on the kernel's main link (a queued evaluation: the MCP server's drain, see [MCP server](#mcp-server)). Without a front end (`$FrontEnd === Null`, which is also what the pump's tasks see under `UsingFrontEnd`), ListNotebooks gives `[]` and the other tools give an error. Internal failures give the agent only "The ... tool failed because of an internal error in Chatbook." and are logged as `"NotebookToolFailed"`.

Limitations: the agent sees no graphics or images (only `[graphics]`), so replacing a cell that has some with the markdown that was read loses them; markdown is converted like a chat answer, so cells that are rewritten from what was read can come out slightly different (styles, options and the boxes of typeset outputs are not kept); no tool evaluates cells.

Tool descriptions and errors are texts for the agent, not for the user, so they are not in the `.tr` files. `Tests/ACPNotebookTools.wlt` tests the tools on real notebooks under `UsingFrontEnd` (it starts a front end if the test kernel has none, and gives `Missing["TestSkipped"]` if none can be started) and closes every notebook it opens.

## MCP server

`MCP.wl` offers the [notebook tools](#notebook-tools) to the agent as an MCP server. AgentTools' `StartMCPSocketServer` runs a Streamable HTTP MCP server inside the kernel (SocketListen on 127.0.0.1, a free port, the path `/mcp`), and the sessions of a local window pass it to the agent in `session/new`, `session/load` and `session/resume` (the same entry for all three), as an `http` MCP server named `WolframNotebooks`, with a bearer token of the window's connection:

```json
{"type": "http", "name": "WolframNotebooks", "url": "http://127.0.0.1:41234/mcp",
 "headers": [{"name": "Authorization", "value": "Bearer <64 hexadecimal digits>"}]}
```

The name is not `Wolfram`: OpenCode registers the MCP servers of ACP sessions per project folder by name, and a `Wolfram` server would replace the user's own Wolfram MCP server.

**When.** `acpConnect` (in the pump) calls `acpMCPEnsureServer[]` before it starts the agent of a local window that offers the server (`acpMCPEnabledQ[agent, settings]`: `"ACPMCPServer" -> True`, or `Automatic` with the agent's own program, see [Settings](#settings)): it starts the kernel's only server unless it runs, and replaces one that no longer runs (e.g. deleted by hand). Right after the connection is claimed, before `initialize` is sent, `acpMCPConnectionStarted` gives the connection its token. `acpMCPServersParam[window]` (pure, also used in reader handlers) gives the entry, or `{}` for a remote window (its agent can't reach this computer's 127.0.0.1, and ssh's forwardings are off, see [Security](#security)), for a window that doesn't offer the server, without a server or a token, and when the agent's `agentCapabilities.mcpCapabilities.http` is neither `true` nor an object.

**Lifetime.** The server listens only while it is used, because SocketListen accepts every connection before AgentTools can check its token, and the 15.0.1 kernel leaks file descriptors for each accepted connection (see [Security of the MCP server](#security-of-the-mcp-server)). Housekeeping (`serverHousekeeping`, every second while the server runs: the pump keeps running for it, `acpMCPPendingQ`) stops it once no connection has had a valid token for 30 s (`$mcpIdleStopDelay`, logged as `"MCPServerStopped"`), e.g. after the window was closed or disconnected, or its setting was turned off (a connect that finds it running starts the count again); the next connect of a window that offers it starts a new one, on a new port. Starting and stopping the server leaks no file descriptors (20 cycles: none), so the grace period only keeps a reconnect from restarting it. `acpMCPStopServer[]` stops it at once (the tests do); it is never called from the server's handler.

**AgentTools** is optional and loaded on demand, the first time a window needs the server, never when Chatbook loads:

* Only a paclet whose kernel extension lists `` Wolfram`AgentTools`StartMCPSocketServer `` in its `"Symbols"` is loaded (read from its `PacletInfo.wl`), and only if it is the one that `Needs` would load (the first of `PacletFind["Wolfram/AgentTools"]`). Older versions, such as AgentTools 2.2.0 and the one that comes with Wolfram 15.0, are never loaded. An AgentTools that some other code loaded is used if it has the function (`acpMCPAvailableQ[]` tells).
* For development, the environment variable `AGENTTOOLS_DIRECTORY` may point to an AgentTools paclet directory (the one containing `PacletInfo.wl`), which is then loaded with `PacletDirectoryLoad`, like `ACPLINK_DIRECTORY` for ACPLink. `Tests/ACPMCP.wlt`, `Tests/ACPConnection.wlt` and `Tests/ACPSessions.wlt` use `~/AgentTools` if the variable is not set.
* A front end's kernel has usually loaded the installed AgentTools already, at startup: the front end's AI Settings preferences use it (e.g. `` Wolfram`AgentTools`DetectedMCPClients ``), and an AgentTools that comes with Wolfram (2.2.0 and older) has no `StartMCPSocketServer`. Chatbook never reloads an AgentTools that is loaded (it may be in use), with one exception for developers: when `AGENTTOOLS_DIRECTORY` is set and that directory's AgentTools declares the function (and is the one `Needs` would load), it is loaded with `Get` in place of the old one (`reloadAgentTools`, logged as `"MCPAgentToolsReloaded"` with its version), under `PreemptProtect` (no Dynamic of the AI Settings runs while AgentTools' loader clears and defines its symbols again) and without adding its context to `$ContextPath`.
* It is loaded with `` Needs["Wolfram`AgentTools`" -> None] ``, so its context is not added to `$ContextPath`, and its symbols are only referenced through `agentTools["name"]` once it is loaded: kernels (and the MX file) that don't use it never get them.
* Without such an AgentTools the sessions get no MCP servers, logged once per kernel session as `"MCPServerUnavailable"`. A missing AgentTools is looked for again at the next connect; for one that is loaded but too old the result is kept until `AGENTTOOLS_DIRECTORY` changes (so setting it and pressing Reconnect is enough).
* Loading AgentTools from a source checkout takes about 3.5 s, in the pump (the front end's Dynamics stop meanwhile), once per kernel session.

**The server** is an in-memory `MCPServerObject` with the six `LLMTool`s of `acpNotebookTools[]`, Chatbook's version as `"ServerVersion"`, and a short text as `"Prompts"`, which AgentTools sends as the `instructions` of the `initialize` result (OpenCode gives them to the model with the server's tools): the tools work on the notebooks open in the user's front end, unsaved changes included; start with ListNotebooks, whose first notebook is "this notebook"; notebooks and cells are named by the tools' ids; new content is markdown, and nothing is evaluated; InsertCells, ReplaceCells and DeleteCells need the user's approval; a call waits while the user's own evaluation runs. The server has no MCP prompts, so it does not change the `"MCPReady"` heuristic (see [Known limitations](#known-limitations)). AgentTools answers `initialize`, `ping`, `tools/list`, notifications and requests for unknown tools in the handler itself; only `tools/call` (and `prompts/get`) are deferred to Chatbook.

**Tokens.** Each connection gets 256 random bits from a cryptographic source (the key of `GenerateSymmetricKey[]`, like AgentTools' own tokens) as 64 hexadecimal digits. `$mcpTokens` maps a token to its window and connection. The server's `"Authentication"` function, `acpMCPAuthorizedQ` (called in the handler with the request's bearer token, or `None`), accepts a token only while its window's `"Connection"` is still that connection and the window still offers the server (`tokenValidQ`, a pure lookup). Every way a connection ends sets `"Connection"` to `None` or drops the record (`failConnection`, `onAgentExited`, `acpDisconnect` for every reason, `acpForgetWindow`), so revoking needs no hooks of its own, and housekeeping forgets revoked tokens. Turning `"ACPMCPServer"` off (or giving a command line that runs another program, with `Automatic`) revokes the token at once: the next request gets 401 and queued calls are rejected, while the reconnect still waits for the end of a running turn. A reconnect gets a new token.

### The queue of tool calls

Tool calls never run in the SocketListen handler, and in a notebook front end's kernel they don't run in the pump either (except for the fallback of item 5): both are preemptive evaluations, which stop every `Dynamic`, the pump, ACPLink's readers and every other handler for as long as they run. They run on the kernel's main link; only a kernel without a notebook front end has the pump run them (item 6).

1. **The handler only queues.** AgentTools calls the server's `"EvaluationFunction"`, `acpMCPEnqueue[run, info]`, in the SocketListen handler (rule R2), or, for a request that a client pipelined behind another one on the same connection, in the evaluation that answered that one. It appends the call to a FIFO (`$mcpQueue`, under `PreemptProtect`) and schedules `acpMCPKick[]`. The queued call has no bearer token (`queueEntry`): `info` without its `"Token"`, and the window and connection of the token as `"Caller"`, which the drain checks. Otherwise the token would be in the drain's evaluation stack, which the `"Stack"` of an internal failure keeps (and the debug log records). Meanwhile AgentTools answers the client with an event stream and keeps it alive with comments.
2. **The pump triggers a queued button.** In a notebook front end's kernel, `acpMCPKick` fires the `Method -> "Queued"` button of a hidden notebook with `` MathLink`CallFrontEnd[FrontEnd`TriggerControlBoxObject[box]] `` (the technique of `Developer/FrontEndServer`). Its `ButtonFunction`, `` Wolfram`Chatbook`ACP`Common`acpMCPDrain[] `` (by its full name, which the MX build has too), runs as a main link evaluation: the front end's Dynamics, the pump and the readers keep running while a tool runs, and the call waits behind the user's own evaluations (in order with Shift+Enter cells).
3. **The drain** runs the queued calls in order until the queue is empty; only one drain runs at a time, and it takes the calls that are queued meanwhile. A call that is no longer active (`info["ActiveQ"][]`: answered, cancelled with `notifications/cancelled`, its client gone, its server stopped) is skipped. A call whose `"Caller"` is no longer valid (`tokenValidQ`) is rejected: `info["Reject"]["The ACP connection that made this call has ended."]`. Every other call runs with `run[]`, which evaluates the tool inside AgentTools' state and writes the answer. A call leaves the queue only after it was dealt with, and an internal error answers it with an error, so no call is left waiting: an internal error of Chatbook's (`runQueuedJob`), and also one of AgentTools', for which `run[]` gives a `Failure` (a call that is still active then is rejected with an error). The drain runs in `acpIsolatedAbortable` (like `acpIsolated`, without `AbortProtect`): Alt+. aborts the running tool, and AgentTools' `run[]` answers it "The tool call was aborted by the user."; an abort between two calls ends the drain, and the watchdog starts it again. Only one drain runs at a time (`$mcpDraining`): the drain claims it in the first argument of `WithCleanup`, which an abort can't interrupt, and releases only a claim it made, so an Alt+. that lands right after the claim can't leave the drain claimed for good. Print, Echo and message cells that land in the hidden notebook (the drain's evaluation notebook) are deleted after each drain, except the button's cell; the tools' messages go to the debug log anyway.
4. **The watchdog.** The front end merges the triggers of a button while a run of it is pending, and drops the pending run when the evaluation ahead of it is aborted. So the button drains the whole queue, and housekeeping (`"ACPMCP"`, every second) fires the trigger again when calls wait, no drain runs and the last trigger is more than 3 s old (`$mcpRetriggerDelay`). The pump keeps running while calls wait (`acpMCPPendingQ`, rule R7). Housekeeping also forgets revoked tokens.
5. **The hidden notebook** (`createPump`, made when the first trigger fails): `Visible -> False`, `Saveable -> False`, `ExcludeFromChat` (the notebook tools skip invisible notebooks anyway), the ACP windows' kernel as `Evaluator` (the front end's default kernel may be another one; `$mcpEvaluator`, read from the `Evaluator` of the first window that gets a token in a notebook front end's kernel, `noteEvaluator`: the kernel's name is never guessed, since a button for another kernel would send every later drain there), the TaggingRules key `"ACPMCPPump"` with the kernel session, and one cell with the `ButtonBox` (`BoxID -> "ACPMCPPump"`), found with `` FrontEnd`BoxReferenceBoxObject ``. If the trigger fails (no pump yet, or its notebook is gone), the notebook is made again and the trigger fired once more; the pump notebooks of the same kernel (by the TaggingRules key and the `Evaluator`: one that a kernel restart left behind, or an earlier one) are closed first, other kernels' pumps are left alone. If that fails too, or no window has named the kernel yet, the pump drains the queue itself (`"MCPPumpFailed"`).
6. **Without a notebook front end** the pump drains the queue itself (mode `"Pump"`). Only a notebook front end's kernel fires the button (`notebookFrontEndQ`: `$Notebooks`, a `FrontEndObject` and a parent link). Under `UsingFrontEnd` (the tests, CI), the main evaluation has `$Notebooks` and a front end but no parent link, and the pump's tasks see `$FrontEnd === Null`: firing a queued button in that front end could make it start a kernel of its own. There, ListNotebooks lists nothing and the other tools give their no-front-end error.
7. **Other main link jobs.** `acpMainLinkRun[nbo, eval]` queues other ACP work that makes front end calls and can take seconds (the preparation of a message's [attachments](#attachments)) in `$mcpJobs`; the drain runs the jobs after the tool calls, each inside `acpIsolatedAbortable`, and the watchdog and the pump treat them like calls. A job leaves the queue before it runs, so an aborted job is not run again (it cleans up itself). The window names the kernel of the pump button (`noteEvaluator`). Each job is logged as `"MainLinkJob"` (`"Label"`, `"Mode"`, `"Waited"`, `"Seconds"`).

### Security of the MCP server

* The server listens on 127.0.0.1 only. Every request needs `Authorization: Bearer <token>` of a connection that is still open, otherwise it gets 401 (OpenCode then marks the server as failed). Tokens are compared by an `Association` lookup in the handler (`acpMCPAuthorizedQ`); a token has 256 random bits.
* AgentTools refuses requests whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>`, and whose `Origin`, if there is one, is not one of those two origins (403), so web pages can't reach the server (DNS rebinding). `GET` and `DELETE` get 405.
* A token is a secret: it is in `$mcpTokens` and in the parameters of the session requests only (which ACPLink writes to the agent, and the mock agent's wire log records in tests), never in the window record, the TaggingRules, the queue of tool calls (so not in the evaluation stack of a drain either), the debug log, a Failure, a message or a persisted setting. The server authenticates with a function, so the server object (and its summary box) holds no token. `Tests/ACPMCP.wlt` checks this (`ACPMCP-Agent-SessionNew`, `ACPMCP-Queue-TokenNotInStack`).
* Whoever has the token (the agent and the commands it runs) can read the notebooks the tools reach and change them; the tools never evaluate code (see [Notebook tools](#notebook-tools)).
* OpenCode asks the user before the tools that change notebooks the user has open: its inline config has `"ask"` rules for `WolframNotebooks_InsertCells`, `WolframNotebooks_ReplaceCells` and `WolframNotebooks_DeleteCells` (`acpMCPToolPermissions`, from `$acpNotebookEditTools`). OpenCode checks the permission `<server>_<tool>` (characters outside `[a-zA-Z0-9_-]` replaced by `_`) before it calls an MCP tool, and allows MCP tools by default. ListNotebooks, ReadNotebook and CreateNotebook don't ask. In code mode the request names neither the tool nor its input, only the script: the permission panel shows the script, the tools it names and the arguments it shows (see [Scripts and the notebook tools](#scripts-and-the-notebook-tools)). "Always allow" turns the rule off for that tool in the project for good (OpenCode's saved rules come after the config's). These rules are in `OPENCODE_CONFIG_CONTENT`, so they only hold for an agent that gets the window's environment: with `"ACPMCPServer" -> Automatic`, a command line that runs another program than the agent's (which may not pass the environment on) gets no server; with `True` it does, and its agent may then change the open notebooks without asking.
* File descriptors (unauthenticated): SocketListen accepts every connection before AgentTools can look at it, and the 15.0.1 kernel leaks file descriptors for each accepted connection (measured: about 4 for a connection that the client closes, about 2 for one the server refuses and closes), which are never given back, not even when the server is stopped. Any local process (another local user, or a web page in a browser without local network access protection that found the port) can therefore use up the kernel's file descriptors without a token: past select()'s limit of 1024 the kernel's SocketListen stops working (a front end's kernel then no longer answers on any socket) or the kernel crashes. Every exit of OpenCode also leaks some for its own connections. What limits an attack is that the server listens only while a connection uses it (see Lifetime above): a local process can do this only while a window's agent is connected, and for 30 s after that. On Linux housekeeping also counts the kernel's file descriptors (`/proc/self/fd`, every 5 s while the server runs and before it starts): above 75% of the limit (the soft limit of open files, at most 1024: `fileDescriptorLimit`) it stops the server, logs `"MCPServerFdLimit"` and starts no server for the rest of the kernel session (`$mcpFdLimitReached`; sessions then get no MCP servers). This guard only catches slow growth, such as the leaks of many reconnects of OpenCode: a deliberate flood passes 1024 between two counts (about 64 connections take 0.05 s, measured with a connect-and-close loop), so it does not protect against an attacker. Other systems have no such guard.

### The agent's side

OpenCode 2.0.26 advertises `mcpCapabilities.http` and connects to the server when the session is attached; `initialize` and `tools/list` are answered in the handler, so a busy main link does not delay `session/new`. It sends no `Origin`, appends `?codemode=false` to the URL (the server routes on the path), and keeps its HTTP connections alive. In its default Code Mode the model does not call the tools directly: it calls OpenCode's `execute` tool with JavaScript that calls `tools["WolframNotebooks"]["ListNotebooks"](...)`, and gets the results that start with `{` or `[` parsed as JSON (the tools give JSON for that reason). In the window such a call is a card of the `execute` tool, whose Input section shows each call with its arguments (see [Scripts and the notebook tools](#scripts-and-the-notebook-tools)). A tool call can wait up to OpenCode's 12-hour timeout; AgentTools keeps its event stream alive every 15 s.

### Limitations of the MCP server

* Remote windows offer no server: their agent runs on another computer, and ssh's forwardings are off.
* Tool calls wait while the user evaluates something in the kernel, including a dialog such as `DialogInput`; Alt+. aborts the running tool (and whatever runs ahead of it). Calls of one kernel run one at a time.
* The server runs (with AgentTools' maintenance task, every 5 s, and the pump) while a connection uses it and for 30 s after that; a reconnect after that gets a new port.
* The first connect of a kernel session loads AgentTools in the pump (about 3.5 s from a source checkout).
* The 15.0.1 kernel leaks file descriptors for every connection the server accepts (about 4 for one that the client closes), with or without a token, and they are never given back. OpenCode keeps its connections alive, but each exit of it leaks some, so a kernel session with very many reconnects reaches the file descriptor guard, after which the notebook tools are off until the kernel restarts (`"MCPServerFdLimit"`; see [Security of the MCP server](#security-of-the-mcp-server)). The guard exists only on Linux, and it counts every 5 s, so a local process that opens many connections at once passes select()'s limit before it acts.
* The tools see the notebooks of the front end that the kernel belongs to; with several front ends or kernels, each kernel's ACP window offers its own server.

### Testing the MCP server

`Tests/ACPMCP.wlt`: the setting (also with command lines of the agent's own program or of another one) and the permission rules, `acpMCPServersParam` (capability on, an object, off or missing; remote; setting off; a command line of another program, with `Automatic` and `True`; no server; no token; another connection's token), tokens (issue, randomness, revocation by another connection, `connectionFailedRecord`, `acpDisconnect`, `acpForgetWindow`, turning the setting off, housekeeping), the queue with made-up calls (drain in the pump, order and statuses, rejects of ended connections, skipped inactive calls, internal errors of Chatbook and of AgentTools' `run[]`, no token in the stack of a logged internal failure, the watchdog, the pump kept running, aborts at random points of a drain never leaving it claimed), `notebookFrontEndQ` under `UsingFrontEnd`, the pump notebook (its expression; with a front end it is made and closed again, never fired; the kernel named by a window, never guessed), the server's lifetime with a made-up server (the idle stop and a connect restarting its count, the file descriptor guard with made-up counts and limits), loading AgentTools (a made-up AgentTools that is too old, replaced only with `AGENTTOOLS_DIRECTORY`; that Chatbook does not put AgentTools on `$ContextPath`), the server (start, reuse, restart, HTTP: `initialize`, `tools/list`, a tool call through the queue, 401s, also after the setting was turned off; an idle stop and a restart), and the mock agent: the session's entry and that its token is nowhere else, the `mcp_request` steps (`initialize`, `notifications/initialized`, `tools/list`, a `tools/call` of ListNotebooks, which gives `[]` headless, and 401 for a wrong or no token), a reconnect's `session/resume` with a new token, an agent exit revoking its token, no server with the setting off or without the capability, and a command line of another program (`env`) with and without `"ACPMCPServer" -> True`. The queue and parameter tests run everywhere; the server tests need an AgentTools with `StartMCPSocketServer` (`AGENTTOOLS_DIRECTORY`, default `~/AgentTools`), the agent tests also ACPLink and python3; CI has none of them, so those give `Missing["TestSkipped"]`. `Tests/ACPConnection.wlt` and `Tests/ACPSessions.wlt` expect the server's entry in their sessions when AgentTools is available (`mcpServersExpected`), else `{}`.

**In a real front end** (manual checks): the front end's kernel has the installed AgentTools loaded from its startup (see the AgentTools items above), so a `PacletDirectoryLoad` of an AgentTools checkout is not enough. Set `AGENTTOOLS_DIRECTORY` in the kernel (`SetEnvironment["AGENTTOOLS_DIRECTORY" -> "/path/to/AgentTools"]`, the directory of its `PacletInfo.wl`) before the window connects, or press Reconnect afterwards: Chatbook then loads that AgentTools in place of the installed one (`"MCPAgentToolsReloaded"`). Open the window, and check the debug log for `"MCPServerStarted"` (the port), then, after the agent called a tool, `"MCPPumpCreated"` and `"MCPToolCall"` with `"Mode" -> "MainLink"`. `` Wolfram`Chatbook`ACP`Common`acpMCPServer[ ] `` is the server object (`"Port"`, `"URL"`, `"Running"`, `"PendingRequests"`), `` Wolfram`Chatbook`ACP`MCP`Private`$mcpQueue `` the queued calls, and `` Wolfram`Chatbook`ACP`Common`acpMCPServersParam[ nbo ] `` the entry of the window's sessions (it contains the token).


  A window works the same way: `ShowNotebookAssistance["ACPWindow", "ChatNotebookSettings" -> <| "SSHSettings" -> ssh, ... |>]` connects to the fake home (`$FAKE_SSH_HOME`), with `"ACPAgentCommandLine"` giving the agent's absolute path (the fake's `PATH` is `/usr/bin:/bin`). `Wolfram`ChatbookTests`ACPFakeSSH`fakeSSHCleanup[ ]` restores the environment.
* CI runs every test file in one kernel under `UsingFrontEnd` (`Scripts/TestPaclet.wls`), so the tests must pass with and without a front end. Persisted settings (`acpPersistedSetting`, `acpSetPersistedSetting`) use `$headlessSettings` only when `$FrontEnd === Null`. Under `UsingFrontEnd` only the main evaluation has the front end: the pump's tasks see `$FrontEnd === Null`, so a value that the pump writes is not read back from the front end's preferences. Tests that set or check persisted settings, or that rely on running without a front end (a picker that gives `"Opened"`), therefore run inside `Block[{$FrontEnd = Null, ...}, ...]`, including their waits for pump work (the pump's tasks run inside the `Block` while a test waits). They then behave the same with a front end and never write its preferences:
  * `Tests/ACPConnection.wlt`: `ifRemoteTests` runs every remote test this way, and the snapshot `$savedRemotePersisted` and `Cleanup-RemoteRestore` use the same store.
  * `Tests/ACPFolderPicker.wlt`: `headless[...]` wraps every test after the definitions, and `Cleanup-FrontEndPreferences` fails if any write reached the front end's ACP preferences.
  * Single tests (`PersistedSettings-Headless` and `ConfigOption-ModelPersisted` in ACPConnection, ACPSessions' `Restore-PendingConfigOfLeftSession`, ACPWindow's persisted-setting tests) also block ``Wolfram`Chatbook`ACP`Agents`Private`$headlessSettings``, to a fixed value or to its own value, so that their writes are dropped afterwards.
  * The `Cleanup-Restore` tests of ACPConnection and ACPSessions put back only the settings that changed: with a front end, writing `Inherited` to an unset `{"LastModel", agent}` would leave an empty `"LastModel"` in its preferences.
  * `Tests/ACPRemote.wlt` and `Tests/ACPGit.wlt` don't depend on persisted settings or the front end.

  `Tests/ACPWindow.wlt` has a few front-end-only tests that run when the test kernel has one. In a kernel without a front end, `Block` can't give `$FrontEnd` another value than `Null`, so a front end can't be simulated that way.
* CI's `TestPaclet` also evaluates every test file in one context (``PacletCICDTest` ``), so the files' helpers share their symbols: a helper that another `Tests/ACP*.wlt` file defines too (`newWindow`, `newRemoteWindow`, `remoteSSH`, `waitUntil`, `logSince`, ...), with other arguments, would otherwise also match calls of the later file. Each file's definitions start with a `ClearAll` of those names; a new helper whose name another file uses goes there too. A test file passing on its own is therefore not enough: run the files in one kernel in `FileNames` order with that context, as CI does, before relying on CI.

## Known limitations

* Only OpenCode is supported as an agent (the registry in `Agents.wl` has room for more).
* The conversation is not forwarded from other notebooks. Notebook context is not attached to prompts automatically: the user attaches open notebooks and files of this computer to a message (see [Attachments](#attachments); not files of a remote host or pasted images yet), and the agent can read open notebooks with the [notebook tools](#notebook-tools) (see [Limitations of the MCP server](#limitations-of-the-mcp-server)). Images pasted into the input field still reach the agent as box text.
* There is no message editing in ACP: a message can't be edited, taken back or sent again in place of an earlier one (OpenCode's own undo is a command of its interface that ACP does not reach, and ACP's `session/fork` copies the whole session). Sending a [prompt notebook](#prompt-notebook) again is a follow-up in the same session; after New it starts a new session, and the files changed by the first attempt stay changed (the Review button shows them; nothing in the window discards them).
* A saved prompt notebook keeps its last status ("Sent at ...") and its link to an ACP window of that front end session: opened later, it says that it is not linked, and its first Send links it to the open ACP window instead of sending.
* A message's attachments are prepared on the kernel's main link: while the user's own evaluation runs, Send waits (the note says "Preparing..."; Stop gives the message back), and after 180 s it is given back.
* There is no "MCP servers starting" indicator in the toolbar: OpenCode often never reports the MCP server's prompts (the listing can time out) even though its tools work. While a turn waits more than 5 s for the first event, the Working header says "Waiting for OpenCode... (MCP servers may still be starting)".
* The model menu uses native `ActionMenu` submenus; long model lists are long menus.
* The reserves of one-line titles and of the toolbar's labels (see [Tool cards](#tool-cards) and [The toolbar](#the-toolbar)) were measured in a real front end on Linux only (Xvfb, 96 dpi). Texts are measured by the front end that draws them, at the drawn size, on any platform; the reserves are layout, split into the screen points that magnification does not scale and the points it scales. On Windows at high DPI (or macOS), where pixels are smaller and the scroll bar, the cells' own screen points or the buttons' fonts may differ, a cut title may end a few points earlier, or be clipped at its edge by its pane (a path at its start, keeping its file name) if the room is smaller than computed. A cell copied into a notebook with another stylesheet (Default.nb, a Chatbook notebook) has other cell margins: its cut titles are clipped by their panes instead of ending with an ellipsis.
* The tool icons of cards are `DynamicBox`es of Chatbook's `"ToolIconCall..."` function front end resources (not the `"ToolIcon..."` templates, which made pastes slow: see [Tool cards](#tool-cards), "Copies and pastes"), and the divider's images are Chatbook's bitmaps (`FrontEnd`FileName[{"Chatbook"}, ...]`). In a copy pasted into a notebook with `Evaluator -> None` they draw; a saved copy opened in a front end without any kernel running was not checked again (the templates drew blank there). They draw only where a Chatbook paclet with these resources (2.7.35 or later, the first version after PR #1686) is installed.
* The colors of the cards' states were checked on Linux (Xvfb) only: light and dark, under the pointer and with the mouse button down; `CurrentValue["MouseButtonTest"]` is the state of the button anywhere, so a line that the pointer crosses while a selection is dragged elsewhere has the "Pressed" color.
* Chatbook's own chat cells use `ThoughtsOpener`s too (and their tool call openers use `DynamicBox`es of the `"ToolIconCall..."` function front end resources): pasting a copy of such a cell with its openers open may be slow in the same way, or hang without a kernel like the "Worked for" template did (not measured).
* In a notebook with the ACPChat stylesheet (the ACP window, and also a plain notebook with that stylesheet), scrolling a tool card's code block to the end of its own scroll pane and then any re-layout of the window (a resize, 480 → 490 → 480 points) draws the card's body blank below its "Input" label (it stays blank until the card is closed and opened, or the window is redrawn otherwise). Reproduced at magnifications 0.85 and 1, with an 80-line command in an expanded card below the "Worked for" opener (fixture in the fitFix session: the titles fixture with `s1`'s command replaced). It does not happen with the same cell in a Default.nb or Chatbook.nb notebook (Chatbook's code block template, where the card's own height-limited pane scrolls), and not with a bare frame and scroll pane in Default.nb. Ruled out: Copy, the outer `heightLimited` pane, the "Worked for" opener, the `AssistantMessageBox` template (removed: still blank), the template's `Scaled[1]` pane width (`Automatic` and `Full`: still blank), the template's Copy/Insert row (removed: still blank) and the magnification. Probably a front end issue with the WorkspaceChat/ACPChat code block template's scroll pane in this stylesheet; not fixed.
* Without an LLMKit key and without a provider the user signed in to, OpenCode offers its own free hosted models ("OpenCode (free)", e.g. `opencode/cat-jam-free`), on this computer and on a remote one. The window treats that as ready (no `NoModels` or `AuthRequired` error), so prompts go to those models; the model menu shows who pays for them. A configuration with `"disabled_providers": ["opencode"]` gives the `NoModels` error instead.
* Localized `.tr` files contain English text for the ACP strings.
* After a kernel restart, the window reconnects and resumes the agent session if the agent supports `session/resume`; turns that were running are shown as interrupted.
* Sessions can only be listed through a connection: a window without a project folder (or disconnected) lists nothing. Restoring a session of another folder restarts the agent in that folder. A restored session shows only its last 30 turns, without timing, usage or permission decisions (OpenCode does not replay them).
* The Sessions window is a separate window, not a sidebar (see [A real sidebar](#the-sessions-window)); it is placed when it opens (and when the toolbar button brings it back to the front) and does not follow the ACP window. Whether it is hidden behind other windows is judged from `Notebooks[]` being in front-to-back order, which was not checked in an interactive front end (a headless front end has no window stacking). Session titles are shortened by characters (40), not by their measured width, so a wider window still shows the ellipsis (and very wide characters are clipped). Relative times are refreshed by housekeeping, which only runs while the ACP window is connected.
* ACPLink keeps the agent's standard output in a file until the connection is closed, so a window that stays connected for a very long time uses more and more disk space until the window is closed or the kernel is restarted (New keeps the connection).
* Saving the window uses Chatbook's Save As (`SaveAsChatNotebook`); ACP cells convert like notebook assistance cells.
* The front end's assertion `CellControl.cpp:45` ("overcounted formatting"; `INTERNAL SELF-TEST ERROR: CellControl|cpp|45` in the Messages window, or with many `Dynamic`s a crash) comes from a kernel-initiated replacement or deletion of a cell while the front end evaluates one of the cell's `Dynamic`s. Finalization avoids it (see [Finalization](#state-model)); its earlier reports (while a live view updated, in first turns after a kernel restart, after Stop with an approval pending) match that cause at the final cell's write. Other replacements of cells with kernel `Dynamic`s are not preceded by a freeze: New chat (it deletes every cell, also a running turn's live view), the "Interrupted" note that replaces a live view after a kernel restart (`acpMarkOrphanCells`; checked once, with "Working" open during a burst: no assertion), the rebuilt toolbar and input field, and the final cell of a live view that was scrolled out of view (written after 5 s) if the user scrolls it into view exactly during the write.
* Clicking the live "Working" header quickly and repeatedly (about three clicks a second) while a turn streams can log the front end's assertion `Cells.cpp:1228` (`wnc.cell == wnc.notebook->mouseOverCell`; `INTERNAL SELF-TEST ERROR` in the Messages window). It is not a crash and doesn't happen with single clicks; it was seen before the finalization freeze too, so its cause is not the final write. Not investigated.
* A final cell pasted into a notebook without a running kernel appears only when a kernel has started (16 to 24 s measured, with the development Chatbook loading from source): Chatbook's `ChatOutput` style has an `Initialization` (it attaches the chat menu). Not changed: it is Chatbook's style for all chat output cells (see "Copies and pastes" in [Tool cards](#tool-cards)).
* The openers of single thoughts in final cells (inside "Worked for") are still Chatbook's `ThoughtsOpener` template, which needs a kernel in a copy (`DynamicModuleValues -> Automatic`, and its "Hide" label is a `DynamicBox` of `ToBoxes`; in an `Evaluator -> None` copy the "Worked for" template did not open, and these were not checked). A copy with many of them open was not checked without a kernel.
* Line diffs of large files with many repeated lines and changes spread all over them (past the budget of pairs of equal lines, and without lines that occur once in each text between the changes) show some changes as blocks of removed and added lines, with a note (see [Diffs](#diffs)).
* The permission panel is still part of the attached input cell: its few rows are laid out again on every keystroke and window update. Moving it into a cell of its own (an attached cell) would avoid that. Its layout was measured only headless, not in a real front end on Windows.

Remote mode:

* One login per operation: the agent's connection, every git check (every 60 s while the window is idle, at most every 5 s while files change), every Review refresh and every folder picker listing. Each is a line in the server's auth log and costs a sign-in (about 0.3 to 2 s over a WAN, plus one round trip for READY, plus the picker's 150 ms debounce). Failed logins add up in fail2ban and sshd's `PerSourcePenalties`, which can refuse this computer for minutes; the host failure latch keeps Chatbook's automatic runs out of that, but repeated manual reconnects with a wrong key still count. Administrators can exempt clients with `PerSourcePenaltyExemptList`.
* Remote hosts that need interactive sign-in (passwords, keyboard-interactive or MFA, a key with a passphrase that is not in an ssh agent) can't be used: ssh runs with `BatchMode=yes`.
* Host keys are always checked, whatever the user's ssh config says, except that a config with `VerifyHostKeyDNS yes` may accept a key from a DNSSEC-signed SSHFP record instead of known_hosts. A host behind `StrictHostKeyChecking no` or `UserKnownHostsFile /dev/null` needs its key kept in a known_hosts file first. Jump hosts take `BatchMode` and their host key policy from `~/.ssh/config` only.
* On Windows the terminal command of the host key and sign-in instructions follows the C runtime's quoting rules, not a particular shell's. In cmd.exe, an argument that contains both `"` and one of `&`, `|`, `<`, `>`, `^` is not passed on intact (cmd toggles its own quoting at every `"`). In PowerShell, a quoted program path (an `"Executable"` with spaces) needs the call operator `&` in front, PowerShell reads an argument that contains `"` differently, and it expands `$` and backticks inside double quotes. Keep such options (e.g. a quoted `ProxyCommand` path) in the ssh config file.
* The persisted home of a host seeds a new remote window's `"RemoteHome"`, and a `~` folder given later for the same host (`ShowNotebookAssistance` with `"ProjectDirectory" -> "~/q"`) is expanded with it until a launch reports the real home. If an ssh config alias now points to another machine, a window that has never launched can therefore get `<old home>/q` for `~/q`; its first launch, even a failed one, corrects the home, and choosing the folder again fixes the folder. A window's own `~` folder is always left to the launch.
* An open folder picker in an error state uses changed `"SSHSettings"` of the same host only on the next click (Try again, Refresh, navigation); it does not refresh by itself.
* A remote folder name with an emoji's presentation selector (U+FE0F) shows the selector as `⟦U+FE0F⟧`: variation selectors are shown, since a run of them can carry hidden text.
* An explicit `-A`, `-X` or `-K` in `"Arguments"` turns agent, X11 or Kerberos forwarding back on: the agent's shell commands on the remote computer can then use the user's ssh agent or Kerberos ticket.
* A remote agent may outlive a dropped network until the server notices (TCP keepalive, about 2 hours, unless the server sets e.g. `ClientAliveInterval 30`); a reconnect then runs a second agent on the same project for a while. Processes that the remote agent started (e.g. a dev server of a shell tool) end only if OpenCode ends them when its standard input closes: ACPLink's process tree kill reaches only local processes.
* Login shells: restricted shells, `ForceCommand`, `command=` keys and login shells that don't run the command give `RemoteScriptFailed`. Startup files that print to standard output make ACPLink answer the noise with a parse error (the setup continues), and one-shot runs end after 64 KB of it without READY (`NoReady`); startup files that read standard input take the script.
* Only OpenSSH clients are supported: `"Arguments"` are validated against OpenSSH's options (an option of a newer OpenSSH is refused until the table is updated), and `plink` is not supported.
* One-shot scripts drop relative and empty `PATH` entries; the agent keeps the account's `PATH`, so with `.` in it the agent's shell commands find programs in the project folder, as they would for that account locally.
* Review's "Open" and the Sessions window's "open folder" are hidden for remote folders. Markdown `file://` links in the agent's text are not made remote-aware. Markdown images in the agent's text show as links to their source in both local and remote windows (they are never fetched).
* The Wolfram MCP server (or any MCP server) must be configured in OpenCode on the remote computer: remote sessions get no MCP servers from Chatbook, not even the notebook tools' server. A remote OpenCode without the LLMKit key needs `opencode auth login` there for models other than OpenCode's free ones.
* The folder picker lists at most 1,000 folders and 200 other entries per class (hidden or not); others can be opened by typing their path. Each click takes a sign-in (above).
* The folder picker has no keyboard navigation of its list (no arrow keys or Enter on an entry, no type-to-find); the only keys are Return (Go) and Escape (Cancel) in the path field.
* Git checks and folder listings need a writable `$TMPDIR` or `/tmp` on the remote computer.
* The same `"MachineName"` alias used with different `-F` configs counts as one host for the per-host preferences.
* Remote mode's automated tests run on Linux with a fake ssh; its scripts were checked under dash, bash, busybox and zsh's sh emulation, and its ssh options and error texts against OpenSSH 10.2 with a loopback sshd. Windows clients (`ssh.exe`) and macOS remotes have not been tested on real systems yet.
